## Two Locking Systems in PostgreSQL

PostgreSQL has two separate locking systems:

1. **MVCC** (Multi-Version Concurrency Control): Readers and writers don't block each other. No locks needed for normal SELECT vs INSERT/UPDATE/DELETE.

2. **Explicit Locks**: For DDL operations, and to prevent conflicts between concurrent writes to the same data.

Understanding which lock operations acquire — and which operations conflict — is essential for DBA work.

---

## Table-Level Lock Modes

From least to most restrictive:

| Lock Mode | Acquired By | Conflicts With |
|---|---|---|
| ACCESS SHARE | `SELECT` | ACCESS EXCLUSIVE only |
| ROW SHARE | `SELECT FOR UPDATE/SHARE` | EXCLUSIVE, ACCESS EXCLUSIVE |
| ROW EXCLUSIVE | `INSERT`, `UPDATE`, `DELETE` | SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE |
| SHARE UPDATE EXCLUSIVE | `VACUUM`, `CREATE INDEX CONCURRENTLY`, `ALTER TABLE` (some) | SHARE UPDATE EXCLUSIVE, SHARE, SHARE ROW EXCLUSIVE, EXCLUSIVE, ACCESS EXCLUSIVE |
| SHARE | `CREATE INDEX` (non-concurrent) | ROW EXCLUSIVE and above |
| SHARE ROW EXCLUSIVE | Rare | ROW EXCLUSIVE and above |
| EXCLUSIVE | Rare | Everything except ACCESS SHARE |
| ACCESS EXCLUSIVE | `DROP TABLE`, `TRUNCATE`, `ALTER TABLE` (most), `VACUUM FULL` | EVERYTHING |

**The one that matters most in practice:**

`ACCESS EXCLUSIVE` is acquired by:
- `ALTER TABLE ADD COLUMN` (any)
- `ALTER TABLE ALTER COLUMN TYPE`
- `DROP TABLE`
- `TRUNCATE`
- `VACUUM FULL`
- `CLUSTER`

It blocks **everything** — all reads and writes. Even a simple SELECT cannot run while ACCESS EXCLUSIVE is held.

## The Deadly Pattern: Long Transaction + DDL

```
Session 1 (open for 2 hours):
  BEGIN;
  SELECT * FROM orders;
  -- ... app is slow, hasn't committed yet

Session 2:
  ALTER TABLE orders ADD COLUMN archived boolean DEFAULT false;
  -- BLOCKED: waiting for ACCESS EXCLUSIVE
  -- ACCESS EXCLUSIVE blocks ACCESS SHARE
  -- So now ALL new queries on orders queue behind this ALTER

Session 3, 4, 5... (new connections):
  SELECT * FROM orders;
  -- ALL BLOCKED behind Session 2's ALTER
  -- Which is blocked behind Session 1
```

Session 1 (2-hour-old idle transaction) is blocking Session 2's DDL which is blocking every subsequent query on the table. This is how production incidents happen.

**Prevention:**
```
lock_timeout = 5s          # DDL fails after 5s if it can't get the lock (better than blocking)
statement_timeout = 30min  # Kill runaway queries
idle_in_transaction_session_timeout = 10min  # Kill idle-in-transaction sessions
```

**If you need to do DDL on a busy table:**
```sql
SET lock_timeout = '3s';   -- fail fast if locked
ALTER TABLE orders ADD COLUMN archived boolean DEFAULT false;
-- If it fails, retry later when traffic is lower
```

## Row-Level Locks

When you UPDATE or DELETE rows, PostgreSQL places row-level locks on those specific rows (not the whole table).

```sql
-- Normal UPDATE: row lock held until commit/rollback
BEGIN;
UPDATE orders SET status='processing' WHERE id = 42;
-- Row 42 is locked. Other transactions cannot UPDATE/DELETE row 42.
-- Other transactions CAN SELECT row 42 (MVCC — they see the old version).
COMMIT;
```

**SELECT FOR UPDATE / SELECT FOR SHARE:**

```sql
-- Lock rows for update (you intend to update them)
SELECT * FROM orders WHERE id = 42 FOR UPDATE;
-- Row 42 is now locked — no one else can update/delete/lock it

-- Skip locked rows (don't wait)
SELECT * FROM orders WHERE status = 'pending' FOR UPDATE SKIP LOCKED;
-- Common pattern for job queues — each worker grabs unlocked rows
```

`SKIP LOCKED` is great for implementing work queues:
```sql
-- Worker process:
BEGIN;
SELECT * FROM jobs WHERE status = 'pending' FOR UPDATE SKIP LOCKED LIMIT 1;
-- Process the job
UPDATE jobs SET status = 'done' WHERE id = ...;
COMMIT;
```

## Deadlocks

A deadlock happens when:
- Session A holds lock on row 1, wants lock on row 2
- Session B holds lock on row 2, wants lock on row 1
- Neither can proceed

```
Session A:
  BEGIN;
  UPDATE orders SET status='X' WHERE id = 1;   -- locks row 1
  -- ... (something slow happens)
  UPDATE orders SET status='Y' WHERE id = 2;   -- BLOCKED by Session B

Session B:
  BEGIN;
  UPDATE orders SET status='A' WHERE id = 2;   -- locks row 2
  UPDATE orders SET status='B' WHERE id = 1;   -- BLOCKED by Session A
  -- DEADLOCK!
```

PostgreSQL detects deadlocks automatically (every `deadlock_timeout` seconds, default 1s). When detected, PostgreSQL kills one of the transactions (picks the one with less work done) and the other proceeds.

The killed transaction gets: `ERROR: deadlock detected`

**Fix at the application level**: Always lock multiple rows in the same order. If your app always updates rows in ascending ID order, deadlocks between the same pair of rows become impossible.

```sql
-- Instead of: UPDATE orders WHERE id IN (2, 1)
-- Do: UPDATE orders WHERE id IN (1, 2) ORDER BY id ASC
```

**Monitor deadlocks:**
```sql
SELECT datname, deadlocks FROM pg_stat_database;
-- If deadlocks is increasing → app has an ordering bug
```

## Advisory Locks — Application-Level Locks

Advisory locks are user-defined locks. PostgreSQL manages the locking mechanism, but your application defines what the lock IDs mean.

Use case: You have a cron job that shouldn't run concurrently. You want a distributed lock.

```sql
-- Try to acquire lock (returns true if acquired, false if already held)
SELECT pg_try_advisory_lock(12345);

-- Do the work
-- ...

-- Release lock
SELECT pg_advisory_unlock(12345);
```

```sql
-- Wait until acquired (blocking)
SELECT pg_advisory_lock(12345);

-- Session-level: held until session ends or explicit unlock
-- Transaction-level: released at end of transaction
SELECT pg_advisory_xact_lock(12345);
```

**Useful for:**
- Ensuring only one instance of a cron job runs at a time
- Application-level resource locking
- Coordinating distributed processes via PostgreSQL as a locking server

## Monitoring Locks

```sql
-- See all currently held locks
SELECT
    pid,
    locktype,
    relation::regclass,
    mode,
    granted,
    wait_start,
    now() - wait_start AS wait_duration
FROM pg_locks
LEFT JOIN pg_stat_activity USING (pid)
WHERE relation IS NOT NULL
ORDER BY wait_duration DESC NULLS LAST;

-- Find blocking chains
WITH RECURSIVE lock_chain AS (
    SELECT
        blocked.pid AS blocked_pid,
        blocker.pid AS blocker_pid,
        blocked_act.query AS blocked_query,
        blocker_act.query AS blocker_query
    FROM pg_locks blocked
    JOIN pg_locks blocker ON blocker.transactionid = blocked.transactionid
    JOIN pg_stat_activity blocked_act ON blocked_act.pid = blocked.pid
    JOIN pg_stat_activity blocker_act ON blocker_act.pid = blocker.pid
    WHERE NOT blocked.granted AND blocker.granted
)
SELECT * FROM lock_chain;

-- Simpler: find anything waiting on locks
SELECT pid, wait_event_type, wait_event, state, query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
```

## Lock Timeouts

```sql
-- Set lock_timeout for a specific statement
SET lock_timeout = '5s';
ALTER TABLE orders ADD COLUMN xyz text;
-- If can't acquire lock in 5s, raises an error instead of waiting

-- Set statement_timeout to kill slow queries
SET statement_timeout = '30min';

-- Per-role settings (in postgresql.conf)
ALTER ROLE myrole SET lock_timeout = '10s';
```

**Operational recommendation:**
```
# postgresql.conf
lock_timeout = 0              # global default: no timeout (0 = wait forever)
                              # set per-statement for DDL
deadlock_timeout = 1s         # how long before deadlock detection runs
```

Don't set a global lock_timeout unless you're sure all your queries can tolerate it. Better to set it per DDL operation.

## Lightweight Locks (LWLocks)

Internal PostgreSQL locks for protecting shared memory data structures. Not visible in `pg_locks`. Visible in `pg_stat_activity.wait_event_type = 'LWLock'`.

Common LWLocks:
- `BufferMapping`: protecting the buffer pool mapping
- `WALInsert`: protecting WAL insert positions
- `lock_manager`: protecting the lock table itself

High LWLock contention = internal bottleneck. Usually means:
- `shared_buffers` too small (lots of BufferMapping contention)
- Extremely high WAL write rate (WALInsert contention)
- Too many connections (lock_manager contention)

```sql
-- Check for LWLock waits
SELECT wait_event, count(*)
FROM pg_stat_activity
WHERE wait_event_type = 'LWLock'
GROUP BY wait_event
ORDER BY count(*) DESC;
```

## Summary: Lock Cheat Sheet

| You are doing | Lock acquired | Blocks |
|---|---|---|
| `SELECT` | Access Share | Only VACUUM FULL, DROP TABLE, TRUNCATE |
| `INSERT/UPDATE/DELETE` | Row Exclusive | CREATE INDEX, ALTER TABLE, VACUUM FULL |
| `SELECT FOR UPDATE` | Row Share | EXCLUSIVE, ACCESS EXCLUSIVE |
| `CREATE INDEX` | Share | All writes |
| `CREATE INDEX CONCURRENTLY` | Share Update Exclusive | Other concurrent operations |
| `VACUUM` | Share Update Exclusive | Other VACUUMs, DDL |
| `ALTER TABLE` (most) | Access Exclusive | EVERYTHING |
| `VACUUM FULL` | Access Exclusive | EVERYTHING |
| `DROP TABLE` | Access Exclusive | EVERYTHING |

**Rule**: Any time you need to do DDL on a production table, set `lock_timeout` and have a retry plan.
