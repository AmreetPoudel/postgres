# 1.5 — WAL: The Backbone of PostgreSQL

**Phase**: 1 — Internals
**Est. reading time**: 25 min

---

## The Problem WAL Solves

Imagine no WAL. Your server crashes halfway through writing a large transaction to disk. Some pages are written. Some are not. Which data do you trust? You don't know. The database is corrupt.

WAL solves this with one rule:

> **Write a record of what you intend to do BEFORE you actually do it. Once the WAL record is safely on disk, the change is permanent — even if the server crashes before the data files are updated.**

---

## How WAL Works, Step by Step

```
Backend running UPDATE orders SET status='shipped' WHERE id=1:

Step 1: Backend writes a WAL record to WAL buffers (in shared memory):
        "At LSN 0/15D3A00: Update page 24601, slot 5, set status='shipped'"

Step 2: Backend writes the new row version into shared_buffers (page is now dirty)

Step 3: On COMMIT:
        WAL writer flushes WAL buffers → pg_wal/000000010000000000000001

Step 4: COMMIT returns success to client.
        At this point, the change is durable. WAL is on disk.
        The data file change (dirty page) may NOT be on disk yet.

Step 5: Eventually, checkpointer flushes the dirty page to the data file.
```

If the server crashes between Step 3 and Step 5: WAL is on disk. On restart, PostgreSQL replays the WAL record and writes the change to the data file. Data is safe.

## LSN — Log Sequence Number

Every byte of WAL has a position called an LSN. It's a 64-bit number written as two hex values separated by a slash:

```
0/15D3A00
│  └── byte offset within the WAL stream
└── high bits
```

LSNs let you:
- Know where you are in the WAL stream
- Measure replication lag (difference between primary LSN and standby's applied LSN)
- Know where to start crash recovery from (the last checkpoint's LSN)

```sql
-- Current WAL position on primary
SELECT pg_current_wal_lsn();

-- Which WAL file contains that position
SELECT pg_walfile_name(pg_current_wal_lsn());

-- How much WAL between two points (in bytes)
SELECT pg_wal_lsn_diff('0/16000000', '0/15D3A00');
```

## WAL Segments

WAL is stored in 16MB files called segments in `pg_wal/`:

```
000000010000000000000001   ← first segment
000000010000000000000002   ← second segment (first one is full)
```

When a segment fills, a new one starts. Old segments are:
- **Recycled** (renamed and reused) if not needed for recovery
- **Archived** (copied to archive location) if archive_mode = on
- **Kept** if a replication slot is holding them (danger — can fill disk)

**WAL segment size**: 16MB by default. Can be changed at `initdb` time:
```bash
initdb --wal-segsize=64 -D $PGDATA    # 64MB segments
```

Larger segments = fewer files = slightly less overhead. Only matters on very high-write systems.

---

## WAL Levels

`wal_level` controls how much information goes into WAL:

```
wal_level = minimal      # Minimum for crash recovery only
wal_level = replica      # Default: includes info needed for streaming replication
wal_level = logical      # Adds info needed for logical replication/decoding
```

**Always use `replica` or higher** on any production system that might have a standby. Setting it to `minimal` after adding a standby will require PostgreSQL restart.

`logical` is needed if you want to use logical replication (Phase 4.4) or tools like Debezium, pglogical.

**Cost of higher wal_level**: Slightly more WAL generated. Not significant enough to justify using `minimal` on a replica setup.

## Crash Recovery — What Happens at Startup

If PostgreSQL was shut down uncleanly (crash, kill -9, power cut):

```
PostgreSQL starts
    ↓
Reads pg_control file → finds last checkpoint LSN
    ↓
Opens WAL at that LSN
    ↓
Startup process replays every WAL record:
    - Committed transactions → apply changes to data files
    - Uncommitted transactions → skip (they're rolled back)
    ↓
Data files are now consistent
    ↓
PostgreSQL opens for connections
```

The time to recover = how much WAL has accumulated since the last checkpoint.

- Checkpoint every 5 minutes, crash happens at 4:55 → replay ~5 minutes of WAL
- Checkpoint every 30 minutes, crash happens at 29:55 → replay ~30 minutes of WAL

This is the tradeoff for `checkpoint_timeout`. Longer timeout = less I/O during normal operation but slower crash recovery.

**Check crash recovery in logs:**
```bash
grep "database system" $PGDATA/log/postgresql-*.log | tail -20
# "database system was shut down at ..." = clean shutdown
# "database system was not properly shut down" = crash, recovery will run
# "redo starts at ..." = recovery starting
# "database system is ready to accept connections" = recovery done
```

## Write Amplification — WAL is Bigger Than Your Data

When you `INSERT` a row, PostgreSQL writes:
1. The WAL record (includes full before/after image depending on `wal_level` and settings)
2. Eventually, the dirty page to disk

The WAL record can be larger than the actual data change because it includes:
- Full page images (FPI) for pages modified after a checkpoint (to protect against partial writes)
- Transaction metadata
- Various bookkeeping info

```sql
-- How much WAL has been generated since startup?
SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0') AS total_wal_bytes;

-- Watch WAL generation rate during a workload:
SELECT pg_current_wal_lsn();
-- run some workload
SELECT pg_current_wal_lsn();
-- difference = WAL generated by that workload
```

**Full Page Images (FPI)**: After a checkpoint, the first modification to any page includes the full 8KB page image in WAL. This protects against partial page writes (if server crashes mid-page-write). This is controlled by:

```
full_page_writes = on    # default, leave it on
```

Turning this off reduces WAL size and improves write performance, but only safe if your storage guarantees atomic 8KB writes (some enterprise storage does). On commodity hardware: leave it on.

## WAL Archiving — The Foundation of PITR

When `archive_mode = on`, PostgreSQL copies completed WAL segments to an archive:

```
postgresql.conf:
archive_mode = on
archive_command = 'cp %p /archive/%f'
# %p = path to WAL segment
# %f = filename
```

Better archive commands (with error handling):
```bash
# Via rsync to another server
archive_command = 'rsync -a %p backup-server:/archive/wal/%f'

# Via pgBackRest
archive_command = 'pgbackrest --stanza=main archive-push %p'

# Via WAL-G to S3
archive_command = 'wal-g wal-push %p'
```

**The archive_command must:**
- Return exit code 0 on success
- Return non-zero on failure (PostgreSQL retries, keeps the segment)
- Not overwrite existing files (PostgreSQL handles this by unique filenames)

**Monitoring archiving:**
```sql
SELECT * FROM pg_stat_archiver;
-- Check: last_archived_time should be recent
-- Check: failed_count should not be growing
```

## archive_cleanup_command — Cleaning Old WAL

On a standby, after WAL is no longer needed for recovery, you want to clean it up:

```
recovery.conf (PG11 and earlier) or postgresql.conf (PG12+):
restore_command = 'cp /archive/wal/%f %p'
archive_cleanup_command = 'pg_archivecleanup /archive/wal %r'
```

`pg_archivecleanup` removes WAL segments older than the standby's current position. Without it, archives grow forever.

## Point-In-Time Recovery (PITR) — Why You Need Archiving

The full power of WAL: restore to any point in time.

Scenario: At 2am, a developer ran `DELETE FROM orders;` without a WHERE clause. At 3am you notice. You want to restore to 1:59am.

```bash
# 1. Stop PostgreSQL
pg_ctl stop -m fast

# 2. Restore the last base backup
rsync -a /backup/base/ $PGDATA/

# 3. Create recovery.conf (PG11-) or edit postgresql.conf (PG12+)
cat >> $PGDATA/postgresql.conf << EOF
restore_command = 'cp /archive/wal/%f %p'
recovery_target_time = '2026-10-06 01:59:00'
recovery_target_action = promote
EOF

# 4. Create standby.signal (PG12+ recovery mode trigger)
touch $PGDATA/recovery.signal

# 5. Start PostgreSQL — it will replay WAL up to 1:59am, then stop
pg_ctl start

# 6. Verify, then promote to read-write
```

PITR requires: base backup + all archived WAL segments from that backup to the target time.

This is why WAL archiving is critical infrastructure, not optional. Covered in depth in Phase 3.

## Replication — WAL Streaming

This is covered in Phase 4, but the mechanism is WAL:

```
PRIMARY                                    STANDBY
Backend commits, WAL written
    ↓
WAL Writer flushes to pg_wal/  ──stream──► WAL Receiver receives WAL
                                               ↓
                                           Startup process applies WAL
                                           to standby data files
```

The standby is always "in recovery mode" — continuously applying WAL from the primary. This is streaming replication in a nutshell.

## WAL and Performance — The Key Knobs

```
# How WAL is synced to disk (leave as default unless you know your storage)
wal_sync_method = fdatasync      # Linux default

# How big the WAL buffer is in shared memory
wal_buffers = -1                 # auto-sized: fine for almost all systems

# Compression of WAL records
wal_compression = off            # turn on to reduce WAL size at cost of CPU
                                 # useful if disk write bandwidth is the bottleneck

# How many WAL segments to pre-create (reduces file creation overhead)
wal_keep_size = 0                # 0 = only keep what's needed
                                 # set to non-zero if standbys fall behind temporarily
```

---

## The Most Important WAL Rules

1. **Never delete files from `pg_wal/` manually.** PostgreSQL manages this.
2. **Never disable `fsync`.** Data corruption, not just data loss.
3. **Archive WAL if you care about PITR.** A base backup alone only gets you to the backup time.
4. **Monitor replication slots.** A stuck slot holds WAL forever, filling disk.
5. **Monitor archiving.** A failing archiver fills `pg_wal/` silently.
