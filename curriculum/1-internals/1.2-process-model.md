# 1.2 — The Process Model: Every Process Has a Job

**Phase**: 1 — Internals
**Prerequisite**: 1.1 read and understood
**Est. reading time**: 20-25 min

---

## Why This Matters Operationally

You will spend a lot of time looking at `ps aux` and `pg_stat_activity`. You need to know every process you see, what it does, what breaks if it misbehaves, and how to tell if it is sick.

Most PostgreSQL performance problems leave fingerprints in the process model. A bgwriter that can't keep up. An autovacuum worker thrashing. A checkpointer running too often. Know the processes = know where to look.

## The Full Process Map

```bash
ps aux --forest | grep postgres | grep -v grep
```

Output:
```
postgres   1001  ...  /usr/lib/postgresql/16/bin/postgres -D /var/lib/postgresql/16/main ...   ← postmaster
postgres   1002  ...  postgres: checkpointer
postgres   1003  ...  postgres: background writer
postgres   1004  ...  postgres: walwriter
postgres   1005  ...  postgres: autovacuum launcher
postgres   1006  ...  postgres: logical replication launcher
postgres   2001  ...  postgres: myapp mydb 10.0.0.5(51234) idle
postgres   2002  ...  postgres: myapp mydb 10.0.0.6(51240) SELECT
postgres   2003  ...  postgres: autovacuum worker
```

There is no `stats collector` line: that process was removed in PostgreSQL 15 (statistics now live in shared memory). On a primary with standbys you'll also see one `walsender` per standby; on a standby, `startup recovering <WAL file>` and `walreceiver streaming <LSN>`. Debian/Ubuntu insert the cluster name, e.g. `postgres: 16/main: checkpointer`.

## The Postmaster

Parent of everything. If it dies, all connections die.

**What it does:**
- Listens on port 5432
- Calls `fork()` for each new client → creates a dedicated backend process
- If *any* backend or worker crashes, terminates every other session, runs crash recovery, and starts over (an ordinary ERROR or FATAL in one session doesn't trigger this)

**Proper shutdown (not kill -9):**
```bash
pg_ctl stop -m smart      # wait for every client to disconnect, then stop (can wait forever)
pg_ctl stop -m fast       # default: roll back open transactions, disconnect clients, checkpoint, stop
pg_ctl stop -m immediate  # abort now, no checkpoint: crash recovery on next start
```

On Debian/Ubuntu `pg_ctl` isn't on your PATH; use `pg_ctlcluster 16 main stop` or `systemctl stop postgresql`.

**Common mistake**: `kill -9 <postmaster_pid>`. The postmaster dies but its backends can keep running for a while, and the next start needs crash recovery.

**The other common mistake**: `kill -9` on a single *backend* to get rid of a stuck query. To the postmaster that's a crash: every session on the server is disconnected and crash recovery runs. Use `pg_cancel_backend()` or `pg_terminate_backend()` instead.

## Backend Processes (One Per Client)

```
Client connects → Postmaster fork() → Backend process born
                  ↑ keeps listening    ↑ owns that session exclusively
```

**Session states** (visible in `pg_stat_activity.state`):

| State | Meaning |
|---|---|
| `active` | Running a query |
| `idle` | Waiting for next query from client |
| `idle in transaction` | Inside BEGIN..COMMIT, between statements |
| `idle in transaction (aborted)` | Error happened, client hasn't issued ROLLBACK |

**`idle in transaction` is dangerous.** The session keeps every lock its transaction took (even a plain SELECT holds a lock that blocks DDL on that table). If it has written anything, or holds a REPEATABLE READ snapshot, it also stops VACUUM from removing dead rows anywhere in the database.

```sql
-- Find idle-in-transaction sessions
SELECT pid, usename, now() - xact_start AS duration, query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY duration DESC;

-- Cancel vs terminate (12345 = a pid from the query above)
SELECT pg_cancel_backend(12345);    -- cancels the *running query*; does nothing useful for an idle session
SELECT pg_terminate_backend(12345); -- ends the session: its transaction rolls back, its locks are released
```

**Auto-kill with a timeout:**
```
# postgresql.conf
idle_in_transaction_session_timeout = 30min
statement_timeout = 0            # 0 = no limit (set per app if needed)
```

## The Checkpointer

**Job**: Flush all dirty pages from shared_buffers to data files on disk.

After a crash, PostgreSQL replays WAL from the last checkpoint. Shorter interval = faster recovery but more I/O. Longer interval = less I/O but slower recovery.

**Two checkpoint triggers (whichever comes first):**
```
checkpoint_timeout = 5min    # time-based
max_wal_size = 1GB           # WAL size-based
```

**Key monitoring query:**
```sql
SELECT
    checkpoints_timed,        -- triggered by timeout (normal)
    checkpoints_req,          -- triggered by WAL size limit (bad if >> timed)
    checkpoint_write_time,    -- ms spent writing pages
    checkpoint_sync_time,     -- ms spent doing fsync
    buffers_checkpoint,       -- pages written by checkpointer
    buffers_clean,            -- pages written by bgwriter
    buffers_backend           -- pages written by backends themselves (watch its share)
FROM pg_stat_bgwriter;
```

**Red flags:**
- `checkpoints_req >> checkpoints_timed` → `max_wal_size` is too small, increase it
- `buffers_backend` is a large share of all writes → bgwriter isn't keeping clean buffers ready, so backends write dirty pages themselves (some backend writes are normal, e.g. during bulk loads)
- Long `sync=` times in the `log_checkpoints` log lines → storage can't absorb the fsyncs. Don't alarm on `checkpoint_write_time`: it's cumulative, and writes are *meant* to be spread across 90% of the interval
- PostgreSQL 16's `pg_stat_io` view breaks reads and writes down by process type when you need more detail

**Smooth I/O across the checkpoint interval:**
```
checkpoint_completion_target = 0.9    # spread writes over 90% of interval
```

**Production starting point:**
```
checkpoint_timeout = 15min
max_wal_size = 4GB
checkpoint_completion_target = 0.9
```

## The Background Writer (bgwriter)

**Job**: Pre-write dirty pages between checkpoints so checkpointer doesn't face a huge burst at checkpoint time.

Also prevents backends from being forced to write dirty pages themselves when shared_buffers is full.

```
bgwriter_delay = 200ms
bgwriter_lru_maxpages = 100
bgwriter_lru_multiplier = 2.0
```

Defaults are fine for most systems. Watch `buffers_backend` in pg_stat_bgwriter — if it's a large share of all buffer writes, bgwriter is losing the race.

---

## The WAL Writer

**Job**: Write WAL from the WAL buffers (in shared memory) to the files in `pg_wal/`, in the background.

Your COMMIT is not done until its WAL is on disk, but it's the committing backend that flushes it, not the WAL writer. When many sessions commit at once, one fsync covers them all (group commit). The WAL writer keeps the WAL buffers from filling up and flushes asynchronous commits.

**Critical parameters:**
```
fsync = on              # NEVER disable in production
                        # off = risk of data corruption on crash, not just lost commits

synchronous_commit = on # COMMIT waits for WAL flush before returning to client
                        # off = a crash can lose up to 3 × wal_writer_delay (600ms) of commits (but no corruption)
wal_writer_delay = 200ms
```

`synchronous_commit = off` is a valid performance trick for non-critical bulk loads. Data files stay consistent — you just lose very recent commits. Much safer than `fsync = off`.

## The Autovacuum Launcher

**Job**: Watch all tables across all databases. Spawn autovacuum workers when tables need cleaning.

```
autovacuum_naptime = 1min        # how often launcher checks
autovacuum_max_workers = 3       # max concurrent vacuum workers
```

**Autovacuum is not optional.** Without it:
1. Dead tuples pile up → table bloat → full scans get slower
2. Statistics go stale → planner picks bad plans → queries 10x slower
3. Transaction ID counter hits 2 billion limit → PostgreSQL stops accepting writes

```sql
-- Which tables need vacuum most?
SELECT relname, n_dead_tup, n_live_tup,
       round(n_dead_tup::numeric / nullif(n_live_tup + n_dead_tup, 0) * 100, 1) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
```

## The WAL Archiver

**Job**: Copy completed WAL segments to an archive location when `archive_mode = on`.

```sql
-- Is archiving healthy?
SELECT archived_count, last_archived_wal,
       failed_count, last_failed_wal, last_failed_time
FROM pg_stat_archiver;
```

If `failed_count` grows and `last_failed_time` is recent → WAL segments pile up in `pg_wal/` → if disk fills → database stops writing. Fix immediately.

## The WAL Receiver (Standbys Only)

On a standby: connects to the primary's WAL sender and writes the streamed WAL into the local `pg_wal/`. The **startup process** replays it into the data files. In `ps` they show up as `postgres: walreceiver streaming <LSN>` and `postgres: startup recovering <WAL file>`.

```sql
-- On primary: see standbys and their lag
SELECT application_name, state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
FROM pg_stat_replication;

-- On standby: receiver status
SELECT * FROM pg_stat_wal_receiver;
```

## Daily Operational Queries

```sql
-- Everything at once: all sessions, states, waits, duration
SELECT pid, usename, backend_type, state,
       wait_event_type, wait_event,
       now() - query_start AS duration,
       left(query, 80) AS query
FROM pg_stat_activity
ORDER BY duration DESC NULLS LAST;

-- Anything blocked on a lock right now?
SELECT pid, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';

-- How full is the connection pool?
SELECT count(*) AS connections,
       (SELECT setting::int FROM pg_settings WHERE name = 'max_connections') AS max_conn
FROM pg_stat_activity;
```

**Common wait events and meanings:**

| wait_event_type / wait_event | What is happening |
|---|---|
| `Lock` / `relation`, `transactionid`, `tuple` | Waiting for a table or row lock — something is blocked |
| `IO` / `WALSync`, `WALWrite` | Waiting for WAL to reach disk — usually a commit waiting |
| `IO` / `DataFileRead` | Waiting for a data page read — slow I/O or cache miss |
| `Client` / `ClientRead` | Idle backend waiting for the client to send the next query |

## The Hardware Trap

You buy a 64GB RAM server, point PostgreSQL at it, and keep defaults:

- `shared_buffers = 128MB` — only 0.2% of RAM used as buffer pool
- `max_connections = 100` — 100 connections max on a powerful server
- `max_wal_size = 1GB` — constant checkpoints, constant I/O
- `autovacuum_max_workers = 3` — only 3 tables cleaned at once

You are driving a sports car in first gear. Phase 2 fixes this.
