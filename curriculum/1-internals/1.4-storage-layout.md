# 1.4 — Storage Layout: Where Your Data Actually Lives

**Phase**: 1 — Internals
**Est. reading time**: 20 min

---

## PGDATA — The Root of Everything

Every PostgreSQL cluster has a data directory (`PGDATA`). This is where everything lives: your data, WAL, config files, everything.

```bash
echo $PGDATA
# or: psql -c "SHOW data_directory;"
# Typical paths:
# Debian/Ubuntu:  /var/lib/postgresql/16/main
# RHEL/Rocky:     /var/lib/pgsql/16/data
```

```
$PGDATA/
├── base/               ← YOUR DATA IS HERE (one dir per database)
├── pg_wal/             ← Write-Ahead Log segments (16MB each)
├── pg_xact/            ← Transaction status (commit/abort records)
├── pg_multixact/       ← Multi-transaction lock info
├── pg_subtrans/        ← Savepoint tracking
├── pg_tblspc/          ← Symlinks to tablespace directories
├── pg_stat_tmp/        ← Temporary stats files
├── pg_logical/         ← Logical replication state
├── global/             ← Cluster-wide tables (pg_database, pg_authid)
├── postgresql.conf     ← Main config
├── pg_hba.conf         ← Client authentication rules
├── pg_ident.conf       ← OS username → PG username mapping
├── postgresql.auto.conf← Written by ALTER SYSTEM commands
├── PG_VERSION          ← Contains just "16"
└── postmaster.pid      ← PID file (exists only when running)
```

**Never delete files from PGDATA manually.** Everything has a purpose.

## The `base/` Directory — Where Tables Live

```bash
ls $PGDATA/base/
# 1      5      13448   16384
```

Each number is a **database OID** (Object Identifier). Every database in the cluster gets its own directory.

```sql
-- Match OIDs to database names
SELECT oid, datname FROM pg_database ORDER BY oid;
```

Inside each database directory:
```bash
ls $PGDATA/base/16384/ | head -20
# 112     ← some system table
# 113     ← another system table
# 24601   ← your 'orders' table
# 24601_fsm  ← free space map for orders
# 24601_vm   ← visibility map for orders
# 24604   ← index on orders
```

**Every table, index, sequence = one file (or more files if > 1GB), named by relfilenode.**

## Finding Your Table's File

```sql
-- Step 1: Get your database OID
SELECT oid FROM pg_database WHERE datname = 'mydb';
-- e.g., 16384

-- Step 2: Get your table's relfilenode
SELECT relname, relfilenode, relpages,
       pg_size_pretty(pg_relation_size(oid)) AS size
FROM pg_class
WHERE relname = 'orders';
-- e.g., relfilenode = 24601

-- Step 3: The file is at:
-- $PGDATA/base/16384/24601
```

```bash
ls -lh $PGDATA/base/16384/24601*
# -rw------- 1 postgres postgres  432M  orders data file
# -rw------- 1 postgres postgres  512K  orders_fsm (free space map)
# -rw------- 1 postgres postgres   24K  orders_vm (visibility map)
```

**If the table is > 1GB:**
```
24601         ← first 1GB
24601.1       ← second 1GB
24601.2       ← third 1GB
```

PostgreSQL automatically creates new segment files. There's nothing you need to do.

## The Three Files Per Table

### Main data file (`24601`)
Contains the actual rows. Divided into 8KB pages.

### Free Space Map (`24601_fsm`)
Tracks which pages in the main file have free space for new rows. When you INSERT, PostgreSQL consults the FSM to find a page with enough room instead of always appending to the end.

This is why you can INSERT into a table that has had lots of DELETEs without the file growing immediately — VACUUM marks dead space in the FSM, and new rows fill it.

### Visibility Map (`24601_vm`)
Tracks which pages contain ONLY live tuples (no dead tuples, nothing older than oldest active transaction).

This is used by:
1. **VACUUM**: Skip pages that are already all-visible (huge performance win)
2. **Index-only scans**: If a page is all-visible, PostgreSQL can return data from the index alone without checking the heap (main file) — much faster

## Inside an 8KB Page

Every page in PostgreSQL is exactly 8192 bytes:

```
┌──────────────────────────────────────────────────┐
│  Page Header (24 bytes)                          │
│  - pd_lsn: LSN of last WAL record touching this  │
│  - pd_checksum: page checksum (if enabled)        │
│  - pd_lower: start of free space                 │
│  - pd_upper: end of free space                   │
│  - pd_special: start of special space (indexes)  │
├──────────────────────────────────────────────────┤
│  Item Pointers (array of (offset, length) pairs) │
│  One entry per row. Points to where row starts.  │
│  Growing DOWN from top.                          │
├──────────────────────────────────────────────────┤
│                                                  │
│  F R E E   S P A C E                            │
│                                                  │
├──────────────────────────────────────────────────┤
│  Row Data (tuples) growing UP from bottom        │
│  ┌──────────────────────────────────────────┐   │
│  │ HeapTupleHeader | actual column data     │   │
│  │ - xmin (creator transaction ID)          │   │
│  │ - xmax (deleter transaction ID, or 0)    │   │
│  │ - ctid (self pointer: page,slot)         │   │
│  │ - infomask (flags: has nulls, is HOT...) │   │
│  └──────────────────────────────────────────┘   │
│  ┌──────────────────────────────────────────┐   │
│  │ Another row...                           │   │
│  └──────────────────────────────────────────┘   │
└──────────────────────────────────────────────────┘
```

**Key fields on every row:**
- `xmin`: Transaction ID that created this row version
- `xmax`: Transaction ID that ended this row (DELETE or UPDATE). 0 = still live.
- `ctid`: Physical location (page number, item slot) — used internally

**Why 8KB?** Matches OS page size. File I/O happens in 8KB chunks. Reading one row → always reads the whole 8KB page containing it. This is why wide rows (with large columns) are more expensive — fewer rows per page.

## TOASTing — What Happens to Large Values

What if a row is bigger than 8KB? Or if a column value is huge (like a 10MB text field)?

PostgreSQL uses **TOAST**: The Oversized-Attribute Storage Technique.

If a column value is too large:
1. It gets compressed (if possible)
2. If still too large, stored in a separate **TOAST table**
3. The main row contains a small pointer to the TOAST table

```sql
-- Find the TOAST table for a relation
SELECT relname, reltoastrelid::regclass AS toast_table
FROM pg_class WHERE relname = 'documents';

-- TOAST storage strategies per column
SELECT attname, attstorage
FROM pg_attribute
WHERE attrelid = 'documents'::regclass AND attnum > 0;
-- p = plain (no TOAST)
-- x = extended (compress then TOAST)
-- e = external (TOAST without compression)
-- m = main (compress, try to keep inline)
```

**Operational implication**: Queries that touch TOASTed columns do extra I/O. If you have a table with large text/json/bytea columns and you're querying them a lot, that's extra reads you might not be accounting for.

## The `pg_wal/` Directory

```bash
ls -lh $PGDATA/pg_wal/
# -rw------- 1 postgres postgres 16M 000000010000000000000001
# -rw------- 1 postgres postgres 16M 000000010000000000000002
# -rw------- 1 postgres postgres 16M 000000010000000000000003
```

Each file is exactly 16MB. The filename is 24 hex characters:

```
000000010000000000000003
│        │               │
│        high 8 chars     low 8 chars (segment number)
│
timeline ID (1 = original, increments after failover/recovery)
```

**Normal operation**: A few WAL segments exist. Old ones get recycled or archived.
**Danger sign**: WAL directory growing without bound → archiving is failing, or replication slot is holding WAL (see Phase 4.3).

```bash
# How much WAL space being used?
du -sh $PGDATA/pg_wal/
```

## Tablespaces — Storing Data on Different Disks

By default everything goes into `$PGDATA/base/`. But you can create tablespaces to put data on different disk volumes:

```sql
-- Create a tablespace on a fast NVMe disk
CREATE TABLESPACE fast_disk LOCATION '/mnt/nvme/pg_data';

-- Put a specific table there
CREATE TABLE hot_data (...) TABLESPACE fast_disk;

-- Or move an existing table
ALTER TABLE orders SET TABLESPACE fast_disk;

-- See tablespaces
SELECT spcname, pg_tablespace_location(oid) AS location FROM pg_tablespace;
```

**When to use:**
- Put indexes on faster NVMe, main data on slower SAS/SATA
- Put pg_wal on a separate disk (important for write-heavy workloads — keeps data writes and WAL writes from competing)
- Separate hot tables from cold tables onto different storage tiers

**Operational note**: Moving pg_wal to a dedicated disk is one of the highest-ROI storage changes on write-heavy systems.

## Checksums — Data Integrity

```bash
# Check if checksums are enabled (do this on your server)
pg_controldata $PGDATA | grep "Data page checksum"
```

If checksums are off (default in many installs), PostgreSQL will not detect if a page is silently corrupted on disk (bit rot, bad disk firmware).

**Enable checksums** when creating a new cluster:
```bash
initdb --data-checksums -D $PGDATA
```

Or convert an existing cluster (requires downtime, PG12+):
```bash
pg_checksums --enable -D $PGDATA    # offline conversion
```

**Should you enable it?** Yes, on production. The performance overhead is ~1-2% CPU. The benefit is catching silent corruption before it spreads.

---

## What Breaks If PGDATA Fills Up

If the disk hosting PGDATA fills up completely:
1. WAL writes fail → PostgreSQL panics → crashes immediately
2. On restart, crash recovery tries to write WAL → fails again
3. Database cannot start until you free space

**Mitigation:**
- Put `pg_wal/` on a separate filesystem (high-priority)
- Put `pg_wal/` on a separate disk from data files
- Monitor disk usage with alerts at 70%, 80%, 90%
- Never let PGDATA disk get above 85% on a busy write system

## Useful Storage Queries

```sql
-- Database sizes
SELECT datname, pg_size_pretty(pg_database_size(datname)) AS size
FROM pg_database ORDER BY pg_database_size(datname) DESC;

-- Table sizes including indexes and TOAST
SELECT relname,
       pg_size_pretty(pg_total_relation_size(oid)) AS total,
       pg_size_pretty(pg_relation_size(oid)) AS table_only,
       pg_size_pretty(pg_total_relation_size(oid) - pg_relation_size(oid)) AS indexes_toast
FROM pg_class
WHERE relkind = 'r' AND relnamespace = 'public'::regnamespace
ORDER BY pg_total_relation_size(oid) DESC
LIMIT 20;

-- Biggest indexes
SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 10;
```
