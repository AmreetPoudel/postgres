## Start Here: The Question Nobody Asks

Everyone learns SQL. Nobody asks: *what actually happens when I type a query?*

That gap — between "I write SQL" and "I understand what the database does with it" — is exactly the gap between a junior who keeps hitting problems they can't explain, and a senior who can diagnose anything.

We're going to close that gap. Permanently.

## Part 1: The Story of a Connection

Let's start with the most basic thing you do every day:

```bash
psql -U amrit -d mydb
```

You hit enter. A prompt appears. Simple, right?

No. This is what actually happened:

### 1.1 — The Postmaster: PostgreSQL's Front Door

When PostgreSQL starts, it launches **one master process** called the **postmaster**. This process does almost nothing all day — it just sits there, listening on port 5432, waiting for connections.

Think of it like the **receptionist at a company**. When you walk in, the receptionist doesn't do your actual work. They pick up the phone, call the right department, and a real person comes to handle you.

```
You (psql client)
     │
     │  "I want to connect to mydb as user amrit"
     │  ──────────────────────────────────────────►  port 5432
                                                      │
                                                 [postmaster]
                                                 "OK, let me get
                                                  someone for you"
```

### 1.2 — fork(): The Receptionist Clones a Worker

The postmaster does something called `fork()`.

`fork()` is a Linux system call that **clones the current process into two identical processes**. The original keeps running (still listening for new connections). The clone becomes **your dedicated backend process**.

```
[postmaster]  ──fork()──►  [backend process]  ←── this is YOUR session
     │                           │
     │                    handles ONLY your connection
     │                    parses YOUR queries
     │                    runs YOUR transactions
     │
     └── keeps listening for the next connection
```

This is the key insight: **every single client connection = one OS process**.

Not a thread. Not a fiber. A full OS process.

Right now on your server:
```bash
ps aux | grep postgres
```

You'll see something like this (Debian/Ubuntu add the `16/main:` cluster name; RHEL shows just `postgres: checkpointer`):
```
postgres  1234  ...  /usr/lib/postgresql/16/bin/postgres -D /var/lib/postgresql/16/main ...   ← the postmaster
postgres  1241  ...  postgres: 16/main: checkpointer
postgres  1242  ...  postgres: 16/main: background writer
postgres  1243  ...  postgres: 16/main: walwriter
postgres  1244  ...  postgres: 16/main: autovacuum launcher
postgres  1245  ...  postgres: 16/main: logical replication launcher
postgres  1890  ...  postgres: 16/main: amrit mydb [local] idle    ← THIS IS YOU
```

That last line — that's your backend process. Your session. If your query hits an error, only your session sees it. But be careful with the word "isolation": if that process *crashes* (a segfault, or the OOM killer's `kill -9`), the postmaster can no longer trust shared memory. It terminates every other session, runs crash recovery, and reopens, usually within seconds. One crashed backend means a short outage for everyone, not just you.

### 1.3 — Why Processes, Not Threads?

You might be thinking: "Isn't this wasteful? Modern software uses threads."

Fair question. Here's the honest answer from a production DBA perspective:

**Threads are fast but they share everything. Processes are slower to start, but each one's private memory is its own.**

Here's what that buys you, and what it doesn't. A bug that scribbles over one backend's private memory can't silently corrupt another session's private memory. And when a backend dies, the postmaster survives to clean up. What the postmaster does *not* do is let everyone else carry on: shared memory might be damaged, so it resets the whole server.

```
LOG:  server process (PID 1890) was terminated by signal 9: Killed
LOG:  terminating any other active server processes
LOG:  all server processes terminated; reinitializing
LOG:  database system was not properly shut down; automatic recovery in progress
```

That reset is fast and fully automatic, and that's the real win: in a single multi-threaded server, the same crash would take the whole server down until something outside restarted it. The rest of the honest answer is history: when the process model was designed, portable threading on Unix wasn't something you could rely on.

The tradeoff: process startup is slower, and each process uses more RAM.
- Each backend process: ~5–10MB base RAM
- 200 connections × 10MB = 2GB just for processes, before any query runs

**This is why PgBouncer exists.** We'll get there in Phase 2. For now, just remember: connection count in PostgreSQL is expensive in a way it isn't in other systems.

## Part 2: Shared Memory — The Common Workspace

Here's a problem: you have 200 backend processes, all handling different queries, all potentially touching the same tables. How do they coordinate?

They can't each have their own copy of the data — that's both slow (read from disk every time) and dangerous (who has the "real" version?).

The answer: **shared memory**.

When the postmaster starts, it allocates a big chunk of RAM that **all processes can see simultaneously**. The biggest piece of it is the buffer pool, sized by `shared_buffers` in PostgreSQL config.

```
RAM
┌──────────────────────────────────────────────┐
│              SHARED MEMORY                    │
│                                              │
│  ┌─────────────────────────────────┐        │
│  │  shared_buffers (e.g., 4GB)     │        │
│  │  ← cached copies of disk pages  │        │
│  │  ← all backends read/write here │        │
│  └─────────────────────────────────┘        │
│                                              │
│  ┌──────────────┐  ┌──────────────┐         │
│  │  WAL buffers │  │  Lock table  │         │
│  │  (pre-flush) │  │  (who holds  │         │
│  │              │  │   what lock) │         │
│  └──────────────┘  └──────────────┘         │
│                                              │
│  ┌──────────────────────────────────┐        │
│  │  Proc array (one slot per        │        │
│  │  backend — for MVCC visibility)  │        │
│  └──────────────────────────────────┘        │
└──────────────────────────────────────────────┘
         ▲          ▲          ▲
    backend 1   backend 2   backend 3
```

### What lives in shared_buffers?

PostgreSQL reads data from disk in **8KB pages** (also called blocks). When a page is needed, it's loaded into `shared_buffers`. The next query that needs the same page finds it already in memory — much faster.

This is PostgreSQL's **buffer pool**. The whole game of performance tuning around `shared_buffers` is: how much of your working data can you keep in memory so you never have to go to disk?

**A critical production insight**: PostgreSQL competes with the OS page cache for RAM. The OS also caches disk reads. This is why we typically set `shared_buffers` to 25% of RAM and no more — because the OS cache handles the rest. Setting it too high starves other processes. We'll tune this in Phase 2.

## Part 3: The Background Workers — Each One Has a Job

When you run `ps aux | grep postgres`, you see processes that aren't your session. These are **background workers**. Each one runs forever, doing a specific job. Here's what they do:

### The WAL Writer
Writes WAL from the in-memory WAL buffers out to `pg_wal/` in the background, so backends rarely have to do that work themselves. One thing it does *not* do is make your COMMIT durable. With the default `synchronous_commit = on`, the committing backend flushes its own WAL and waits for the fsync; when many sessions commit at once, one flush covers all of them (group commit). The WAL writer's own flushing matters most for asynchronous commits (`synchronous_commit = off`).

### The Checkpointer
Periodically writes all dirty pages from `shared_buffers` to the actual data files on disk. This is called a **checkpoint**. Between checkpoints, a change is only guaranteed to be on disk in WAL; the data-file copy may or may not have been written yet. After a crash, PostgreSQL uses WAL to replay changes since the last checkpoint.

### The Background Writer (bgwriter)
Gradually writes dirty pages to disk **between checkpoints** so the checkpointer doesn't have to do a huge burst of disk writes all at once. Think of it as pre-washing dishes so the final cleanup is faster.

### The Autovacuum Launcher
Watches tables for "bloat" (dead row versions from UPDATE/DELETE). When a table needs cleaning, it spawns an **autovacuum worker** to do it. We'll spend an entire session on this because it's a major operational concern.

### Cumulative Statistics (no separate process since PostgreSQL 15)
Older guides describe a *stats collector* process. PostgreSQL 15 removed it. Each backend now accumulates its own counters (rows read and written, index usage, vacuum activity) and flushes them into shared memory, where the `pg_stat_*` views read them; they're saved to disk at a clean shutdown. You won't find this in `ps`, but those views are still your primary tool for understanding what the database is actually doing.

### The Logical Replication Launcher
You'll see this in `ps` even if you never use logical replication. It starts apply workers for subscriptions (Phase 4.4) and otherwise sleeps.

### The WAL Archiver
If WAL archiving is enabled, copies completed WAL segments to an archive location. This is the foundation of Point-In-Time Recovery. Standbys can also fetch WAL from the archive, but streaming replication doesn't require it.

### The WAL Receiver (standby only)
If this is a replica, the WAL receiver connects to the primary's **WAL sender** and writes the streamed WAL into the standby's `pg_wal/`. It doesn't apply anything. Replay is the job of the **startup process**, which runs continuously on a standby (it's the same process that performs crash recovery). This is streaming replication.

## Part 4: Where Data Actually Lives on Disk

This is the one most people get completely wrong.

Your `PGDATA` directory (usually `/var/lib/postgresql/16/main` on Debian/Ubuntu) is everything PostgreSQL owns. Let's walk through what matters:

```
$PGDATA/
├── base/                ← WHERE ALL YOUR DATA IS
│   ├── 1/               ← database with OID 1 (template1)
│   ├── 4/               ← template0 (OIDs 4 and 5 are fixed since PG15)
│   ├── 5/               ← postgres
│   └── 16384/           ← database with OID 16384 (mydb ← YOUR DB)
│       ├── 2619          ← table: pg_statistic  (filename = relfilenode)
│       ├── 2619_fsm      ← free space map for pg_statistic
│       ├── 2619_vm       ← visibility map for pg_statistic
│       ├── 1259          ← table: pg_class
│       └── ...           ← one file per table/index
│
├── pg_wal/              ← Write-Ahead Log segments
│   ├── 000000010000000000000001   ← 16MB WAL segment
│   ├── 000000010000000000000002
│   └── ...
│
├── pg_xact/             ← transaction status (did this txn commit or abort?)
├── pg_multixact/        ← for rows locked by multiple transactions
├── pg_subtrans/         ← savepoint tracking
├── pg_tblspc/           ← symlinks to custom tablespace directories
│
├── postgresql.conf      ← ALL tunable parameters
├── pg_hba.conf          ← who can connect, from where, how
├── pg_ident.conf        ← OS user → PG user mapping
├── PG_VERSION           ← just contains "16"
└── postmaster.pid       ← PID of running postmaster (gone when stopped)
```

On Debian/Ubuntu the three `.conf` files live in `/etc/postgresql/16/main/` instead. `SHOW config_file;` tells you where yours are.

### OIDs — The Internal IDs

Everything in PostgreSQL has an OID (Object Identifier): databases, tables, indexes, functions, types — everything. Data files are named by **relfilenode**, a separate number that starts out equal to the table's OID but changes whenever the table is rewritten (TRUNCATE, VACUUM FULL, CLUSTER, some ALTER TABLEs).

To find your table's file:
```sql
-- Find the OID of your database
SELECT oid, datname FROM pg_database WHERE datname = 'mydb';

-- Find the OID of your table
SELECT relfilenode, relname FROM pg_class WHERE relname = 'orders';

-- The file is at:
-- $PGDATA/base/<db_oid>/<relfilenode>

-- Or let PostgreSQL do the lookup:
SELECT pg_relation_filepath('orders');   -- e.g. base/16384/24601
```

### What's inside a data file?

Each table file is divided into **8KB pages**. Every page looks like this:

```
┌─────────────────────────────────────────┐
│  Page Header (24 bytes)                 │
│  (LSN, checksum, free space info)       │
├─────────────────────────────────────────┤
│  Item Pointers (array of offsets)       │
│  ← tells you where each row starts     │
├─────────────────────────────────────────┤
│                                         │
│  Free Space                             │
│                                         │
├─────────────────────────────────────────┤
│  Row data (tuples), stored from bottom  │
│  ┌─────────────────────────────────┐   │
│  │ xmin | xmax | data...           │   │  ← one row (tuple)
│  └─────────────────────────────────┘   │
│  ┌─────────────────────────────────┐   │
│  │ xmin | xmax | data...           │   │  ← another row
│  └─────────────────────────────────┘   │
└─────────────────────────────────────────┘
```

`xmin` = the transaction ID that created this row version  
`xmax` = the transaction ID that deleted/updated this row (0 if still live)

This is the physical implementation of MVCC. Every row version on disk carries the transaction IDs that created and ended it.

## Part 5: WAL — The Single Most Important Concept

This is where everything clicks.

### The Problem WAL Solves

Imagine PostgreSQL writes data directly to the data files, and your server crashes halfway through writing a large transaction. The data files are now corrupted — half a transaction is written, half isn't. How do you know which data to trust?

You don't. The database is broken.

### The Solution: Write Intent Before Writing Data

WAL solves this with a simple rule:

> **A changed page may not be written to its data file until the WAL record describing that change is safely on disk. And a COMMIT isn't acknowledged until its WAL is on disk.**

WAL is a **sequential log** of every change ever made to the database, written in order, never modified. If the server crashes:

1. PostgreSQL restarts
2. It reads WAL from the last checkpoint forward
3. It replays every WAL record, committed or not. There's no undo step: transactions that never committed are simply recorded as aborted, and MVCC hides their row versions
4. The database is consistent again

This is why deleting `pg_wal/` while running doesn't just lose "a few commits" — **it makes crash recovery impossible**. The data files might be in an inconsistent state from the last checkpoint, and without WAL, there's no way to bring them to a consistent state.

### WAL is also how replication works

On a standby server, the WAL receiver process connects to the primary and receives WAL records in real time, and the startup process replays them into the standby's data files. The standby is always "replaying" the primary's WAL.

```
PRIMARY                                 STANDBY
────────                                ───────
client commits txn
    │
    ▼
commit's WAL flushed to pg_wal/
    │
    ▼
WAL sender ── streams WAL ──────────►   WAL receiver writes it to pg_wal/
    │                                        │
    ▼                                        ▼
Checkpointer eventually                 Startup process replays it
writes data files                       into the standby's data files
```

**One WAL, three uses**: crash recovery, point-in-time recovery, and replication. 

### WAL Segments

WAL is stored in 16MB files called **segments** in `pg_wal/`. The 24-character filename encodes position (shown here split into its three 8-character fields):

```
00000001 00000000 00000001
│        │        │
│        │        └── segment number, low 32 bits (hex)
│        └── segment number, high 32 bits
└── timeline ID (1 = original; increments after each promotion or PITR)
```

When a segment fills up, a new one starts. After a checkpoint, segments that are no longer needed are recycled (renamed for reuse) or removed, but never before they've been archived (if archiving is on) and never while a replication slot still needs them.

## Part 6: MVCC — Why PostgreSQL Never Blocks Reads

You already knew that PostgreSQL keeps old row versions. Now you know *why*.

### The Problem Without MVCC

```
Time ──►

T1: UPDATE orders SET status='shipped' WHERE id=1;
    (locks row, holds lock until commit)
    
T2: SELECT * FROM orders WHERE id=1;
    ← BLOCKED. Must wait. Even though it's a READ.
```

In a system with lots of concurrent reads and writes, this is a disaster for performance.

### MVCC: Multiple Versions of the Same Row

```
Time ──►

T1 starts (txid=100): UPDATE orders SET status='shipped' WHERE id=1;
    Creates new row version with xmin=100
    Marks old row version with xmax=100
    
T2 starts (txid=101): SELECT * FROM orders WHERE id=1;
    Sees its snapshot: "I started at txid=101, T1 not yet committed"
    Reads old row version (xmax=100, T1 not committed = invisible)
    ← NOT BLOCKED. Returns immediately.

T1 commits.

T3 starts (txid=102): SELECT * FROM orders WHERE id=1;
    Sees T1 committed. Reads new row version.
    Returns status='shipped'.
```

Each query sees a **snapshot** of the database. In the default READ COMMITTED level every statement takes a fresh snapshot; in REPEATABLE READ and SERIALIZABLE one snapshot, taken at the transaction's first statement, is used for the whole transaction. New row versions are written for updates; old versions stay around until VACUUM cleans them.

### The Dead Weight: Why VACUUM is Not Optional

Every UPDATE creates a dead row version. Every DELETE leaves a dead row. These **dead tuples** accumulate. The table file grows even if you're deleting data. This is called **bloat**.

VACUUM's job: scan the table, find dead tuples that no active transaction can see anymore, mark their space as reusable.

If autovacuum is disabled or too slow, tables bloat, indexes bloat, queries slow down, and eventually you hit **transaction ID wraparound** protection: PostgreSQL stops accepting write transactions until VACUUM has frozen old rows. We'll cover this in depth in 1.7.

## Part 7: What Actually Happens to Your Query

Now let's revisit your answer to Q4. Here's the full journey of:

```sql
SELECT * FROM orders WHERE customer_id = 42;
```

### Step 1: Parser
The query string is tokenized and parsed into an **abstract syntax tree (AST)**. Pure syntax check — it knows nothing about whether `orders` exists.

```
SELECT ──► [SelectStmt]
              ├── targetList: [*]
              ├── fromClause: [orders]
              └── whereClause: [customer_id = 42]
```

### Step 2: Analyzer / Rewriter
Resolves names to actual database objects. Checks `orders` exists, checks `customer_id` exists in it, expands `*` to the actual column list, and notes which permissions the query needs (they're checked when execution starts). Views get rewritten as subqueries here.

### Step 3: Planner / Optimizer
This is where the magic and the danger is. The planner:
1. Looks at statistics (row counts, value distributions in `pg_statistic`)
2. Considers possible plans: sequential scan? index scan? index only scan? bitmap scan?
3. Estimates cost for each plan
4. Picks the cheapest one

If you have `CREATE INDEX ON orders(customer_id)`, the planner will use it — IF it estimates that's cheaper than a seq scan. If the statistics are stale (no ANALYZE recently), the planner makes bad estimates and picks wrong plans.

**This is the #1 cause of "my query used to be fast and now it's slow."**

### Step 4: Executor
Runs the plan. Reads 8KB pages from shared_buffers (or disk if not cached). Applies filters. For joins, builds hash tables or drives nested loops. Sorts if needed.

### Step 5: Results Sent Back
Rows are formatted according to PostgreSQL's wire protocol and sent back to the client incrementally (PostgreSQL is a streaming system — it doesn't need to collect ALL results before sending the first row).

## Summary: The Mental Model You Need

```
CLIENT (psql)
    │ connects to port 5432
    ▼
POSTMASTER
    │ fork() ── creates YOUR backend process
    ▼
YOUR BACKEND PROCESS
    │ shares access to...
    ├──► SHARED BUFFERS (data page cache)
    ├──► WAL BUFFERS (writes go here before disk)
    ├──► LOCK TABLE (who holds what lock)
    └──► PROC ARRAY (for MVCC snapshot computation)
    
    │ reads/writes...
    ├──► $PGDATA/base/<dboid>/<relfilenode>  (data files, 8KB pages)
    └──► $PGDATA/pg_wal/  (WAL segments, sequential write)
    
BACKGROUND WORKERS running in parallel:
    ├── WAL Writer      → writes WAL buffers to pg_wal/ in the background
    ├── Checkpointer    → flushes dirty pages to data files
    ├── bgwriter        → cleans dirty buffers ahead of demand
    ├── Autovacuum      → cleans dead tuples, updates statistics
    └── Logical replication launcher → starts subscription workers
    (pg_stat_* counters live in shared memory: no stats collector since PG15)
```

## Part 8: The Three Ways PostgreSQL Dies (And How to See It Coming)

This is the most practical framing a DBA can have. Every PostgreSQL performance crisis — without exception — traces back to one of these three resources being exhausted:

### 1. DISK — The most common killer

PostgreSQL is fundamentally a disk database. Everything eventually goes to disk. When disk is the bottleneck:

**Symptoms:**
- High `await` in `iostat` (disk queue building up)
- WAL flushes (fsync) get slow → every commit waits longer → clients pile up
- Checkpoints happen too often → "checkpoints are occurring too frequently" warnings in the log (the threshold is `checkpoint_warning`)
- Autovacuum falling behind → bloat accumulates → queries slow down

**What to watch:**
```bash
iostat -x 1          # look at: await, %util, w_await
iotop -o             # which process is hammering disk?
```
```sql
-- Is the checkpoint too frequent? (means WAL is filling up faster than checkpoints run)
SELECT * FROM pg_stat_bgwriter;
-- If checkpoints_req >> checkpoints_timed: your max_wal_size is too small
-- (PostgreSQL 17 moved these columns to pg_stat_checkpointer; on 16 they're here)

-- Is WAL archiving falling behind?
SELECT * FROM pg_stat_archiver;
```

**Root causes**: Not enough IOPS (cheap HDD vs NVMe), too many small random writes, checkpoint config wrong, autovacuum writing too much.

---

### 2. MEMORY — The second killer

PostgreSQL needs RAM for three things:
- `shared_buffers` — the buffer pool (keep hot data in memory, avoid disk reads)
- `work_mem` — per-sort, per-hash-join allocation (multiplied by all concurrent operations)
- OS page cache — PostgreSQL relies on this for the data `shared_buffers` doesn't hold

When memory is the bottleneck:

**Symptoms:**
- High swap usage → everything slows down (swap is disk-speed memory)
- OOM killer terminates PostgreSQL processes → sudden disconnections
- Queries doing disk sorts when they shouldn't (`Sort Method: external merge Disk`)
- Buffer hit rate dropping (data evicted from shared_buffers too fast)

**What to watch:**
```bash
free -h              # how much swap is in use?
vmstat 1             # si/so columns = swap in/out (nonzero = disaster)
```
```sql
-- Buffer hit rate — should be >99% for a well-tuned DB
SELECT 
    round(blks_hit * 100.0 / nullif(blks_hit + blks_read, 0), 2) AS hit_rate_pct
FROM pg_stat_database 
WHERE datname = current_database();

-- Are queries spilling to disk?
EXPLAIN (ANALYZE, BUFFERS) <your query>;
-- Look for: "Sort Method: external merge Disk" or "Batches: N" in Hash Join
```

**Root causes**: `shared_buffers` too small for working set, `work_mem` set too high (everyone × parallel ops × sorts × hash joins), server RAM just insufficient.

---

### 3. CPU — The sneaky killer

CPU is often the last bottleneck because PostgreSQL is usually I/O bound. But it becomes a problem when:

- Query planning is slow (too many join permutations, bad statistics)
- Sequential scans on huge tables (CPU doing row filtering with no index)
- Too many connections → too much process context switching
- Autovacuum running too aggressively on CPU

**What to watch:**
```bash
top                  # which postgres PID is eating CPU?
perf top             # what is that PID actually doing? (requires perf tools)
```
```sql
-- PostgreSQL doesn't count CPU per backend. Find the hot PID with top
-- (or pidstat -u 1), then ask PostgreSQL what that backend is doing:
SELECT pid, usename, state, now() - query_start AS running_for, query
FROM pg_stat_activity
WHERE pid = 12345;   -- the PID from top

-- Over time, pg_stat_statements (must be in shared_preload_libraries) shows
-- which queries use the most time. With track_io_timing = on, time not spent
-- on block I/O is mostly CPU (lock waits and sleeps count here too):
SELECT left(query, 60) AS query, calls,
       round(total_exec_time::numeric) AS total_ms,
       round((total_exec_time - blk_read_time - blk_write_time)::numeric) AS non_io_ms
FROM pg_stat_statements
ORDER BY non_io_ms DESC
LIMIT 10;
```

**Root causes**: Missing indexes (full seq scans), plan regressions from stale stats, too many connections causing context-switch overhead, autovacuum not throttled.
