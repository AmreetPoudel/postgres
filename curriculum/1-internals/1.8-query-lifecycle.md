# 1.8 — Query Lifecycle: From SQL String to Rows

**Phase**: 1 — Internals
**Est. reading time**: 20 min

---

## The Journey of a Query

When you send a query to PostgreSQL, it goes through 5 stages:

```
SQL text
  ↓ Parser
Abstract Syntax Tree (AST)
  ↓ Analyzer / Rewriter
Semantic Query Tree
  ↓ Planner / Optimizer
Execution Plan
  ↓ Executor
Result rows
  ↓ Wire protocol
Client
```

Each stage has its own job, its own failure modes, and its own tuning knobs.

---

## Stage 1: Parser

**What it does**: Tokenizes the SQL string and checks that it's valid SQL syntax.

```
"SELECT * FROM orders WHERE id = 42"
          ↓
[SELECT] [*] [FROM] [orders] [WHERE] [id] [=] [42]
          ↓
SelectStmt {
  targetList: [A_Star]
  fromClause: [RangeVar "orders"]
  whereClause: [A_Expr "=" [ColumnRef "id"] [Integer 42]]
}
```

At this stage:
- PostgreSQL does NOT check if `orders` exists
- Does NOT check if `id` is a real column
- Does NOT check your permissions
- Only checks syntax

**What breaks here**: Syntax errors. `SELECT * FORM orders` → syntax error.

---

## Stage 2: Analyzer / Rewriter

**What it does**: Resolves names to actual database objects.

- Looks up `orders` in `pg_class` — does it exist? What's its OID?
- Looks up `id` in `pg_attribute` — does it exist in `orders`? What type is it?
- Expands `*` into the actual list of columns
- Checks permissions: does your role have `SELECT` on `orders`?
- Rewrites views: if `orders` is a view, substitutes the view definition

**What breaks here**: Table doesn't exist, column not found, permission denied.

**Rewriter**: If you `SELECT * FROM my_view` and `my_view` is `CREATE VIEW my_view AS SELECT * FROM orders WHERE status='pending'`, the rewriter substitutes the view body. The planner then sees the underlying query.

---

## Stage 3: Planner / Optimizer

This is where the magic and the danger lives.

**What it does**: Given multiple ways to execute the query, figure out the cheapest one.

For `SELECT * FROM orders WHERE customer_id = 42`:

Possible plans:
1. Sequential scan: read every row, check if customer_id = 42
2. Index scan on customer_id: find matching rows via index, fetch them
3. Bitmap index scan: use index to build a bitmap, then fetch pages

**How does the planner choose?**

It estimates the **cost** of each plan using:
1. **Table statistics** (from `pg_statistic`) — how many rows, value distributions
2. **Cost constants** — how expensive is a random I/O vs sequential I/O
3. **Row estimates** — how many rows will this filter return?

If `customer_id = 42` matches 100 out of 1,000,000 rows → index scan wins.
If `customer_id = 42` matches 900,000 out of 1,000,000 rows → seq scan wins.

**The planner is only as good as its statistics.** If ANALYZE hasn't run recently, row estimates are wrong → plan is wrong.

```sql
-- See the plan WITHOUT running the query
EXPLAIN SELECT * FROM orders WHERE customer_id = 42;

-- See the plan AND run it (shows actual vs estimated row counts)
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE customer_id = 42;
```

**Reading EXPLAIN output:**
```
Index Scan using orders_customer_id_idx on orders  (cost=0.43..8.45 rows=1 width=64)
  Index Cond: (customer_id = 42)
  Buffers: shared hit=3 read=1
```

- `cost=0.43..8.45`: startup cost .. total cost (in arbitrary units, lower = better)
- `rows=1`: planner estimates 1 row
- `width=64`: estimated average row width in bytes
- `shared hit=3`: 3 pages found in shared_buffers
- `read=1`: 1 page had to be read from disk

**Red flags in EXPLAIN ANALYZE:**
```
Seq Scan on orders  (cost=0.00..150000.00 rows=1000 width=64)
                                            ↑ estimated
    (actual time=0.5..12000ms rows=1000000) ← actual
```

The planner estimated 1,000 rows but got 1,000,000. Bad statistics. The seq scan was actually the right choice for 1M rows, but if it had estimated correctly it might have picked a better plan for a smaller result.

## Key Planner Parameters

```
# Tell the planner the relative cost of random vs sequential I/O
random_page_cost = 4.0      # default: 4x more expensive than seq
seq_page_cost = 1.0

# On NVMe SSDs, random I/O is much cheaper:
random_page_cost = 1.1      # good for NVMe

# On HDDs, sequential is very cheap compared to random:
random_page_cost = 4.0      # keeps the default

# How much of the table fits in RAM (planner hint)
effective_cache_size = 24GB   # see 1.3
```

**This is one of the most impactful config changes you can make on SSD systems:**
```
random_page_cost = 1.1
```

It tells the planner: "Random I/O is almost as cheap as sequential." The planner will use indexes much more aggressively instead of defaulting to seq scans.

---

## Stage 4: Executor

**What it does**: Runs the chosen plan. Reads pages, applies filters, builds hash tables for joins, sorts rows.

**Key executor operations:**

**Sequential Scan**: Read every page of the table. Each page is loaded from shared_buffers (or disk if cache miss). Apply filter row by row. Return matches.

**Index Scan**: Follow the B-tree index to find matching TID (tuple identifier = page + slot). Fetch that row from the heap. Return it. Good for small result sets.

**Bitmap Heap Scan**: Use index to build a bitmap of which pages contain matching rows. Then read those pages in order (more sequential → better than index scan for medium-sized result sets).

**Hash Join**:
1. Read the smaller table, build a hash table in `work_mem`
2. Stream the larger table, probe the hash table for matches
3. If the hash table doesn't fit in `work_mem` → spill to disk (temp files)

**Merge Join**: Sort both tables on the join key, then merge them. Good for already-sorted data.

**Nested Loop**: For each row in outer table, scan inner table for matches. Good for tiny inner tables or when inner side is an index lookup.

## Reading EXPLAIN ANALYZE in Detail

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT o.*, c.email
FROM orders o
JOIN customers c ON o.customer_id = c.id
WHERE o.status = 'pending'
ORDER BY o.created_at DESC
LIMIT 100;
```

Sample output (simplified):
```
Limit  (cost=... rows=100) (actual time=15..15 rows=100 loops=1)
  -> Sort  (cost=... rows=5000) (actual time=14..14 rows=100 loops=1)
       Sort Key: o.created_at DESC
       Sort Method: top-N heapsort  Memory: 35kB
       -> Hash Join  (cost=...) (actual time=8..13 rows=5000 loops=1)
             Hash Cond: (o.customer_id = c.id)
             Buffers: shared hit=450 read=12
             -> Seq Scan on orders o  (cost=...) (actual time=0.05..6 rows=5000 loops=1)
                   Filter: (status = 'pending')
                   Rows Removed by Filter: 995000
             -> Hash  (cost=...) (actual time=5..5 rows=10000 loops=1)
                   Buckets: 16384  Batches: 1  Memory Usage: 800kB
                   -> Seq Scan on customers c  (cost=...) (actual time=0.02..3 rows=10000 loops=1)
```

Key things to note:
- **Rows Removed by Filter: 995000** → seq scan read 1M rows, kept 5000 → missing index on `status`
- **Batches: 1** → hash table fit in memory (good)
- **Sort Method: top-N heapsort Memory: 35kB** → sort fit in memory with LIMIT optimization
- **Buffers: shared hit=450 read=12** → mostly cache hits (good)

## Common Bad Plans and Fixes

**1. Seq scan instead of index scan**
- Add an index on the filtered column
- Or run `ANALYZE` (statistics were stale)
- Or set `random_page_cost = 1.1` if on SSD (planner undervalued index)

```sql
-- Create missing index
CREATE INDEX CONCURRENTLY ON orders(status) WHERE status = 'pending';
-- Partial index: only indexes pending rows (smaller, faster)
```

**2. Nested loop with huge loop count**
- Planner underestimated rows on outer side
- Run `ANALYZE` to fix statistics
- Or use `SET enable_nestloop = off` temporarily to force different plan (debug only)

**3. Hash join spilling to disk (Batches > 1)**
- `work_mem` too low for this query
- Increase `work_mem` for the session: `SET work_mem = '256MB';`

**4. Sort to disk (Sort Method: external merge Disk)**
- `work_mem` too low
- Same fix: increase `work_mem` for the session

## Stage 5: Wire Protocol

PostgreSQL uses its own binary wire protocol (called "Frontend/Backend Protocol"). It streams rows to the client as they're produced — doesn't collect all results before sending.

This is why `LIMIT 10` on a huge table is fast even without an index — the executor stops after 10 rows.

**Prepared statements**: Saves the parsed + analyzed + planned query. On re-execution, skips stages 1-3. Use when running the same query shape many times.

```sql
PREPARE get_orders(int) AS
  SELECT * FROM orders WHERE customer_id = $1;

EXECUTE get_orders(42);
EXECUTE get_orders(99);
```

ORM frameworks do this automatically (protocol-level prepared statements).

## pg_stat_statements — Finding Slow Queries

The single most useful extension for query performance analysis:

```sql
-- Enable in postgresql.conf:
shared_preload_libraries = 'pg_stat_statements'
-- Restart required, then:
CREATE EXTENSION pg_stat_statements;

-- Find your worst queries by total time
SELECT
    round(total_exec_time::numeric, 2) AS total_ms,
    calls,
    round(mean_exec_time::numeric, 2) AS avg_ms,
    round(stddev_exec_time::numeric, 2) AS stddev_ms,
    rows,
    left(query, 80) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

-- Reset stats (do this before a test)
SELECT pg_stat_statements_reset();
```

**Workflow**: Look at `total_exec_time` (total time spent in this query across all calls). The query with the highest total time is your biggest opportunity, even if individual calls are fast.

## The Planner: When It Fails and How to Debug

**Scenario**: Your query suddenly takes 30 seconds when it used to take 10ms.

**Step 1: Get the plan**
```sql
EXPLAIN (ANALYZE, BUFFERS) <your query>;
```

**Step 2: Look for row estimate mismatch**
- `rows=1` estimate vs `rows=500000` actual → stale statistics

**Step 3: Fix statistics**
```sql
ANALYZE your_table;
```

**Step 4: Re-run EXPLAIN. Plan changed?**
- If yes: statistics were the problem
- If no: look at the plan more carefully

**Step 5: Check for missing indexes**
- Seq scan on a large table with a small result set → add index

**Step 6: Confirm with `pg_stat_statements`**
- Is this query in the top 10 by `total_exec_time`?
