# 1.3 — Memory: Where Everything Happens

**Phase**: 1 — Internals
**Est. reading time**: 20 min

---

## The Big Picture

PostgreSQL uses two kinds of memory:

```
RAM
├── SHARED MEMORY (allocated once at startup, shared by all)
│   ├── shared_buffers        ← data page cache
│   ├── WAL buffers           ← WAL before disk flush
│   ├── Lock table            ← who holds what lock
│   └── Proc array            ← MVCC visibility tracking
│
└── PRIVATE MEMORY (per backend, allocated on demand)
    ├── work_mem              ← per sort/hash operation
    ├── maintenance_work_mem  ← for VACUUM, CREATE INDEX, etc.
    └── Query execution state ← parse trees, plans, cursors
```

Shared memory is fixed. Private memory grows dynamically. The danger is in private memory — it multiplies.

---

## shared_buffers — The Data Cache

**What it is**: PostgreSQL's buffer pool. Every 8KB data page that gets read from disk goes into shared_buffers first. If it's already there when requested → cache hit (fast). If not → cache miss → read from disk (slow).

**How to size it:**

```
shared_buffers = 25% of total RAM
```

Why 25% and not 80%? Because the OS also has a page cache. When PostgreSQL reads from disk, it goes through the OS page cache first, then into shared_buffers. You're double-caching. Setting shared_buffers too high starves the OS cache — which PostgreSQL also relies on.

**On a 32GB machine:**
```
shared_buffers = 8GB       # good
shared_buffers = 24GB      # too high — OS cache starved
shared_buffers = 512MB     # way too low — constant disk reads
```

**Check current hit rate:**
```sql
SELECT
    datname,
    blks_hit,
    blks_read,
    round(blks_hit::numeric / nullif(blks_hit + blks_read, 0) * 100, 2) AS hit_rate_pct
FROM pg_stat_database
WHERE datname = current_database();
```

Target: > 99%. If < 95% → shared_buffers too small, or working set doesn't fit in RAM at all.

**Require restart**: Yes. Changing shared_buffers requires PostgreSQL restart.

## work_mem — The Sort/Hash Budget

**What it is**: RAM available for one sorting or hashing operation inside one query.

This is NOT per session. It is per operation. One complex query might have 5 sort operations. Each gets `work_mem`.

**The math that surprises people:**

```
work_mem = 64MB
200 concurrent sessions
Each session running a query with 3 sort nodes

Maximum RAM for sorts: 200 × 3 × 64MB = 38.4GB
Plus shared_buffers (8GB) = 46.4GB
Plus OS overhead = easily OOM
```

**The OOM killer will kill PostgreSQL processes.** Clients see disconnections. The OOM killer doesn't care about database consistency — it just kills.

**Default is 4MB for a reason.** It's small enough that even many concurrent operations don't OOM you. But 4MB is too small for real analytics queries — they spill to disk.

**How to see if work_mem is too low:**
```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
-- Look for: "Sort Method: external merge Disk"
-- Look for: "Batches: 4" in Hash Join (means it spilled to temp files)

-- Also check temp file usage per database
SELECT datname, temp_files, temp_bytes
FROM pg_stat_database;
-- temp_files > 0 means work_mem is too small for some queries
```

**The right approach:**
```
work_mem = 4MB              # global default (conservative)

-- Then for specific heavy queries, set it in the session:
SET work_mem = '256MB';
SELECT ... complex analytics query ...;
RESET work_mem;
```

Or set it per role:
```sql
ALTER ROLE analyst SET work_mem = '128MB';
```

**Formula for global setting:**
```
work_mem = (available RAM - shared_buffers) / (max_connections × 3)
```

On 32GB RAM, 8GB shared_buffers, 200 max_connections:
```
(32 - 8) × 1024 / (200 × 3) = 24576 / 600 ≈ 40MB
```

But that's the maximum safe global value. Most people set it lower (4-16MB global) and bump it per session for heavy queries.

## maintenance_work_mem — For Heavy Maintenance

**What it is**: RAM used by VACUUM, CREATE INDEX, ALTER TABLE ADD FOREIGN KEY, and pg_restore.

```
maintenance_work_mem = 64MB     # default
```

This one is per worker, but maintenance operations don't run 200 at a time. You can set it much higher:

```
maintenance_work_mem = 2GB     # good for fast index builds and vacuum
```

**When it matters:**
- `VACUUM` needs to sort dead tuple TIDs — more RAM = faster vacuum
- `CREATE INDEX` on a big table — more RAM = sorts more in memory = much faster
- `pg_restore` with indexes — bigger = faster restore

Set it high. On a dedicated PostgreSQL server:
```
maintenance_work_mem = 1GB to 2GB
```

**Also set:**
```
autovacuum_work_mem = -1        # -1 means "use maintenance_work_mem"
                                # set to a specific value if you want autovacuum
                                # to use less RAM than manual VACUUM
```

## wal_buffers — WAL Staging Area

**What it is**: RAM buffer where WAL records are written before the WAL writer flushes them to disk.

```
wal_buffers = -1    # default: auto-sized to 1/32 of shared_buffers, max 64MB
```

The default (`-1` = auto) is fine for almost every system. On high-write servers with very fast NVMe, you might increase it to 64MB explicitly. But this is rarely a bottleneck — if WAL is your bottleneck, the problem is usually disk speed, not buffer size.

---

## effective_cache_size — A Planning Hint (Not Allocation)

**This is NOT memory allocation.** This parameter does not reserve any RAM.

It tells the query planner: "Assume this much RAM is available for caching between shared_buffers and OS page cache." The planner uses this to decide whether index scans are worth it.

```
effective_cache_size = 75% of total RAM
```

On a 32GB system: `effective_cache_size = 24GB`

If set too low → planner thinks less data is cached → prefers sequential scans → slower.
If set too high → planner overestimates cache effectiveness → but this rarely causes harm.

Set it high. It costs nothing and helps the planner.

## The Memory Stack in Practice

On a 32GB dedicated PostgreSQL server:

```
Total RAM:                              32 GB
OS + PostgreSQL process overhead:       ~2 GB
shared_buffers:                          8 GB    (25%)
effective_cache_size hint:              24 GB    (75% — planner hint only)
maintenance_work_mem:                    1 GB    (for VACUUM, index builds)
work_mem (global):                      16 MB    (conservative, raise per session)
wal_buffers:                            64 MB    (or -1 auto)
Connection processes (100 × ~10MB):      1 GB
─────────────────────────────────────────────
Remaining for OS page cache:            ~20 GB   ← this IS being used by PostgreSQL
                                                    (for data not in shared_buffers)
```

## What Happens When You Add RAM But Don't Tune

You upgrade from 16GB to 64GB. You don't change postgresql.conf.

- `shared_buffers` stays at default 128MB or whatever it was
- `effective_cache_size` is wrong → planner makes bad decisions
- `maintenance_work_mem` still 64MB → VACUUMs are slower than they need to be
- You've paid for 64GB and PostgreSQL is using 2GB

Always retune after adding RAM.

```
# Rough formula: after determining shared_buffers
effective_cache_size = total_ram * 0.75
maintenance_work_mem = min(2GB, total_ram * 0.05)
work_mem = (total_ram - shared_buffers) / (max_connections * 3)
```

## Checking Memory Usage Live

```sql
-- How many buffers are dirty right now?
SELECT count(*) FILTER (WHERE isdirty) AS dirty_buffers,
       count(*) AS total_buffers,
       round(count(*) FILTER (WHERE isdirty)::numeric / count(*) * 100, 1) AS dirty_pct
FROM pg_buffercache;   -- requires pg_buffercache extension

-- What is filling shared_buffers?
SELECT datname, relname, count(*) AS buffers
FROM pg_buffercache b
JOIN pg_class c ON b.relfilenode = pg_relation_filenode(c.oid)
JOIN pg_database d ON b.reldatabase = d.oid
WHERE relname IS NOT NULL
GROUP BY 1, 2
ORDER BY 3 DESC
LIMIT 20;
```

## Summary: Memory Parameters Cheatsheet

| Parameter | What it controls | Rule of thumb |
|---|---|---|
| `shared_buffers` | Buffer pool (data page cache) | 25% of RAM |
| `work_mem` | Per sort/hash op | 4-16MB global, raise per session |
| `maintenance_work_mem` | VACUUM, CREATE INDEX | 1-2GB on dedicated servers |
| `wal_buffers` | WAL staging | -1 (auto) or 64MB |
| `effective_cache_size` | Planner cache hint (no allocation) | 75% of RAM |
| `autovacuum_work_mem` | Autovacuum RAM | -1 (use maintenance_work_mem) |
