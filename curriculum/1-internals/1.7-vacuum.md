# 1.7 — VACUUM: The Garbage Collector

**Phase**: 1 — Internals
**Est. reading time**: 25 min

---

## Why VACUUM Exists

Every DELETE and UPDATE leaves dead row versions on disk (MVCC, 1.6). Without cleanup:
1. Table files grow even when you're deleting data
2. Sequential scans read dead rows and waste time
3. Transaction IDs eventually wrap around → database stops

VACUUM is how PostgreSQL reclaims space and keeps the database healthy.

---

## What VACUUM Actually Does

VACUUM does THREE things in one pass:

**1. Reclaim dead tuples**
Scans table pages. Finds rows with `xmax` set where that transaction has committed and no active transaction can see the old version. Marks those slots as reusable.

**2. Update the visibility map**
Pages where all rows are "all-visible" (no dead tuples) get marked in the visibility map (`_vm` file). Future VACUUMs skip these pages. Future index-only scans use them directly.

**3. Freeze old transaction IDs**
Rows with very old `xmin` values get their xmin replaced with `FrozenTransactionId` — a special value meaning "always visible to everyone." This prevents transaction ID wraparound.

---

## VACUUM vs VACUUM FULL vs VACUUM ANALYZE

| Command | What it does | Lock held | When to use |
|---|---|---|---|
| `VACUUM tablename` | Reclaims dead tuples, updates FSM/VM, freezes rows | ShareUpdateExclusive (light) | Normal maintenance — safe in production |
| `VACUUM ANALYZE tablename` | VACUUM + update statistics | ShareUpdateExclusive | After large data changes |
| `VACUUM FULL tablename` | Rewrites entire table to new file, returns space to OS | AccessExclusive (heavy) | Only when you need to shrink the file |
| `VACUUM FREEZE tablename` | VACUUM + aggressive freezing | ShareUpdateExclusive | When approaching txn ID wraparound |

**VACUUM FULL is dangerous in production.** It holds an `AccessExclusive` lock — nothing can read or write the table while it runs. On a large, busy table it can mean minutes or hours of downtime.

**Alternative to VACUUM FULL**: `pg_repack` or `pg_squeeze`. These rewrite the table online with minimal locking.

## Autovacuum — VACUUM That Runs Itself

Manual VACUUM is for special situations. Day-to-day, autovacuum handles it.

```
autovacuum_naptime = 1min           # how often launcher wakes up to check
autovacuum_max_workers = 3          # concurrent autovacuum workers
```

**When does autovacuum trigger VACUUM on a table?**

```
trigger when: dead_tuples > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × live_rows

defaults:
autovacuum_vacuum_threshold = 50       # absolute minimum dead tuples
autovacuum_vacuum_scale_factor = 0.2   # 20% of table
```

So on a 100-row table: trigger when dead tuples > 50 + (0.2 × 100) = 70 dead tuples.
On a 10,000,000-row table: trigger when dead tuples > 50 + (0.2 × 10M) = 2,000,050 dead tuples.

**The problem with scale_factor on large tables**: You have to accumulate 2 million dead tuples before autovacuum kicks in. On a high-write table, that's a lot of bloat accumulating before cleanup.

**Fix: Set per-table autovacuum settings for large, hot tables:**
```sql
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.01,   -- trigger at 1% dead tuples
    autovacuum_vacuum_threshold = 1000       -- or 1000 dead tuples minimum
);
```

**When does autovacuum trigger ANALYZE?**
```
autovacuum_analyze_threshold = 50
autovacuum_analyze_scale_factor = 0.1    # 10% of table changed
```

## Bloat — Why Files Don't Shrink

After VACUUM runs, dead tuples are marked reusable. But the file doesn't shrink.

```
Before:
  File: [live][dead][dead][live][dead][live]   size: 100MB

After VACUUM:
  File: [live][free][free][live][free][live]   size: 100MB
  (but free space is tracked in FSM — new rows fill it)
```

VACUUM returns space for **PostgreSQL to reuse**, not to the OS. The file size stays the same.

Only `VACUUM FULL` (or `pg_repack`) actually returns space to the OS by rewriting the file.

**Is this a problem?** Usually not. If you deleted 50% of a table, VACUUM makes that 50% available for new inserts. The file size stays the same but new inserts don't make it grow further. Only matters when you need to actually reclaim disk space.

## Monitoring VACUUM

```sql
-- Per-table vacuum status
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    round(n_dead_tup::numeric / nullif(n_live_tup + n_dead_tup, 0) * 100, 1) AS dead_pct,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

```sql
-- Is autovacuum currently running? On which tables?
SELECT pid, now() - query_start AS duration, query
FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker';
```

```sql
-- Transaction ID age (wraparound risk)
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
-- Alert if age > 1,500,000,000
-- Emergency VACUUM FREEZE if age > 1,800,000,000
```

## Autovacuum Cost Throttling

By default, autovacuum throttles itself to not hammer your disk. It does some work, then sleeps:

```
autovacuum_vacuum_cost_delay = 2ms    # sleep between work chunks
autovacuum_vacuum_cost_limit = 200    # how much work per chunk

# Cost values:
vacuum_cost_page_hit = 1             # cost to process a cached page
vacuum_cost_page_miss = 10           # cost to read page from disk
vacuum_cost_page_dirty = 20          # cost to write a dirty page
```

At `cost_limit = 200` and `cost_delay = 2ms`:
- If all pages are in shared_buffers: 200 pages/2ms = 100,000 pages/second
- If all pages need disk reads: 200/10 = 20 pages per chunk, then 2ms sleep → ~10,000 pages/second

**The problem**: On heavily loaded systems with large tables, this throttling means autovacuum can't keep up. Dead tuples accumulate faster than autovacuum can clean.

**Fix for systems where autovacuum is falling behind:**
```
autovacuum_vacuum_cost_delay = 2ms     # or even 0ms to remove throttling
autovacuum_vacuum_cost_limit = 800     # 4x more work per chunk
autovacuum_max_workers = 6             # more parallel workers
```

Or per-table:
```sql
ALTER TABLE hot_table SET (
    autovacuum_vacuum_cost_delay = 0,
    autovacuum_vacuum_cost_limit = 1000
);
```

## The Visibility Map and Index-Only Scans

When VACUUM marks a page as "all-visible" in the visibility map, two great things happen:

**1. Future VACUUMs skip it**: If a page is all-visible, VACUUM doesn't need to scan it again (unless new dead tuples land on it). This makes VACUUM progressively faster as tables stabilize.

**2. Index-only scans become possible**: If an index contains all columns a query needs AND the page is all-visible, PostgreSQL can return results from the index alone without reading the heap. Much faster.

```sql
-- Check how much of the table is all-visible
SELECT relname,
       n_live_tup,
       all_visible_pages,
       total_pages,
       round(all_visible_pages::numeric / nullif(total_pages, 0) * 100, 1) AS pct_visible
FROM pg_stat_user_tables u
JOIN (SELECT oid, relpages AS total_pages FROM pg_class) c ON c.oid = u.relid
CROSS JOIN LATERAL (
    SELECT count(*) AS all_visible_pages
    FROM generate_series(0, relpages - 1) blkno,
         LATERAL (SELECT pg_visibility(relid, blkno)) v
    WHERE v.all_visible
) v;
-- (simpler with pg_visibility extension)
```

## Freezing — The Wraparound Prevention

PostgreSQL uses 32-bit transaction IDs. Max: ~4.2 billion. In practice, ~2.1 billion transactions before wraparound.

VACUUM "freezes" old rows: replaces their `xmin` with `FrozenTransactionId` (special value = always visible). These rows no longer need the transaction ID system.

```
autovacuum_freeze_max_age = 200000000    # 200 million transactions
```

When a table's `relfrozenxid` age exceeds this, autovacuum will trigger an aggressive vacuum (even if the table has few dead tuples) specifically to freeze old rows.

**Emergency response** if approaching wraparound:
```sql
-- Check how close we are
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;

-- If dangerous (> 1.8 billion), force freeze NOW
VACUUM FREEZE ANALYZE mytable;

-- On the whole database
vacuumdb --freeze --analyze --all
```

## ANALYZE — Keeping Statistics Fresh

ANALYZE samples the table data and updates `pg_statistic`. The query planner uses these statistics to estimate how many rows a filter will return, which determines whether to use an index or do a seq scan.

```sql
-- Manual analyze
ANALYZE orders;

-- With verbosity
ANALYZE VERBOSE orders;
```

**When to run manually:**
- After a large bulk INSERT, UPDATE, or DELETE
- After COPY of large datasets
- When you see bad query plans and suspect stale statistics

**autovacuum also runs ANALYZE** based on `autovacuum_analyze_threshold` and `autovacuum_analyze_scale_factor`. You can also tune these per table.

**Statistics depth:**
```
default_statistics_target = 100    # default
```

Higher value = more statistics = better planner estimates = slower ANALYZE. For columns with many distinct values that appear in complex WHERE clauses:
```sql
-- More statistics for this column
ALTER TABLE orders ALTER COLUMN customer_id SET STATISTICS 500;
ANALYZE orders;
```

## Common VACUUM Problems

**1. Long-running transaction blocking VACUUM**
VACUUM can't clean dead tuples that might still be visible to any active transaction. If a transaction has been open for 6 hours, 6 hours of dead tuples are stuck.

```sql
-- Find the oldest transaction
SELECT pid, now() - xact_start AS age, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY age DESC
LIMIT 5;
```

**2. Autovacuum not keeping up on write-heavy tables**
Signs: `n_dead_tup` growing fast, `last_autovacuum` timestamp getting old. Fix: per-table autovacuum settings (see above) or increase `autovacuum_vacuum_cost_limit`.

**3. Autovacuum skipped due to locks**
Autovacuum will back off if it can't acquire the lock after a short wait. If your app holds long transactions on hot tables, autovacuum may never get to run.

**4. Bloat after heavy DELETE**
Ran `DELETE FROM logs WHERE created_at < now() - interval '1 year'` and deleted 80% of table? VACUUM reclaims it but file doesn't shrink. Use `pg_repack` if you need the disk space back without downtime.

## pg_repack — VACUUM FULL Without the Lock

```bash
# Install
apt install postgresql-16-repack   # Debian
yum install pg_repack_16           # RHEL

# Repack a table online (minimal locking)
pg_repack -h localhost -U postgres -d mydb -t orders
```

What it does internally:
1. Creates a new table
2. Copies rows into it while the original stays live (tracks new changes via trigger)
3. Applies captured changes to new table
4. Swaps the tables atomically
5. Drops the old table

Result: compact table, disk space returned, almost no downtime.
