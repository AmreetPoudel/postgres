# 1.9 — Index Internals: B-Trees, GIN, BRIN and When to Use What

**Phase**: 1 — Internals
**Est. reading time**: 25 min

## What an Index Is

An index is a separate data structure that lets PostgreSQL find rows without reading the entire table.

Without index: Read every row in the table, check if it matches. O(n).
With index: Follow a tree structure to the matching rows. O(log n) to find them.

But indexes have costs:
- Take up disk space (often 10-40% of table size)
- Every INSERT, UPDATE, DELETE must update all indexes on the table
- More indexes = slower writes

The art is choosing the right indexes, not just adding them everywhere.

---

## B-Tree Index — The Default

PostgreSQL's default index type. Suitable for most use cases.

**How a B-Tree works:**

```
                     [Root: 500]
                    /            \
            [250]                 [750]
           /     \               /     \
       [100]   [400]         [600]   [900]
      / | \   / | \         /  \    /  \
    ...       ...         ...       ...
        ↑
  Leaf nodes contain: index key + TID (table page, slot)
```

- All leaf nodes are linked (for range scans)
- Balanced tree: every search is O(log n)
- Supports: `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `IS NULL`, `IN`

**What B-Tree does NOT support**: Full-text search, array containment, geometric queries (use other index types for these).

## Index Scan vs Bitmap Index Scan vs Seq Scan

**When the planner chooses each:**

| Plan | When chosen | Reason |
|---|---|---|
| Index Scan | Small result set (< ~5% of table) | Each row lookup is a random I/O, too many is slow |
| Bitmap Index Scan | Medium result set (5-20% of table) | Builds bitmap of pages, reads pages in order (more sequential) |
| Seq Scan | Large result set (> ~20% of table) | Faster to just read everything |

These thresholds depend on `random_page_cost`. On NVMe (`random_page_cost = 1.1`), index scans win more often.

**Force a specific scan type (for debugging, not production):**
```sql
SET enable_indexscan = off;      -- disable index scans
SET enable_seqscan = off;        -- force index usage
EXPLAIN SELECT ...;
RESET enable_indexscan;
RESET enable_seqscan;
```

## Creating Indexes Effectively

```sql
-- Basic index
CREATE INDEX ON orders(customer_id);

-- Named index (good practice)
CREATE INDEX idx_orders_customer_id ON orders(customer_id);

-- CONCURRENTLY: builds index without locking the table
-- Takes longer, but doesn't block reads/writes
CREATE INDEX CONCURRENTLY idx_orders_customer_id ON orders(customer_id);
-- Use CONCURRENTLY on production tables. Always.

-- Composite index (multi-column)
CREATE INDEX ON orders(customer_id, status);
-- Useful for queries filtering on BOTH columns
-- Also useful for queries filtering on customer_id alone (leftmost prefix)
-- NOT useful for queries filtering on status alone
```

**Composite index prefix rule**: Index on `(a, b, c)` can be used for:
- WHERE a = ...
- WHERE a = ... AND b = ...
- WHERE a = ... AND b = ... AND c = ...
- ORDER BY a, b, c (with matching sort direction)

Cannot be used for:
- WHERE b = ... (skips leftmost column)
- WHERE c = ...

## Partial Indexes — Index Only What You Query

If you always query `WHERE status = 'pending'` and pending is 1% of rows:

```sql
-- Full index on status column
CREATE INDEX ON orders(status);
-- Indexes ALL statuses: 'pending', 'shipped', 'cancelled', 'returned'
-- Huge index for something you only query 1% of

-- Partial index: only index pending orders
CREATE INDEX ON orders(customer_id) WHERE status = 'pending';
-- Much smaller, much faster
-- Only used for queries with WHERE status = 'pending'
```

**Partial indexes are one of the most underused PostgreSQL features.**

Use cases:
- Soft-delete tables: `WHERE deleted_at IS NULL` (partial index only on active rows)
- Status workflows: index only active/pending states
- High-cardinality where you always filter: `WHERE is_active = true`

## Covering Indexes — Index-Only Scans

An index normally stores key columns + TID (table location). To get other columns, PostgreSQL must go fetch the table row ("heap fetch").

A covering index includes extra columns in the index so PostgreSQL never needs to touch the table:

```sql
-- Standard index: stores (customer_id, TID)
CREATE INDEX ON orders(customer_id);

-- For query: SELECT created_at, total FROM orders WHERE customer_id = 42
-- Must still fetch heap for created_at and total

-- Covering index: stores (customer_id, created_at, total)
CREATE INDEX ON orders(customer_id) INCLUDE (created_at, total);

-- Now query can be satisfied from the index alone (index-only scan)
-- Requires: visibility map says page is all-visible
```

Index-only scans are significantly faster — no heap access at all.

**When to use INCLUDE:**
- Frequently queried columns that are not the search key
- When you see a lot of heap fetches in EXPLAIN BUFFERS

## GIN Index — For Arrays, JSON, Full-Text Search

GIN = Generalized Inverted Index. Think of a book's back-index: for each word, a list of pages it appears on.

```sql
-- For full-text search
CREATE INDEX ON articles USING GIN(to_tsvector('english', body));

-- For JSONB containment
CREATE INDEX ON events USING GIN(data jsonb_path_ops);

-- For arrays
CREATE INDEX ON tags USING GIN(tag_list);
```

**Queries GIN supports:**
```sql
-- Full-text
SELECT * FROM articles WHERE to_tsvector('english', body) @@ 'postgres & replication';

-- JSONB
SELECT * FROM events WHERE data @> '{"type": "login"}';

-- Array containment
SELECT * FROM tags WHERE tag_list @> ARRAY['postgres', 'performance'];
```

**GIN vs B-Tree for JSONB:**
- GIN: Use for `@>` (containment), `?` (key exists), `@@` (path queries)
- B-Tree: Can't index inside JSONB efficiently
- `jsonb_path_ops` GIN is more compact than default `jsonb_ops` — use it if you only need `@>` queries

## BRIN Index — For Naturally Ordered Data

BRIN = Block Range INdex. Stores the min/max value of each range of pages.

```sql
CREATE INDEX ON events USING BRIN(created_at);
```

**How it works**: Instead of indexing every value, BRIN stores:
```
Pages 0-127:   created_at MIN='2024-01-01' MAX='2024-01-15'
Pages 128-255: created_at MIN='2024-01-15' MAX='2024-01-31'
...
```

A query for `created_at > '2024-03-01'` skips the first two ranges.

**Size**: BRIN is tiny — a few hundred KB for a multi-GB table. A B-tree on the same column would be hundreds of MB.

**Use BRIN when:**
- Data is naturally ordered by the indexed column (time-series, auto-increment IDs)
- The column has high correlation with physical order
- You don't need point lookups, just range scans

**Don't use BRIN when:**
- Data is randomly ordered (BRIN provides no benefit)
- You need exact matches (BRIN returns a range — PostgreSQL still scans those pages)

## Hash Index

```sql
CREATE INDEX ON users USING HASH(email);
```

Only supports `=` queries. Faster than B-Tree for equality lookups on very high-cardinality columns. But B-Tree handles equality too, plus ranges. In practice, stick with B-Tree unless you have a specific benchmark showing Hash wins for your workload.

## Index Bloat

Indexes get bloat too. When rows are deleted or updated, the old index entries become dead. VACUUM cleans heap dead tuples, but index entries also need cleanup.

Regular VACUUM handles this via "index vacuum" passes. But if write rate is very high, indexes can bloat significantly.

```sql
-- Check index sizes (large index relative to table is suspicious)
SELECT
    schemaname,
    relname AS table,
    indexrelname AS index,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    pg_size_pretty(pg_relation_size(indrelid)) AS table_size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC;
```

**Reindex if bloated:**
```sql
-- Rebuild a specific index (locks table briefly during final swap)
REINDEX INDEX CONCURRENTLY idx_orders_customer_id;  -- PG12+

-- Rebuild all indexes on a table
REINDEX TABLE CONCURRENTLY orders;
```

## Unused Indexes

Every index you create slows down writes. Unused indexes are pure overhead.

```sql
-- Find indexes with zero or very low usage
SELECT
    schemaname,
    relname AS table,
    indexrelname AS index,
    idx_scan AS scans,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan < 10            -- rarely used
  AND indisunique = false      -- not a unique constraint (needed for data integrity)
ORDER BY pg_relation_size(indexrelid) DESC;
```

**Caution**: Reset stats after a deployment that changed query patterns. An index may look unused because it's only needed for a seasonal query.

```sql
-- Reset index stats
SELECT pg_stat_reset();
-- Wait a few weeks, then check again
```

## Common Index Mistakes

**1. Indexing low-cardinality columns**
`CREATE INDEX ON orders(status)` where status has 4 values: PostgreSQL will probably prefer a seq scan anyway. Don't bother.

**2. Index on (a) and index on (a, b) — the first is redundant**
`CREATE INDEX ON orders(customer_id)` becomes redundant if you have `CREATE INDEX ON orders(customer_id, status)`. The composite can be used for queries on just `customer_id`.

**3. Too many indexes on a write-heavy table**
10 indexes on a table that gets 100,000 inserts/second = 10 index writes per insert = 1,000,000 index writes/second. Feel that?

**4. Not using CONCURRENTLY on production**
`CREATE INDEX` without CONCURRENTLY takes a `ShareLock` on the table — no writes during the build. On a large production table, that's unacceptable. Always use `CONCURRENTLY`.

**5. Not analyzing after creating an index**
The planner won't use a new index until it knows about it via statistics. Run `ANALYZE tablename` after creating an important index.

## Quick Decision Guide

| Query type | Index type |
|---|---|
| Equality, range on simple columns | B-Tree |
| JSON containment, array contains | GIN |
| Full-text search | GIN on tsvector |
| Time-series, append-only ordered data | BRIN |
| Only query active rows (small subset) | Partial B-Tree |
| Need all SELECT columns from index | Covering B-Tree with INCLUDE |
