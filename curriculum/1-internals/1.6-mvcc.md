# 1.6 — MVCC: Multiple Versions, No Read Locks

**Phase**: 1 — Internals
**Est. reading time**: 20 min

---

## The Problem MVCC Solves

In a simple database, reads and writes conflict. If Transaction A is updating a row, Transaction B has to wait to read it. This kills performance on any system with concurrent users.

PostgreSQL's answer: **Multi-Version Concurrency Control**.

The rule: **readers never block writers, writers never block readers.**

---

## How It Works — The Simple Version

When you UPDATE a row in PostgreSQL:
1. The old row version is **not deleted**. It gets a "deleted by transaction X" stamp.
2. A **new row version** is written with the new data.
3. Both versions physically exist on disk.
4. Different transactions see different versions, depending on their snapshot (taken per statement in READ COMMITTED, once per transaction in REPEATABLE READ and SERIALIZABLE).

```
Before UPDATE:
  Row version 1: [xmin=50, xmax=0, status='pending']

Transaction 100 runs: UPDATE orders SET status='shipped' WHERE id=1;

After UPDATE (before commit):
  Row version 1: [xmin=50, xmax=100, status='pending']   ← "deleted by txn 100"
  Row version 2: [xmin=100, xmax=0, status='shipped']    ← new version by txn 100

Transaction 101 (started before txn 100 commits):
  Snapshot says: txn 100 not committed yet
  Sees: Row version 1 (status='pending')  ← reads consistently, not blocked

Transaction 100 commits.

Transaction 102 (started after txn 100 commits):
  Snapshot says: txn 100 committed
  Sees: Row version 2 (status='shipped')
```

This is how PostgreSQL serves different views of data to different transactions simultaneously.

## xmin, xmax — The Visibility Fields

Every row in PostgreSQL has hidden fields (you can SELECT them):

```sql
SELECT xmin, xmax, * FROM orders WHERE id = 1;
```

- `xmin`: The transaction ID that **created** this row version. Row is visible to transactions that can see txn `xmin` committed.
- `xmax`: The transaction ID that **ended** this row version. 0 = still live. Non-zero usually means deleted or updated, but not always: `SELECT ... FOR UPDATE` stores the locker's ID there, and a DELETE that rolled back leaves its ID behind. Visibility checks treat both as live.

**Visibility rule** (simplified):
```
A row version is visible to my snapshot if:
  - xmin committed before my snapshot was taken
  - AND (xmax = 0 OR xmax aborted OR xmax hadn't committed when my snapshot was taken)
```

Your snapshot is built from the **proc array** in shared memory: which transactions were still running at that moment. Whether a transaction committed or aborted comes from `pg_xact`, and the answer gets cached on the row itself as *hint bits*, so later readers don't have to look it up again.

## Transaction Isolation Levels

MVCC makes multiple isolation levels possible:

| Level | What you see |
|---|---|
| `READ COMMITTED` (default) | Each statement sees a fresh snapshot — data committed by others shows up between statements |
| `REPEATABLE READ` | Entire transaction sees snapshot from when first query ran — no phantoms, no non-repeatable reads |
| `SERIALIZABLE` | Fully serializable — as if transactions ran one at a time |

```sql
-- Check current level
SHOW transaction_isolation;

-- Set for a transaction
BEGIN ISOLATION LEVEL REPEATABLE READ;
```

**Operational relevance**: Most applications use READ COMMITTED (default). A single statement always sees one consistent snapshot, even in READ COMMITTED. Use REPEATABLE READ when a report runs *several* queries that must agree with each other (and be ready to retry serialization errors if such a transaction also writes).

## The Hidden Cost: Dead Tuples

Every UPDATE leaves behind a dead row version. Every DELETE leaves a dead row.

```
Table with 1 million rows.
You run: UPDATE orders SET status='shipped' WHERE id <= 500000;

Result:
  500,000 new row versions (live)
  500,000 old row versions (dead, waiting for VACUUM)
Total physical rows on disk: 1,500,000

Table file size grows significantly even though you just updated, not inserted.
```

These dead tuples:
- Take up space (table bloat)
- Get scanned by sequential scans (wasted I/O)
- Must be cleaned by VACUUM

## Transaction IDs and Wraparound

PostgreSQL uses 32-bit transaction IDs. Range: 0 to ~4.2 billion. In practice, half of that space is "past" and half is "future" — so effective range is ~2.1 billion transactions before wraparound.

**The wraparound problem**: If transaction IDs wrap around without freezing old rows, very old rows might appear to be "in the future" and become invisible. That's data loss.

**Protection mechanism**: VACUUM "freezes" old rows: it marks them as visible to everyone, forever, so their xmin no longer matters. (Since PG 9.4 this sets flag bits; the original xmin stays readable for forensics.) The `relfrozenxid` column in `pg_class` tracks how old the oldest unfrozen transaction in each table is.

```sql
-- How far are we from wraparound? (warn at > 500 million, critical at > 1 billion)
SELECT datname,
       age(datfrozenxid) AS xid_age,
       pg_size_pretty(pg_database_size(datname)) AS db_size
FROM pg_database
ORDER BY age(datfrozenxid) DESC;

-- Per-table status
SELECT relname, age(relfrozenxid) AS xid_age
FROM pg_class
WHERE relkind = 'r'
ORDER BY age(relfrozenxid) DESC
LIMIT 20;
```

**What happens as the age climbs** (PostgreSQL 16 defaults):
- **200 million** (`autovacuum_freeze_max_age`): autovacuum forces an anti-wraparound VACUUM on the table, even if autovacuum is turned off
- **1.6 billion** (`vacuum_failsafe_age`): VACUUM enters failsafe mode, ignoring cost delays and skipping index cleanup to finish freezing as fast as possible
- **40 million XIDs before the limit** (about 2.1 billion): each new transaction ID comes with `WARNING: database "mydb" must be vacuumed within N transactions`
- **3 million XIDs before the limit**: PostgreSQL refuses to assign new transaction IDs: `ERROR: database is not accepting commands to avoid wraparound data loss`. Read-only queries still work, and so does VACUUM

The fix at that point is plain `VACUUM`: not `VACUUM FREEZE` (more work than needed) and not single-user mode (no longer necessary). First get rid of whatever holds the oldest XID back: old prepared transactions, long-running transactions, stale replication slots. T-11 walks through it. Prevention is proper autovacuum tuning (Phase 2.5).

## HOT Updates — An Optimization

Normal UPDATE = new row written to possibly a different page. All indexes pointing to the old row need updating.

**HOT (Heap-Only Tuple) update**: If the new row fits on the **same page** as the old row AND no indexed columns changed, PostgreSQL can do a "HOT update":
1. New row version written on same page
2. Old row points to new row via a chain
3. Indexes don't need updating (they still point to the same page, and follow the chain)

This is much cheaper. HOT updates happen automatically when conditions are met.

**What helps HOT updates:**
- `fillfactor` on tables — leaving free space on pages for updates to land on same page
```sql
-- Table with 80% fillfactor (20% free for HOT updates)
CREATE TABLE orders (...) WITH (fillfactor = 80);
ALTER TABLE orders SET (fillfactor = 80);
```

For tables with frequent UPDATEs on non-indexed columns, fillfactor = 70-80 dramatically reduces index bloat.

## Snapshot Isolation in Practice

```sql
-- Session 1
BEGIN;
SELECT status FROM orders WHERE id = 1;
-- Returns 'pending'

-- Session 2 (different connection)
BEGIN;
UPDATE orders SET status = 'shipped' WHERE id = 1;
COMMIT;

-- Session 1 (still running)
SELECT status FROM orders WHERE id = 1;
-- With READ COMMITTED: returns 'shipped' (sees committed data)
-- With REPEATABLE READ: returns 'pending' (snapshot taken at the first query, not at BEGIN)

COMMIT;
```

## MVCC and Locks — What Still Gets Locked

MVCC eliminates read-write conflicts. But some operations still need explicit locks:

| Operation | Lock taken | What it conflicts with |
|---|---|---|
| `SELECT` | ACCESS SHARE (table) | Only ACCESS EXCLUSIVE: most `ALTER TABLE`, `DROP`, `TRUNCATE`, `VACUUM FULL` |
| `SELECT FOR UPDATE` | ROW SHARE (table) + row locks | Other writers and lockers of the *same rows* |
| `INSERT/UPDATE/DELETE` | ROW EXCLUSIVE (table) + row locks | Writers of the same rows; `CREATE INDEX` (non-concurrent); DDL |
| `ALTER TABLE` (most) | ACCESS EXCLUSIVE | EVERYTHING |
| `VACUUM FULL` | ACCESS EXCLUSIVE | EVERYTHING |
| `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE | VACUUM, ANALYZE, other concurrent index builds, DDL |

The key insight: **a normal SELECT never blocks DML and is never blocked by it.** It does take a lightweight table lock, though, and that lock is enough to make DDL (`ALTER TABLE`, `DROP TABLE`, `TRUNCATE`, `VACUUM FULL`) wait — and everything queued behind the DDL waits too.

This is why long-running transactions + DDL = problems:
```sql
-- Session 1 has been running for 2 hours
BEGIN;
SELECT ... -- long running analytics

-- Session 2 runs:
ALTER TABLE orders ADD COLUMN created_at timestamp;
-- This is BLOCKED by Session 1's long transaction
-- AND now blocks every new query on orders (they queue behind the ALTER)
```

## Practical MVCC Gotchas

**1. Long transactions cause bloat**
VACUUM can't remove a row version that some open snapshot might still need: anything that became dead after the oldest snapshot (or oldest running transaction ID) in the database. Keep a REPEATABLE READ transaction open for 3 hours and 3 hours of dead tuples accumulate, in every table.

```sql
-- Find longest running transactions
SELECT pid, now() - xact_start AS duration, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY duration DESC;
```

**2. Idle in transaction**
Same problem, with a nuance worth testing yourself. A session sitting `idle in transaction` holds back VACUUM if it has written anything (its transaction ID still counts as running) or holds a snapshot (REPEATABLE READ, or an open cursor). Then dead tuples can't be cleaned anywhere in the database, not just in the tables it touched. A read-only READ COMMITTED transaction sitting idle holds no snapshot between statements, so it doesn't block VACUUM, but it still holds its locks. `backend_xid` and `backend_xmin` in `pg_stat_activity` tell you which case you have.

**3. Replication can hold the horizon too**
A standby with `hot_standby_feedback = on` reports its oldest snapshot to the primary, and a replication slot can pin an old `xmin` (logical slots pin `catalog_xmin`). Either one stops VACUUM on the primary exactly like a long transaction. (Older guides mention `vacuum_defer_cleanup_age`; PostgreSQL 16 removed it.)

**4. Subtransactions (savepoints)**
Each SAVEPOINT starts a subtransaction, which gets its own XID once it writes. A backend caches up to 64 of them in the proc array; beyond that the cache overflows and other sessions have to look visibility up in `pg_subtrans`, a known performance cliff (worse on standbys). ORMs that wrap every statement in a savepoint hit this.

## Key MVCC Queries

```sql
-- The xid type has no ordering operators, so min() or ORDER BY on backend_xmin fail.
-- Compare ages instead: how far back does the oldest snapshot reach?
SELECT max(age(backend_xmin)) AS oldest_snapshot_age FROM pg_stat_activity;

-- See all transaction IDs currently "in flight"
SELECT pid, backend_xid, state, left(query, 60) AS query
FROM pg_stat_activity WHERE backend_xid IS NOT NULL;

-- Everything that holds back the VACUUM horizon, oldest first
SELECT 'session snapshot' AS holder, pid::text AS id, age(backend_xmin) AS xmin_age, state, left(query, 40) AS detail
FROM pg_stat_activity WHERE backend_xmin IS NOT NULL
UNION ALL
SELECT 'session xid', pid::text, age(backend_xid), state, left(query, 40)
FROM pg_stat_activity WHERE backend_xid IS NOT NULL
UNION ALL
SELECT 'replication slot', slot_name::text, greatest(age(xmin), age(catalog_xmin)), active::text, slot_type
FROM pg_replication_slots WHERE xmin IS NOT NULL OR catalog_xmin IS NOT NULL
UNION ALL
SELECT 'prepared xact', gid, age(transaction), owner::text, database::text
FROM pg_prepared_xacts
ORDER BY xmin_age DESC;
```
