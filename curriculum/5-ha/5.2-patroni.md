**Phase**: 5 — HA & Failover

## How Patroni Works

Every PostgreSQL node runs a Patroni process. Patroni:
- Manages a **leader lease** in etcd (or Consul/ZooKeeper)
- Primary holds the lease, renews it every `ttl` seconds
- If primary can't renew the lease (crash, network isolation from etcd), the lease expires
- A standby acquires the lease and promotes itself
- All nodes watch etcd for state changes

```
Node 1 (Primary)                    etcd
  Patroni → acquire lease ─────────►│
  Patroni → renew every 10s ────────►│
  Patroni → monitors PG health       │

Node 2 (Standby)                    etcd
  Patroni → watch for lease ─────────►│
  (if lease expires: try to acquire)  │
```

## Installation

```bash
# Install on all PostgreSQL nodes. Easiest: the package from the PostgreSQL
# apt/yum repositories (PGDG), which pulls in its dependencies and ships a unit file
apt install patroni

# Or with pip, in a virtualenv (recent Debian/Ubuntu refuse a system-wide pip install).
# Patroni doesn't bring a PostgreSQL driver by itself, so name one in the extras:
python3 -m venv /opt/patroni
/opt/patroni/bin/pip install 'patroni[psycopg3,etcd3]'
ln -s /opt/patroni/bin/patroni /opt/patroni/bin/patronictl /usr/local/bin/
```

## Patroni Configuration

```yaml
# /etc/patroni/patroni.yml
scope: postgres-cluster         # cluster name (all nodes same scope)
namespace: /service/            # etcd key prefix
name: pg-node1                  # THIS node's name (unique per node)

restapi:
  listen: 0.0.0.0:8008          # Patroni REST API (for HAProxy health check)
  connect_address: 10.0.0.10:8008

etcd3:
  hosts: 10.0.0.1:2379,10.0.0.2:2379,10.0.0.3:2379

bootstrap:
  dcs:
    ttl: 30                     # lease TTL: how long before failover if primary silent
    loop_wait: 10               # how often Patroni runs its main loop
    retry_timeout: 10           # timeout for DCS operations
    maximum_lag_on_failover: 1048576  # 1MB max lag for standby to be eligible for promotion

    postgresql:
      use_pg_rewind: true       # use pg_rewind to resync demoted primary
      use_slots: true           # use replication slots
      parameters:
        wal_level: replica
        hot_standby: "on"
        max_connections: 200
        max_wal_senders: 10
        max_replication_slots: 10
        wal_log_hints: "on"     # required for pg_rewind

  initdb:
    - encoding: UTF8
    - data-checksums            # enable checksums for new clusters

  pg_hba:
    - local all all peer
    - host all all 127.0.0.1/32 scram-sha-256
    - host all all ::1/128 scram-sha-256
    - host replication replicator 10.0.0.0/24 scram-sha-256
    - host all all 10.0.0.0/24 scram-sha-256    # the cluster's subnet, never 0.0.0.0/0

  # Patroni 4 removed bootstrap.users. It creates the superuser, replication and
  # rewind users from the authentication section below; create application roles
  # yourself after bootstrap (or from a post_bootstrap script).

postgresql:
  listen: 0.0.0.0:5432
  connect_address: 10.0.0.10:5432   # THIS node's IP:port (use node-specific IP)
  data_dir: /var/lib/postgresql/16/main
  bin_dir: /usr/lib/postgresql/16/bin
  config_dir: /etc/postgresql/16/main

  authentication:
    replication:
      username: replicator
      password: replicatorpassword
    superuser:
      username: postgres
      password: postgrespassword
    rewind:
      username: rewind_user
      password: rewindpassword

  parameters:
    unix_socket_directories: '/var/run/postgresql'

tags:
  nofailover: false             # this node can become primary
  noloadbalance: false          # include in load balancing
  clonefrom: false              # don't use as source for cloning
  nosync: false                 # can be sync standby
```

Different YAML files per node — only `name` and `connect_address` / `restapi.connect_address` differ.

The passwords in this file are placeholders: make the file readable only by the postgres user (`chmod 600`).

## Starting Patroni

```bash
# Create systemd service
cat > /etc/systemd/system/patroni.service << 'EOF'
[Unit]
Description=Patroni PostgreSQL HA
After=syslog.target network.target

[Service]
Type=simple
User=postgres
ExecStart=/usr/local/bin/patroni /etc/patroni/patroni.yml
KillMode=process
TimeoutSec=30
Restart=no

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable patroni
systemctl start patroni
```

If you installed the PGDG package, use the unit file it ships instead of writing this one.

**First node to start**: bootstraps the cluster (runs initdb if data dir empty, or adopts existing cluster)

**Subsequent nodes**: join as standbys (pg_basebackup from primary automatically)

## Patroni CLI (patronictl)

```bash
# Cluster status
patronictl -c /etc/patroni/patroni.yml list

# Output:
# + Cluster: postgres-cluster ----+----+-----------+
# | Member   | Host          | Role    | State   | TL | Lag in MB |
# +-----------+---------------+---------+---------+----+-----------+
# | pg-node1 | 10.0.0.10:5432| Leader  | running |  1 |           |
# | pg-node2 | 10.0.0.20:5432| Replica | running |  1 |         0 |
# | pg-node3 | 10.0.0.30:5432| Replica | running |  1 |         0 |

# Planned switchover (healthy cluster): Patroni checks the candidate is caught up,
# demotes the leader cleanly, then promotes the candidate
patronictl -c /etc/patroni/patroni.yml switchover postgres-cluster

# Switchover to a specific node (Patroni 4 uses --leader; the old --master flag is gone)
patronictl -c /etc/patroni/patroni.yml switchover postgres-cluster --leader pg-node1 --candidate pg-node2

# Failover is for an unhealthy cluster (no working leader): promote a specific replica
patronictl -c /etc/patroni/patroni.yml failover postgres-cluster --candidate pg-node2

# Restart a member (rolling restart without cluster downtime)
patronictl -c /etc/patroni/patroni.yml restart postgres-cluster pg-node1

# Reinitialize a node (rebuild from primary)
patronictl -c /etc/patroni/patroni.yml reinit postgres-cluster pg-node2

# Change cluster-wide config (stored in DCS, applies to all nodes)
patronictl -c /etc/patroni/patroni.yml edit-config

# Show cluster config
patronictl -c /etc/patroni/patroni.yml show-config

# Pause automation (for maintenance)
patronictl -c /etc/patroni/patroni.yml pause

# Resume
patronictl -c /etc/patroni/patroni.yml resume
```

## Patroni REST API

Patroni exposes a REST API on port 8008. HAProxy uses this for health checks.

```bash
# Primary only (returns 200)
curl http://10.0.0.10:8008/primary

# Replica only (returns 200)
curl http://10.0.0.10:8008/replica

# Any healthy node (returns 200)
curl http://10.0.0.10:8008/health

# Full cluster status
curl http://10.0.0.10:8008/ | python3 -m json.tool
```

## pg_rewind — Resyncing a Demoted Primary

When a failover happens:
1. Old primary (pg-node1) was writing up to LSN X
2. New primary (pg-node2) was at LSN Y (Y < X, slightly behind)
3. After promotion, pg-node2 continues from LSN Y
4. pg-node1 has writes beyond Y that are not on pg-node2 (those are lost in async replication)

pg_rewind resyncs pg-node1 by:
1. Identifying what diverged (pg-node1 has extra WAL beyond the common ancestor)
2. Copying the changed files from pg-node2 to pg-node1
3. Making pg-node1 a standby of pg-node2

```bash
# pg_rewind (usually done automatically by Patroni with use_pg_rewind: true)
pg_rewind \
  --target-pgdata=/var/lib/postgresql/16/main \
  --source-server="host=10.0.0.20 port=5432 user=rewind_user dbname=postgres"
```

Requirements:
```
wal_log_hints = on    # or checksums enabled
                       # pg_rewind needs this to determine which pages changed
```

Patroni creates the rewind user itself from `authentication.rewind`. Outside Patroni, a non-superuser can run pg_rewind against a source server if it may execute the file-access functions pg_rewind uses (there is no `pg_rewind` role):

```sql
CREATE USER rewind_user WITH LOGIN PASSWORD 'pass';
GRANT EXECUTE ON FUNCTION pg_catalog.pg_ls_dir(text, boolean, boolean) TO rewind_user;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_stat_file(text, boolean) TO rewind_user;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_read_binary_file(text) TO rewind_user;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_read_binary_file(text, bigint, bigint, boolean) TO rewind_user;
```

## Failover Timeline

**Normal failover with Patroni (everything working):**

```
t=0     Primary crashes / becomes unreachable
t=10s   Patroni on primary stops renewing lease (ttl=30s)
t=30s   Lease expires
t=31s   Standbys see expired lease, race to acquire
t=32s   Winner standby acquires lease, starts promotion
t=35s   PostgreSQL promotion completes
t=36s   HAProxy health check sees new primary at port 8008
t=38s   New connections go to new primary
Total: ~38 seconds downtime
```

**Tune for faster failover:**
```yaml
dcs:
  ttl: 15           # shorter lease = faster detection but more false positives
  loop_wait: 5      # check more often
  retry_timeout: 5  # Patroni requires loop_wait + 2 × retry_timeout ≤ ttl
```

With ttl=15, loop_wait=5: ~20s total failover instead of ~38s.

## Synchronous Replication, the Patroni Way

Don't hand-write `synchronous_standby_names` in a Patroni cluster. Let Patroni manage it, so it knows which standby is safe to promote. These are dynamic settings: put them under `bootstrap.dcs` for a new cluster, or change them later with `patronictl edit-config`.

```yaml
synchronous_mode: true          # or quorum (Patroni 4+): ANY n (...) with quorum-aware failover
synchronous_node_count: 1
synchronous_mode_strict: false  # see the tradeoff below
```

What you get, per the Patroni documentation:
- Patroni only promotes a standby that's certain to have every commit already acknowledged to a client. No acknowledged commit is lost in a failover.
- **Non-strict** (the default): if no synchronous standby is available, the primary keeps accepting writes without replicating them. Availability wins, and RPO isn't zero until a standby is back.
- **Strict** (`synchronous_mode_strict: true`): the primary blocks writes until a synchronous standby comes back. Zero RPO wins, availability suffers.
- The `nosync: true` tag stops a node from ever being chosen as synchronous, which is how you steer which site acknowledges commits (5.5).

## Common Patroni Issues

**1. Patroni won't start because PostgreSQL is already running**
```bash
# Stop PostgreSQL first, then start Patroni (Patroni manages PostgreSQL)
pg_ctl stop -D /var/lib/postgresql/16/main
systemctl start patroni
```

**2. Standby stuck in "start failed" state**
```bash
# Check logs
journalctl -u patroni -n 50

# Reinitialize (rebuild standby from scratch)
patronictl -c /etc/patroni/patroni.yml reinit postgres-cluster pg-node2
```

**3. "No space left" during failover**
Replication slot accumulated too much WAL. Set `max_slot_wal_keep_size`.

**4. pg_rewind fails**
```bash
# Check wal_log_hints is on (or that data checksums are enabled)
psql -c "SHOW wal_log_hints;"
# Must be on (requires restart if not already)
```

**5. A new replica refuses to start with a "system ID mismatch"**
Its data directory belongs to a different cluster. On Debian/Ubuntu that's usually the one `apt install postgresql-16` created automatically. Remove it (`pg_dropcluster --stop 16 main`) so Patroni can clone a fresh copy from the leader.
