# 5.6 — Failover Drills & Runbooks

**Phase**: 5 — HA & Failover
**Est. reading time**: 15 min

---

## Why Drills Matter

An HA cluster that has never failed over is an HA cluster that might not fail over when you need it.

Drills:
- Validate the cluster actually works as designed
- Train operators so they're calm during real incidents
- Identify gaps in runbooks
- Verify monitoring alerts fire correctly
- Measure actual RTO (it's often longer than you think)

**Do planned failover drills at least quarterly.**

---

## Drill 1: Planned Switchover (Seconds of Downtime)

Tests normal operation. No data loss expected.

```bash
# Check cluster state before
patronictl -c /etc/patroni/patroni.yml list

# Initiate a planned switchover (Patroni checks the candidate is caught up first)
patronictl -c /etc/patroni/patroni.yml switchover postgres-cluster

# Watch it happen
watch -n 1 "patronictl -c /etc/patroni/patroni.yml list"

# Verify new primary is accepting writes
psql -h 10.0.0.100 -p 5000 -U postgres -c "SELECT pg_is_in_recovery();"
# Should return false

# Verify old primary is now a standby
psql -h 10.0.0.10 -U postgres -c "SELECT pg_is_in_recovery();"
# Should return true
```

**Measure**: Time from the `switchover` command to the new primary accepting writes. Document it.

## Drill 2: Unplanned Failover (Kill Primary)

Tests actual crash behavior. Small data loss possible if async.

```bash
# First, a trap worth seeing once. On the primary, stop only PostgreSQL:
pg_ctl stop -D /var/lib/postgresql/16/main -m immediate
# Patroni is still running and still holds the leader lock, so it simply starts
# PostgreSQL again within a loop or two. No failover: that's Patroni doing its job.

# Now simulate a real crash of the whole node (start the write loop below in
# another terminal first). Best: hard power-off the VM from the hypervisor.
# Next best: kill Patroni and every PostgreSQL process at once (Patroni runs as
# the postgres user in our unit file):
sudo pkill -9 -u postgres

# Watch Patroni detect and fail over (from another node)
watch -n 1 "patronictl -c /etc/patroni/patroni.yml list"

# Expected:
# 1. The old leader disappears from the list (or shows as stopped)
# 2. After the leader key's TTL expires, a standby gets promoted
# 3. New primary starts accepting writes

# Verify application is still working (from application server)
# Run a test write while watching for errors
for i in $(seq 1 100); do
  psql -h 10.0.0.100 -p 5000 -U myapp -d mydb \
    -c "INSERT INTO test_table (value) VALUES ($i);" 2>&1
  sleep 0.5
done

# How many inserts succeeded? How many failed during failover window?
```

**Measure**: 
- Time from kill to new primary accepting writes (actual RTO)
- Number of failed write attempts during failover window

## Drill 3: Network Partition Simulation

Tests Patroni's network partition handling.

```bash
# On primary server: block communication to etcd (simulate network partition)
iptables -A OUTPUT -d 10.0.0.1 -j DROP    # block etcd-A1
iptables -A OUTPUT -d 10.0.0.2 -j DROP    # block etcd-A2
iptables -A OUTPUT -d 10.0.0.3 -j DROP    # block etcd-B1

# Watch: primary should demote itself (can't renew lease)
watch -n 1 "patronictl -c /etc/patroni/patroni.yml list"

# Restore connectivity
iptables -D OUTPUT -d 10.0.0.1 -j DROP
iptables -D OUTPUT -d 10.0.0.2 -j DROP
iptables -D OUTPUT -d 10.0.0.3 -j DROP

# Watch: old primary rejoins as standby
```

## Drill 4: Datacenter Failover

Tests DR procedure.

```bash
# Simulate Site A outage: power off every Site A machine (PostgreSQL, etcd,
# HAProxy). Stopping PostgreSQL alone isn't an outage: Patroni restarts it.

# On Site B: promote pg-node3
# - etcd quorum survives (third site) and pg-node3 was synchronous: automatic
# - etcd quorum survives but pg-node3 was async: Patroni waits for your decision (5.5)
# - no etcd quorum: manual promotion, following 5.5 Option 2 step by step

# Update HAProxy on Site B or update DNS to point to Site B
# Update application connection strings

# Verify Site B is accepting writes
psql -h site-b-vip -U myapp -d mydb -c "SELECT pg_is_in_recovery();"

# Document:
# Time from Site A outage detection to Site B ready: ?
# Data loss (check latest committed timestamp): ?
```

## The Standard Runbook Template

```markdown
# Runbook: PostgreSQL Primary Failover

## Trigger Conditions
- Primary node unreachable for > 2 minutes
- Patroni automated failover occurred (verify alert)
- Application reporting connection errors

## Severity: P1 — Immediate response required

## Contacts
- On-call DBA: [name/phone]
- Backup contact: [name/phone]
- Application lead: [name]

## Diagnostic Steps (2 minutes)
1. Check Patroni status:
   patronictl -c /etc/patroni/patroni.yml list

2. Check if new primary is serving traffic:
   psql -h [VIP] -p 5000 -U postgres -c "SELECT pg_is_in_recovery();"

3. Check HAProxy status:
   curl http://[haproxy]:7000/

4. Check application error rate in monitoring

## If Patroni Auto-Failover Succeeded
1. Verify new primary accepting writes ✓
2. Verify replicas connected to new primary ✓
3. Notify stakeholders: "Automated failover completed, service restored"
4. File incident report
5. Schedule post-mortem within 48 hours

## If Patroni Auto-Failover Failed (Manual Intervention Required)
1. Identify best standby (lowest lag):
   patronictl -c /etc/patroni/patroni.yml list

2. Force failover to specific node:
   patronictl -c /etc/patroni/patroni.yml failover postgres-cluster \
     --candidate [node-name] --force

3. If Patroni can't act (no etcd quorum), promote manually, and only after
   confirming the old primary is down or fenced off from clients:
   systemctl stop patroni        # stops PostgreSQL too
   pg_ctl start -D /var/lib/postgresql/16/main
   pg_ctl promote -D /var/lib/postgresql/16/main

4. Update HAProxy/DNS if needed

5. Verify application traffic restored

## After Failover
1. Old primary: check if recoverable (hardware failure vs crash?)
2. If it may hold commits the new primary never received (async replication), copy its data directory aside *before* touching it
3. Then pg_rewind it (or rebuild it) and rejoin it as a standby
4. Check data loss: SELECT max(created_at) FROM [critical_table];
5. Update monitoring baselines (new primary node name)
6. Verify backups are still running on new primary
7. Update pgBackRest primary connection if needed

## Data Loss Assessment
If data loss occurred:
1. Work out what the old primary committed after the timelines forked (the fork LSN is in the new primary's `pg_wal/<timeline>.history` file; read the old primary's WAL from there with `pg_waldump`)
2. pg_rewind does NOT preserve those transactions: it discards them to make the old primary match the new one. Recover them, if at all, from the copy you set aside before rewinding (start it standalone and extract the rows)
3. Document lost data, notify stakeholders, determine if manual re-entry is needed

## Recovery Complete Checklist
- [ ] New primary accepting writes
- [ ] All standbys replicating to new primary
- [ ] HAProxy routing to correct nodes
- [ ] Application errors resolved
- [ ] Monitoring showing healthy cluster
- [ ] Backups running on new primary
- [ ] Incident report filed
- [ ] Post-mortem scheduled
```

## Post-Failover: Rebuilding the Old Primary as Standby

After a failover, the old primary (pg-node1) needs to become a standby of the new primary (pg-node2).

**If pg_rewind is configured (Patroni handles this automatically):**
```bash
# Patroni will pg_rewind and restart the old primary as standby automatically
# Just start Patroni on pg-node1:
systemctl start patroni
# Watch it rejoin
patronictl -c /etc/patroni/patroni.yml list
```

**If manual rebuild is needed:**
```bash
# On old primary (pg-node1), with Patroni stopped
pg_ctl stop -m fast -D /var/lib/postgresql/16/main     # if it's still running

# Optional but wise: keep a copy in case it holds commits you need (see above)
cp -a /var/lib/postgresql/16/main /var/lib/postgresql/16/main.before-rewind

# Try pg_rewind first (fast)
pg_rewind \
  --target-pgdata=/var/lib/postgresql/16/main \
  --source-server="host=10.0.0.20 port=5432 user=rewind_user dbname=postgres"

# Rewound? Start Patroni: it brings the node up as a replica of the new primary
systemctl start patroni

# pg_rewind failed? Start Patroni anyway and have it rebuild the node from scratch
patronictl -c /etc/patroni/patroni.yml reinit postgres-cluster pg-node1
```
