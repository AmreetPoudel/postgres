# 5.5 — Cross-Datacenter HA Design

**Phase**: 5 — HA & Failover
**Est. reading time**: 20 min

---

## The Challenge

Single-datacenter HA protects against server failures. Cross-datacenter HA protects against entire datacenter failures (power outage, network partition, natural disaster).

But cross-DC adds complexity:
- Higher network latency between datacenters
- Synchronous replication becomes expensive (every commit waits for cross-DC round trip)
- Etcd quorum decisions across datacenters become tricky

---

## Network Latency Reality

Same datacenter: 0.1-1ms round trip
Different buildings / PoPs: 1-5ms round trip
Different cities: 10-100ms round trip
Different continents: 50-300ms round trip

With synchronous replication, EVERY COMMIT waits for this round trip. At 50ms RTT between datacenters: every commit takes at least 50ms extra. This is often unacceptable for OLTP workloads.

---

## Architecture Option 1: Async Cross-DC, Sync Within DC

```
Site A (Primary DC)
  PG Primary
  PG Standby-A1 ← sync replication (LAN: ~1ms)
      ↓
  async replication (~50ms WAN)
      ↓
Site B (DR DC)
  PG Standby-B1
  PG Standby-B2 ← cascades from B1 (cascaded standbys are always async)
```

**Configuration:**
```
# On primary
synchronous_standby_names = 'ANY 1 (standby-a1)'
# Only site A standby is synchronous → zero RPO within Site A
# Site B is async → small data loss if Site A completely fails
```

**Tradeoffs:**
- All commits take ~1ms extra (within-DC sync) → acceptable
- Site A failure: failover to Standby-A1, zero data loss
- Site A total failure (both primary + A1 fail): fail to Site B and lose whatever Site B hadn't received yet: usually milliseconds to seconds, unbounded if the link was degraded

**This is the most common production setup for two-site HA.**

---

## Architecture Option 2: Quorum Across DCs

```
Site A:  PG Primary + PG Standby-A1
Site B:  PG Standby-B1 + PG Standby-B2
Site C:  Arbitrator (etcd only, no PostgreSQL)

synchronous_standby_names = 'ANY 2 (standby-a1, standby-b1, standby-b2)'
```

Every commit must be acknowledged by any 2 of the 3 standbys. Only one of them is in Site A, so every acknowledged commit is also in Site B. You're safe even if Site A disappears, and one standby can be down without blocking commits.

Compare `'ANY 2 (standby-a1, standby-b1)'` with only two standbys: that means "all of them", and losing either one blocks every commit (4.2).

**The catch:** every commit waits for Site B, so commit latency is at least the cross-DC round trip. May not be acceptable.

**When it works:** Sites with fast interconnects (<5ms), and when zero RPO is non-negotiable.

---

## etcd Across Datacenters

etcd quorum decisions must complete across the network. If you spread etcd nodes across DCs:

```
3 etcd nodes:
  etcd-A1 (Site A)
  etcd-A2 (Site A)
  etcd-B1 (Site B)
```

Quorum = 2 of 3. If Site B is unreachable, etcd can still reach quorum (etcd-A1 + etcd-A2). Good.

If Site A is unreachable, only etcd-B1 is available. Quorum fails. etcd is unavailable. Patroni can't function. Database goes read-only or unavailable.

**Solution:** 5 etcd nodes across 3 sites:
```
Site A: etcd-A1, etcd-A2
Site B: etcd-B1, etcd-B2
Site C: etcd-C1 (arbitrator)
```

Loss of any one site: 3-4 nodes remain, quorum achieved.

**The rule behind this:** an etcd cluster survives losing a site only if no single site holds a majority of its members. With two sites, one of them always holds the majority, so automatic failover can only survive losing the *other* site. To survive losing either site, you need a third location, even a small VM in a cloud region, holding a tie-breaker member.

---

## Disaster Recovery vs HA

**HA** (what Patroni does): Automatic, seconds-level failover for node/server failures.

**DR** (Disaster Recovery): Manual or semi-automatic, minutes-to-hours failover for datacenter failures.

For DR, your Site B might be:
- A hot standby (Patroni-managed, can be promoted in minutes)
- A warm standby (not running, needs to be started and promoted)
- A backup restoration (hours, from pgBackRest)

**RPO and RTO for DR depend on your architecture:**

| DR type | RPO | RTO |
|---|---|---|
| Sync hot standby | 0 (if sync to Site B) | ~5 min (manual failover + DNS) |
| Async hot standby | Seconds to minutes of data loss | ~5-10 min |
| Warm standby | Minutes to hours | ~15-30 min |
| Backup restore | Hours | Hours |

## Practical Two-Site Design for Your Setup

Given your goal (2-site sync HA cluster), here's the layout, and what each choice actually guarantees:

```
Site A:
  pg-node1 (Primary, Patroni-managed)
  pg-node2 (Replica, Patroni-managed)
  HAProxy + keepalived (VIP: 10.0.0.100)
  etcd-A1

Site B:
  pg-node3 (Replica, Patroni-managed)
  HAProxy + keepalived (VIP: 10.0.1.100)
  etcd-B1

Site C (a small VM in a third location: another building, or a cloud region):
  etcd-C1 (tie-breaker, no PostgreSQL)

Total etcd: 3 members, one per site → quorum = 2, and any one site can be lost
```

**Why not put the tie-breaker in Site A?** Then Site A holds the etcd majority. Lose Site B and nothing happens; lose Site A and Site B can't form a quorum, so there's no automatic failover at all. Also avoid an even number of members: 4 tolerates one failure, exactly like 3, with one more box to break. If a third location is truly impossible, accept that losing Site A means a manual DR promotion (below).

**Replication:** let Patroni manage it (5.2) instead of writing `synchronous_standby_names` by hand:

```yaml
# patronictl -c /etc/patroni/patroni.yml edit-config
synchronous_mode: true
synchronous_node_count: 1
```

With pg-node2 and pg-node3 both eligible, Patroni picks one synchronous standby, usually pg-node2 (fast LAN). Then:

- **Primary fails, Site A otherwise fine:** automatic failover to pg-node2, zero data loss (Patroni only promotes a standby that has every acknowledged commit)
- **All of Site A fails:** pg-node3 was the *asynchronous* standby, so Patroni will not promote it on its own: it can't be sure pg-node3 has every acknowledged commit. You decide. Accept that the last commits may be lost, turn synchronous mode off with `patronictl edit-config` (that works because Sites B and C still have an etcd quorum), then fail over to pg-node3.

If losing all of Site A must cost zero commits *and* fail over automatically, tag pg-node2 with `nosync: true`. pg-node3 is then the only synchronous candidate, so a Site A loss promotes it automatically with nothing lost. The price: every commit pays the cross-site round trip, and when pg-node3 is down you must choose between non-strict mode (writes continue, unreplicated) and `synchronous_mode_strict` (writes block). Patroni 4's `synchronous_mode: quorum`, with two standbys in Site B, avoids that dilemma.

## Promoting the DR Standby

When Site A is completely unavailable and you need to fail to Site B:

```bash
# On Site B
# Option 1: Patroni-managed (needs an etcd quorum, e.g. Site B + Site C)
patronictl -c /etc/patroni/patroni.yml failover postgres-cluster \
  --candidate pg-node3 \
  --force

# Option 2: Manual, when there's no etcd quorum (no third site).
# First make sure Site A's PostgreSQL really is down or fenced off from clients:
# a second primary is the split-brain from 5.1.
systemctl stop patroni                     # this also stops PostgreSQL on the node
pg_ctl start -D /var/lib/postgresql/16/main
pg_ctl promote -D /var/lib/postgresql/16/main
# Keep Patroni off on this node until you've rebuilt the cluster state in etcd,
# or it will try to turn the node back into a replica.

# After promotion: update application connection strings / DNS
# Point to Site B HAProxy VIP: 10.0.1.100
```

## Documenting Your DR Plan

Write this BEFORE you need it (see Phase 3.5 for runbook template):

1. How to determine if Site A is truly down vs network partition
2. How to promote Site B standby (Patroni command or manual)
3. How to update DNS / load balancer / application connection strings
4. How to verify Site B is working
5. How to rebuild Site A as a standby after it recovers
6. Communication chain (who to call, what to say)

**Test it.** Do a planned DR drill: intentionally take Site A offline and verify Site B takes over correctly.
