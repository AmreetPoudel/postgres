# 5.1 — HA Concepts: Split-Brain, Fencing, Quorum

**Phase**: 5 — HA & Failover
**Est. reading time**: 20 min

---

## What HA Means for PostgreSQL

High Availability means: if the primary PostgreSQL server fails, another server automatically becomes the new primary, and your application continues with minimal downtime.

The hard problems:
- How does the system detect a real failure vs a temporary glitch?
- How does it ensure the old primary doesn't come back as a second primary?
- How does it ensure no data is lost during failover?
- How does the application find the new primary?

---

## Split-Brain: The Worst Failure Mode

**Split-brain** happens when both the old primary and the new primary think they're the primary and accept writes simultaneously.

```
Before failure:
Primary ←── replication ──► Standby

Network partition:
Primary │   network break   │ Standby
   ↓                              ↓
Still writing             Promoted to new primary
                          Also writing
   
Both are accepting writes → data diverges → when network heals, which version is "real"?
```

There's no automatic way to merge diverged databases. You have to pick one and throw away the other's writes. This is data loss.

**This is why HA is hard.** Detecting the difference between "primary is dead" and "we can't reach primary but it's still alive" is fundamentally a hard distributed systems problem.

---

## Fencing: Ensuring the Old Primary Stops

Fencing (also called STONITH — Shoot The Other Node In The Head) is the mechanism that ensures the old primary cannot continue accepting writes after a new primary is promoted.

Methods:
1. **IPMI / iDRAC / iLO**: Remote power off the failed node via server management interface
2. **Power distribution unit (PDU)**: Cut power to the failed node
3. **Shared disk fence**: Revoke the failed node's access to shared storage
4. **Network fence**: Block the failed node from communicating (firewall rules)

**Without fencing, split-brain is possible.** Any HA system that promotes without ensuring the old primary is truly dead is playing with fire.

**Patroni's approach**: Patroni uses a DCS (etcd/Consul/ZooKeeper) as the arbiter. The primary must continuously renew a lease in the DCS. If it can't renew (network partition from DCS), it **demotes itself**. The standby, seeing no active lease, promotes. The old primary cannot write because it demoted itself. No split-brain.

---

## Quorum: Avoiding False Failovers

Quorum means: only take action if a majority of nodes agree on what's happening.

Why it matters: if the standby can't reach the primary, is the primary down, or is the standby's network broken?

```
3-node cluster: Primary + Standby + Arbitrator (etcd)

Standby can't reach Primary.
But Standby CAN reach etcd → etcd says Primary's lease expired.
→ Primary is likely actually down → safe to promote.

vs.

Standby can't reach Primary.
Standby also CAN'T reach etcd → network partition isolated the standby.
→ Primary is likely still running → do NOT promote.
```

**The minimum quorum requirement**: You need at least 3 nodes (primary, standby, arbitrator) to detect failure safely. With only 2 nodes, you cannot distinguish "primary is dead" from "standby's network is broken."

---

## Recovery Time Objective (RTO) vs Recovery Point Objective (RPO)

**RPO**: How much data loss is acceptable?
- RPO = 0: Zero data loss. Requires synchronous replication.
- RPO = 30s: Can lose up to 30 seconds of data. Async replication with monitoring.

**RTO**: How long can the system be unavailable?
- RTO = 30s: Failover completes within 30 seconds.
- RTO = 5min: Failover can take up to 5 minutes.

These drive your HA architecture decisions:

| RPO | RTO | Architecture |
|---|---|---|
| 0 | < 30s | Sync replication + automatic failover (Patroni) |
| ~1s | < 30s | Async replication + automatic failover (Patroni) |
| Minutes | Minutes | Manual failover with monitoring |
| Hours | Hours | Backup restore only |

## What Patroni Provides

Patroni is a template for PostgreSQL HA. It:
- Uses a DCS (Distributed Configuration Store) as the arbiter and configuration store
- Manages promotion, demotion, and standby registration
- Provides a REST API for health checking (used by load balancers)
- Handles configuration management for primary and standbys
- Monitors replication slots
- Integrates with HAProxy/keepalived for application connection routing

**What Patroni does NOT do:**
- Network fencing (you add this separately)
- Load balancing (you add HAProxy/PgBouncer)
- Backup (you add pgBackRest)

## The Components of a Full HA Stack

```
Applications
    ↓
HAProxy (active/passive VIP or load balancing)
    ↓
PgBouncer (connection pooling on each node)
    ↓
PostgreSQL primary (Patroni managed)
    ↓
WAL replication to standbys
    ↓
PostgreSQL standbys (Patroni managed, hot standby for reads)

Patroni on each PostgreSQL node
    ↓
etcd cluster (3+ nodes for quorum)

pgBackRest (backup)
Prometheus + Grafana (monitoring)
```
