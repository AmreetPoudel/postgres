# 2.7 — OS-Level Tuning: Linux Settings for PostgreSQL

**Phase**: 2 — Configuration & Tuning
**Est. reading time**: 20 min

---

## Why OS Tuning Matters

PostgreSQL runs on Linux. Linux makes decisions about memory, I/O scheduling, and disk flushing that directly affect PostgreSQL behavior. The defaults are for general-purpose workloads — not for a database server.

These tunings can make 10-40% difference in performance on a busy server.

---

## Swappiness

```bash
cat /proc/sys/vm/swappiness
# Default: 60
```

`vm.swappiness` controls how aggressively Linux swaps RAM to disk. At 60, Linux will start swapping before memory is actually full.

**For PostgreSQL**: Swapping is catastrophic. If any PostgreSQL memory goes to swap (disk-speed), queries dramatically slow down. PostgreSQL should never swap.

```bash
# Set to 1 (not 0 — 0 can cause OOM issues, 1 means "swap only when desperate")
sysctl -w vm.swappiness=1

# Make permanent
echo 'vm.swappiness = 1' >> /etc/sysctl.d/99-postgresql.conf
sysctl -p /etc/sysctl.d/99-postgresql.conf
```

## Huge Pages

Standard Linux memory pages are 4KB. With 8GB of shared_buffers, PostgreSQL needs to track 2 million page mappings. Tracking all these pages uses a lot of CPU (TLB = Translation Lookaside Buffer pressure).

**Huge pages**: 2MB pages instead of 4KB. 8GB shared_buffers → 4,096 page mappings instead of 2 million. Much less TLB pressure.

**Setting up huge pages:**

```bash
# 1. Calculate how many huge pages you need
# shared_buffers size (bytes) / huge_page_size (bytes) + some overhead
# Example: 8GB / 2MB = 4096 pages, add 10% overhead = 4500

# Check huge page size (usually 2MB on x86)
grep Hugepagesize /proc/meminfo

# 2. Set the kernel parameter
sysctl -w vm.nr_hugepages=4500

# Make permanent
echo 'vm.nr_hugepages = 4500' >> /etc/sysctl.d/99-postgresql.conf

# 3. Tell PostgreSQL to use huge pages
# postgresql.conf:
huge_pages = try    # try to use, fall back if not available
# or
huge_pages = on     # require (PostgreSQL fails to start if not available)
```

**Verify huge pages are being used:**
```bash
grep HugePages /proc/meminfo
# HugePages_Total: 4500    (how many configured)
# HugePages_Free: 300      (unused — should decrease after PostgreSQL starts)
# HugePages_Rsvd: 4200     (reserved by PostgreSQL)
```

**Performance gain**: 5-20% reduction in CPU usage on systems with large `shared_buffers`. More impactful the larger shared_buffers is.

## Transparent Huge Pages (THP) — Disable It

Linux has "Transparent Huge Pages" which tries to automatically use huge pages. For PostgreSQL, THP causes problems:
- THP uses pages that are "transparent" to the application
- Compaction operations can cause periodic latency spikes
- PostgreSQL's own huge page management conflicts with THP

```bash
# Check current setting
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never  ← "always" is bad for PostgreSQL

# Disable THP
echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo never > /sys/kernel/mm/transparent_hugepage/defrag

# Make permanent (varies by distro)
# RHEL/Rocky: /etc/rc.d/rc.local
# Debian: /etc/rc.local or a systemd service

# Systemd service for disabling THP:
cat > /etc/systemd/system/disable-thp.service << 'EOF'
[Unit]
Description=Disable Transparent Huge Pages
DefaultDependencies=false
After=sysinit.target local-fs.target
Before=basic.target

[Service]
Type=oneshot
ExecStart=/bin/sh -c 'echo never > /sys/kernel/mm/transparent_hugepage/enabled'
ExecStart=/bin/sh -c 'echo never > /sys/kernel/mm/transparent_hugepage/defrag'

[Install]
WantedBy=basic.target
EOF

systemctl daemon-reload
systemctl enable disable-thp
systemctl start disable-thp
```

## vm.dirty_bytes / vm.dirty_background_bytes

These control when Linux starts flushing dirty pages to disk.

```bash
cat /proc/sys/vm/dirty_ratio            # default: 20 (20% of RAM)
cat /proc/sys/vm/dirty_background_ratio  # default: 10 (10% of RAM)
```

Default behavior on a 32GB system:
- `dirty_ratio = 20%` → 6.4GB of dirty pages can accumulate before Linux forces a flush
- When forced flush hits: everything stalls while 6.4GB flushes → huge latency spike

PostgreSQL manages its own dirty page writes via checkpoints/bgwriter. The OS dirty page cache should be kept small.

```bash
# Use absolute bytes instead of percentages (more predictable)
sysctl -w vm.dirty_bytes=536870912        # 512MB
sysctl -w vm.dirty_background_bytes=67108864  # 64MB

# Make permanent
echo 'vm.dirty_bytes = 536870912' >> /etc/sysctl.d/99-postgresql.conf
echo 'vm.dirty_background_bytes = 67108864' >> /etc/sysctl.d/99-postgresql.conf
```

With these settings:
- OS starts background flushing at 64MB of dirty pages (smooth, continuous)
- Forces flush at 512MB (prevents huge buildup)
- Much more predictable latency

## I/O Scheduler

Linux has multiple I/O schedulers. Different storage types need different schedulers.

```bash
# Check current scheduler for each block device
cat /sys/block/sda/queue/scheduler
# [mq-deadline] kyber bfq none  ← current is mq-deadline

# For SSD/NVMe: use 'none' (no reordering needed, drive handles it)
echo none > /sys/block/nvme0n1/queue/scheduler

# For HDD: use 'mq-deadline' or 'bfq' (reordering improves sequential performance)
echo mq-deadline > /sys/block/sda/queue/scheduler
```

**For NVMe drives**: `none` is best. The NVMe controller has its own internal queueing that's better than any Linux scheduler.

**Make permanent via udev:**
```bash
cat > /etc/udev/rules.d/60-ioscheduler.rules << 'EOF'
# NVMe drives: no scheduler
ACTION=="add|change", KERNEL=="nvme[0-9]*", ATTR{queue/scheduler}="none"

# SATA/SAS drives: mq-deadline
ACTION=="add|change", KERNEL=="sd[a-z]", ATTR{queue/rotational}=="0", ATTR{queue/scheduler}="mq-deadline"
ACTION=="add|change", KERNEL=="sd[a-z]", ATTR{queue/rotational}=="1", ATTR{queue/scheduler}="mq-deadline"
EOF

udevadm control --reload-rules
```

## File System Settings

**XFS or ext4**: Both are fine for PostgreSQL. XFS has better performance for large files and parallel writes.

**Mount options** (`/etc/fstab`):
```
# For data disks (PostgreSQL data and WAL)
/dev/nvme0n1p1  /var/lib/postgresql  xfs  defaults,noatime,nodiratime  0 2
```

- `noatime`: Don't update access time on every file read. Saves unnecessary writes.
- `nodiratime`: Same for directories.

**DO NOT use `nobarrier`** (removes write barriers that protect data integrity). Disabling barriers can cause data corruption on power failure. The performance gain is minimal on modern hardware.

## Read-Ahead for Sequential Scans

For large sequential scans (full table scans, backups), increasing read-ahead helps Linux prefetch data:

```bash
# Check current read-ahead
blockdev --getra /dev/sda
# Default: 256 (256 × 512 bytes = 128KB)

# Increase for HDD (large sequential reads benefit more from read-ahead)
blockdev --setra 4096 /dev/sda    # 4096 × 512 = 2MB

# For SSD/NVMe: keep at default or smaller (latency is low, prefetch matters less)
```

## Memory Overcommit

```bash
cat /proc/sys/vm/overcommit_memory
# Default: 0 (heuristic — sometimes allows overcommit, sometimes doesn't)
```

PostgreSQL uses `fork()` which requires the OS to promise a copy of the parent's memory to the child, even though the child immediately exec's something else (the child never actually needs it). With overcommit = 0, this can fail on low-memory systems.

```bash
# Allow overcommit (safe for PostgreSQL)
sysctl -w vm.overcommit_memory=2
sysctl -w vm.overcommit_ratio=80    # allow committing up to 80% of RAM + swap

# This means: total virtual memory cannot exceed 80% of RAM + all swap
# PostgreSQL's fork() will succeed; it won't actually use that memory
```

This prevents OOM conditions from fork() while still allowing normal memory allocation.

## Open File Limits

PostgreSQL needs many file descriptors (one per table file, WAL segment, etc.):

```bash
# Check current limit for postgres user
sudo -u postgres bash -c "ulimit -n"
# Default: 1024 (too low for large databases)
```

```bash
# /etc/security/limits.conf
postgres   soft   nofile   65536
postgres   hard   nofile   65536
```

```
# postgresql.conf (set explicitly)
max_files_per_process = 1000    # default is usually fine, but know where to look
```

## NUMA (Non-Uniform Memory Access)

On multi-socket servers, each CPU socket has its own memory. Accessing memory from the "wrong" socket is slower.

```bash
# Check NUMA topology
numactl --hardware
# node 0 cpus: 0-23
# node 1 cpus: 24-47
# node distances:
#   0   1
# 0: 10  21
# 1: 21  10

# Bad (default): interleave PostgreSQL across NUMA nodes
# Better for PostgreSQL: bind to one NUMA node or use interleave
numactl --interleave=all postgres -D $PGDATA
```

Most PostgreSQL deployments on modern hardware work fine without NUMA tuning. But on very large servers (4+ sockets), NUMA awareness can matter. Use `numactl --interleave=all` as a starting point.

## Complete OS Tuning Summary

```bash
# /etc/sysctl.d/99-postgresql.conf
vm.swappiness = 1
vm.dirty_bytes = 536870912
vm.dirty_background_bytes = 67108864
vm.nr_hugepages = 4500             # adjust based on shared_buffers size
vm.overcommit_memory = 2
vm.overcommit_ratio = 80
kernel.shmmax = 17179869184        # 16GB (must be > shared_buffers)
kernel.shmall = 4194304            # in pages: 16GB / 4KB page size

# /etc/security/limits.conf
postgres   soft   nofile   65536
postgres   hard   nofile   65536

# /etc/fstab (PostgreSQL data mount)
noatime,nodiratime

# I/O scheduler (in udev rules)
nvme: none
ssd:  mq-deadline
hdd:  mq-deadline

# THP: disabled
```
