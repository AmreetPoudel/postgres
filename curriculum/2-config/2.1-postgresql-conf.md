## Where It Lives and How It Works

```bash
# Find your postgresql.conf
psql -c "SHOW config_file;"
# Typically: /etc/postgresql/16/main/postgresql.conf  (Debian)
#            /var/lib/pgsql/16/data/postgresql.conf   (RHEL)
```

**Three ways to change config:**

1. Edit `postgresql.conf` directly → reload or restart
2. `ALTER SYSTEM SET param = value;` → writes to `postgresql.auto.conf` (overrides postgresql.conf) → reload or restart
3. `SET param = value;` within a session → affects only that session, lost on disconnect

```bash
# Reload config (no restart, for most parameters)
pg_ctl reload -D $PGDATA
# or
psql -c "SELECT pg_reload_conf();"

# Check if a parameter needs restart
psql -c "SELECT name, setting, pending_restart FROM pg_settings WHERE pending_restart = true;"
```

**Which parameters need restart vs reload:**
```sql
SELECT name, context
FROM pg_settings
WHERE context IN ('postmaster', 'sighup')
ORDER BY context, name;
-- 'postmaster' = requires restart
-- 'sighup' = just reload
-- 'user' = can be set per session
```

## The Most Important Parameters, Category by Category

### Connection Settings

```
listen_addresses = 'localhost'       # default: only localhost
                                     # production: set to your server IP or '*'
                                     # '*' = listen on all interfaces (common)

port = 5432                          # default TCP port

max_connections = 100                # default
                                     # DON'T just set this high blindly
                                     # Every connection = one OS process = ~10MB RAM
                                     # At 500 connections: 5GB RAM just for processes
                                     # Use PgBouncer instead (Phase 2.4)
```

**Rule of thumb for max_connections:**
```
If using PgBouncer: max_connections = 2× cpu_cores (e.g., 100 on a 48-core server)
If NOT using PgBouncer: max_connections = up to 200 (beyond that, use PgBouncer)
```

**superuser_reserved_connections:**
```
superuser_reserved_connections = 3   # reserve 3 connections for superuser
                                     # so you can always log in even if all
                                     # regular connections are taken
```

### Memory Settings

```
shared_buffers = 128MB               # default (tiny!)
                                     # production: 25% of RAM
                                     # 32GB RAM → shared_buffers = 8GB
                                     # Requires restart

work_mem = 4MB                       # default
                                     # per sort/hash operation
                                     # multiply by: connections × sorts per query
                                     # Keep global low, raise per session for heavy queries
                                     # Reload only (but affects new sessions)

maintenance_work_mem = 64MB          # default (too small for large tables)
                                     # for VACUUM, CREATE INDEX, RESTORE
                                     # production: 1GB to 2GB
                                     # Reload

huge_pages = try                     # try to use Linux huge pages (2MB pages)
                                     # 'try' = use if available, fall back if not
                                     # 'on' = require huge pages (fail if not available)
                                     # Helps reduce TLB pressure on very large shared_buffers
                                     # Requires OS tuning (see Phase 2.7)
                                     # Requires restart
```

**Real configuration for a 32GB server:**
```
shared_buffers = 8GB
work_mem = 16MB
maintenance_work_mem = 1GB
effective_cache_size = 24GB
huge_pages = try
```

### WAL Settings

```
wal_level = replica                  # default in modern PostgreSQL
                                     # 'minimal': crash recovery only (don't use with standbys)
                                     # 'replica': streaming replication (use this)
                                     # 'logical': logical replication/decoding
                                     # Requires restart

fsync = on                           # NEVER TURN OFF
                                     # off = data corruption risk on crash
                                     # Requires restart

synchronous_commit = on              # default
                                     # off = async commits (~200ms data loss risk on crash)
                                     # Reload, can be set per session

wal_compression = off                # compress WAL records
                                     # Reduces disk I/O at cost of CPU
                                     # Turn on if disk bandwidth is bottleneck
                                     # Reload

full_page_writes = on                # LEAVE ON
                                     # Protects against torn page writes on crash
                                     # Restart

wal_buffers = -1                     # auto-sized (1/32 of shared_buffers, max 64MB)
                                     # explicitly set to 64MB on high-write systems
                                     # Requires restart
```

---

### Checkpoint Settings

```
checkpoint_timeout = 5min            # default: checkpoint every 5 minutes
                                     # production: 15min to 30min
                                     # Longer = less I/O, longer crash recovery
                                     # Reload

max_wal_size = 1GB                   # default
                                     # checkpoint also triggers if WAL exceeds this
                                     # production: 4GB to 16GB depending on write rate
                                     # Reload

min_wal_size = 80MB                  # minimum WAL files to keep
                                     # Reload

checkpoint_completion_target = 0.9  # spread checkpoint I/O over 90% of interval
                                     # Reload
```

**What happens if max_wal_size is too small:**
- WAL fills up → checkpoint triggers → too frequent checkpoints → I/O spikes
- You can diagnose this: `checkpoints_req >> checkpoints_timed` in pg_stat_bgwriter

---

### Query Planner Settings

```
random_page_cost = 4.0               # default: 4× more expensive than seq I/O
                                     # SSD/NVMe: set to 1.1
                                     # HDD: keep at 4.0
                                     # This is one of the highest-impact changes for SSD users
                                     # Reload

seq_page_cost = 1.0                  # cost unit reference, rarely changed
                                     # Reload

effective_cache_size = 4GB           # default (usually wrong!)
                                     # Set to 75% of RAM — planner assumes this much
                                     # data fits in OS+PG cache combined
                                     # 32GB RAM → effective_cache_size = 24GB
                                     # Does NOT allocate memory, just a hint
                                     # Reload

default_statistics_target = 100      # default statistics depth
                                     # Higher = better plans, slower ANALYZE
                                     # For complex analytics: 200-500
                                     # Reload

enable_partitionwise_join = off       # default off
                                     # Turn on for partitioned table workloads
                                     # Reload

enable_partitionwise_aggregate = off  # same as above
```

### Autovacuum Settings

```
autovacuum = on                      # NEVER TURN OFF
                                     # Reload

autovacuum_max_workers = 3           # concurrent autovacuum workers
                                     # production with many tables: 5-10
                                     # Requires restart

autovacuum_naptime = 1min            # how often launcher checks tables
                                     # reduce to 30s on high-write systems
                                     # Reload

autovacuum_vacuum_threshold = 50     # min dead tuples before triggering
autovacuum_vacuum_scale_factor = 0.2 # 20% of table = trigger
                                     # For large tables, 20% means millions of dead tuples
                                     # Override per table (ALTER TABLE SET autovacuum_...)

autovacuum_analyze_threshold = 50
autovacuum_analyze_scale_factor = 0.1

autovacuum_vacuum_cost_delay = 2ms   # throttle: sleep between work chunks
                                     # reduce to 0ms if autovacuum falls behind
autovacuum_vacuum_cost_limit = 200   # work budget per chunk
                                     # increase to 800 on fast NVMe systems
```

### Logging Settings

```
log_destination = 'stderr'           # where to send logs
                                     # stderr: goes to systemd/journal
                                     # csvlog: CSV format, good for log analysis
                                     # jsonlog: JSON format (PG17+)

logging_collector = on               # collect logs from stderr to files
                                     # required for csvlog/jsonlog
                                     # Requires restart

log_directory = 'log'                # relative to PGDATA, or absolute path
log_filename = 'postgresql-%Y-%m-%d_%H%M%S.log'
log_rotation_age = 1d                # rotate daily
log_rotation_size = 100MB            # also rotate if > 100MB

# What to log:
log_min_duration_statement = 1000    # log queries taking > 1 second (ms)
                                     # production: 200-1000ms
                                     # 0 = log ALL queries (use only for debugging)
                                     # Reload

log_checkpoints = on                 # log checkpoint info (critical for DBA)
log_connections = off                # log all connections (noisy, use PgBouncer logs instead)
log_disconnections = off
log_lock_waits = on                  # log lock waits > deadlock_timeout
log_temp_files = 0                   # log temp files > 0 bytes (log all temp files)
                                     # useful to detect work_mem issues

log_autovacuum_min_duration = 0      # log all autovacuum runs
                                     # set to 250ms to log only slow vacuums
```

**Recommended logging for production:**
```
log_min_duration_statement = 500     # slow query log
log_checkpoints = on
log_lock_waits = on
log_temp_files = 0
log_autovacuum_min_duration = 250
```

### Replication Settings

```
wal_level = replica                  # required for streaming replication

max_wal_senders = 10                 # max standby connections
                                     # at least 2 for each standby
                                     # Requires restart

wal_keep_size = 0                    # extra WAL to keep for standbys catching up
                                     # 0 = only keep what's needed
                                     # set to 1GB if standbys sometimes fall behind
                                     # Reload

hot_standby = on                     # allow read queries on standby
                                     # (default on since PG9.0)
                                     # Requires restart (on standby)

max_replication_slots = 10           # max replication slots
                                     # Requires restart

synchronous_standby_names = ''       # for synchronous replication
                                     # '' = async (default)
                                     # 'standby1' = sync replication to standby1
                                     # See Phase 4
```

### Lock and Timeout Settings

```
deadlock_timeout = 1s                # how long before deadlock detection runs
                                     # lower on high-concurrency systems: 500ms
                                     # Reload

lock_timeout = 0                     # 0 = wait forever (set per-statement for DDL)
                                     # Reload

statement_timeout = 0                # 0 = no limit (set per role for safety)
                                     # Reload

idle_in_transaction_session_timeout = 0  # 0 = no limit
                                         # production: 10min to 30min
                                         # Reload
```

### Performance Tuning: What to Actually Change

**For a fresh server, change in this order:**

1. Memory settings (biggest impact):
```
shared_buffers = 25% of RAM
effective_cache_size = 75% of RAM
maintenance_work_mem = 1-2GB
work_mem = 8-32MB (keep conservative globally)
```

2. WAL and checkpoint:
```
checkpoint_timeout = 15min
max_wal_size = 4GB
checkpoint_completion_target = 0.9
```

3. I/O cost for SSD:
```
random_page_cost = 1.1
seq_page_cost = 1.0
```

4. Autovacuum for busy systems:
```
autovacuum_max_workers = 5
autovacuum_vacuum_cost_limit = 800
autovacuum_vacuum_cost_delay = 2ms
```

5. Logging:
```
log_min_duration_statement = 500
log_checkpoints = on
log_lock_waits = on
log_temp_files = 0
```

6. Connections:
```
max_connections = 100               # with PgBouncer in front
superuser_reserved_connections = 3
```

## Common Mistakes

**1. Setting shared_buffers to 80% of RAM**
You starve the OS page cache. PostgreSQL uses both. On 32GB: `shared_buffers = 8GB`, leave rest for OS.

**2. Not changing effective_cache_size**
Default is 4GB. On a 32GB server this tells the planner only 4GB is cached — it will prefer sequential scans thinking data isn't cached. Set to 24GB.

**3. Setting work_mem too high globally**
`work_mem = 512MB` with 200 connections = potential 300GB RAM use. OOM killer time.

**4. Not setting log_min_duration_statement**
How do you know which queries are slow if you're not logging them?

**5. Turning off autovacuum to "save I/O"**
You will have bloat, stale statistics, and eventually transaction ID wraparound. You've made things worse.

**6. Changing settings without reloading**
Edit postgresql.conf, forget to reload → settings don't take effect, but you think they did.

```sql
-- Always verify your changes are active
SELECT name, setting, unit, source
FROM pg_settings
WHERE name IN ('shared_buffers', 'work_mem', 'checkpoint_timeout', 'max_wal_size');
-- 'source' shows where the value comes from: 'configuration file', 'command line', 'default'
```

## postgresql.auto.conf

When you use `ALTER SYSTEM`, changes go here:
```bash
cat $PGDATA/postgresql.auto.conf
```

`postgresql.auto.conf` always wins over `postgresql.conf` for the same parameter. This trips people up — they change `postgresql.conf` but `postgresql.auto.conf` has a different value.

To remove an ALTER SYSTEM override:
```sql
ALTER SYSTEM RESET shared_buffers;
-- or reset all
ALTER SYSTEM RESET ALL;
```

## pgtune — Starting Point for Config

```bash
# pgtune.leopard.in.ua — web tool
# Or install locally
pip install pgtune
pgtune --type OLTP --cpus 16 --memory 32GB --max-connections 200
```

pgtune gives you a starting point. It's not production-ready tuning — it doesn't know your workload, disk type, or query patterns. Treat it as a baseline, then measure and adjust.
