# 2.6 — Checkpoint and WAL: Tuning Write Performance

**Phase**: 2 — Configuration & Tuning
**Est. reading time**: 20 min

---

## Understanding Write Performance in PostgreSQL

On every commit:
1. WAL record written to WAL buffers (RAM)
2. The committing backend flushes WAL to `pg_wal/` and waits for the fsync (this is the bottleneck for commit latency; sessions committing at the same moment share one flush)
3. Dirty pages stay in shared_buffers (no disk write on commit)
4. Eventually: checkpointer flushes dirty pages to data files

The disk writes for commits (WAL) and the disk writes for checkpoints (data files) must be tuned separately because they have different patterns:
- **WAL writes**: Sequential, small, happen on every commit. Latency matters.
- **Checkpoint writes**: Potentially large bursts of random I/O. Throughput matters.

## WAL Configuration

```
wal_level = replica               # replica or logical; minimal only if no standby
fsync = on                        # NEVER disable
synchronous_commit = on           # can set to 'off' for async commits
full_page_writes = on             # protect against torn pages; leave on
wal_compression = off             # turn on to reduce WAL size if bandwidth is bottleneck
                                   # compresses full-page images; PG15+ accepts lz4 or zstd,
                                   # which cost less CPU than 'on' (pglz)

wal_buffers = -1                  # auto = 1/32 of shared_buffers, capped at 16MB
                                   # explicitly set 64MB on high-commit-rate systems

wal_writer_delay = 200ms          # how often WAL writer flushes
wal_writer_flush_after = 1MB      # also flush if this much WAL accumulated
```

**wal_sync_method choices:**
```
wal_sync_method = fdatasync      # Linux default (good)
                                  # fdatasync: flushes data, skips metadata update
                                  # faster than fsync which also flushes metadata
                                  # both are safe

# On very fast NVMe with battery-backed write cache:
wal_sync_method = open_sync      # can be faster on some Linux/NVMe combinations
                                  # test it, don't assume
```

## Checkpoint Configuration

```
checkpoint_timeout = 5min         # default (too short for most systems)
                                   # production: 15-30 min
                                   # longer = less frequent I/O = better performance
                                   # longer = more WAL to replay on crash

max_wal_size = 1GB                # default (too small for busy systems)
                                   # checkpoint triggers when WAL reaches this
                                   # production: 4-16GB depending on write rate
                                   # if checkpoints_req >> checkpoints_timed → increase

min_wal_size = 80MB               # minimum WAL space to keep
                                   # increase if WAL creation/deletion cycles are frequent
                                   # 1GB minimum on busy systems

checkpoint_completion_target = 0.9 # spread checkpoint I/O over 90% of interval
                                    # always leave at 0.9 (default)
```

**The checkpoint_timeout vs max_wal_size tradeoff:**

With `checkpoint_timeout = 30min, max_wal_size = 4GB`:
- On a quiet system: checkpoint every 30 minutes (time-based)
- On a busy write system: checkpoint when 4GB WAL accumulates (size-based)
- Worst case, crash recovery replays up to about `max_wal_size` of WAL (here ~4GB): recovery time depends on WAL volume, not on minutes

On very high-write systems (100MB/s+ WAL), `max_wal_size = 16GB` might be needed to avoid excessive checkpoints.

## Diagnosing Checkpoint Issues

```sql
SELECT
    checkpoints_timed,
    checkpoints_req,
    round(checkpoints_req::numeric / nullif(checkpoints_timed + checkpoints_req, 0) * 100, 1) AS pct_req,
    checkpoint_write_time,
    checkpoint_sync_time,
    buffers_checkpoint,
    buffers_clean,
    buffers_backend,      -- should be a small share of all writes
    maxwritten_clean      -- bgwriter stopped due to maxpages limit
FROM pg_stat_bgwriter;
```

**Interpretation:**

| Symptom | Diagnosis | Fix |
|---|---|---|
| `checkpoints_req` >> `checkpoints_timed` | WAL filling up before timeout | Increase `max_wal_size` |
| `buffers_backend` is a large share of writes | Backends writing dirty pages themselves (latency spikes) | More aggressive bgwriter, bigger shared_buffers |
| Long `sync=` times in the `log_checkpoints` lines | Storage can't absorb the fsyncs at the end of each checkpoint | Check disk latency; smooth writeback (`checkpoint_flush_after`, OS dirty settings in 2.7) |
| `maxwritten_clean` > 0 | bgwriter hitting its max pages limit | Increase `bgwriter_lru_maxpages` |

`checkpoint_write_time` is cumulative and *meant* to be large: with `checkpoint_completion_target = 0.9`, writes are deliberately spread across most of the interval. Don't alert on it.

## bgwriter Tuning

```
bgwriter_delay = 200ms               # how often bgwriter wakes up
bgwriter_lru_maxpages = 100          # max pages to write per round
bgwriter_lru_multiplier = 2.0        # aggressiveness factor
bgwriter_flush_after = 512kB         # force flush after this much writing
```

**When to tune bgwriter:**
- `buffers_backend` growing faster than `buffers_clean` → bgwriter not cleaning pages fast enough
- Checkpoint I/O spikes → too many dirty pages accumulating

```
bgwriter_lru_maxpages = 200          # double the default
bgwriter_delay = 100ms               # wake up more often
```

## WAL Archiving Configuration

```
archive_mode = on                    # enable archiving
                                     # Requires restart

archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'
                                     # The 'test ! -f' prevents overwriting
                                     # Always verify %f doesn't exist before writing

archive_timeout = 300                # force a WAL segment switch after 300s if any WAL
                                     # was written since the last switch (an idle server
                                     # doesn't switch). Caps how much recent data a PITR
                                     # could lose; each switch archives a full 16MB file
```

**Better archive commands:**
```bash
# Using pgBackRest
archive_command = 'pgbackrest --stanza=main archive-push %p'

# Using WAL-G to S3
archive_command = 'wal-g wal-push %p'

# Simple copy with verification
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f && sync'
```

**Monitoring archiving:**
```sql
SELECT
    archived_count,
    last_archived_wal,
    now() - last_archived_time AS since_archived,
    failed_count,
    last_failed_wal,
    last_failed_time
FROM pg_stat_archiver;
```

## WAL for Replication

```
max_wal_senders = 10               # max standby + backup connections
                                    # Requires restart

wal_keep_size = 0                  # extra WAL to keep for standbys to catch up
                                    # 0 = only what's needed for checkpoints
                                    # Set to 1GB if standbys frequently lag

recovery_min_apply_delay = 0       # on standby: delay before applying WAL
                                    # useful for a "delayed standby" for accidental deletion protection
                                    # e.g., '1h' = standby is always 1 hour behind
```

**Replication slots and WAL retention** (covered in Phase 4.3, but note here):
Replication slots automatically hold WAL until the standby has consumed it. This prevents WAL from being deleted while the standby is behind. But a dead/stuck standby with a slot will hold WAL forever. Monitor:
```sql
SELECT slot_name, pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS lag_bytes
FROM pg_replication_slots;
```

If `lag_bytes` is growing for a slot whose standby is gone: drop the slot.

## commit_delay — Batching Commits

```
commit_delay = 0                   # microseconds to delay commit
commit_siblings = 5                # only delay if this many transactions are active
```

If non-zero: PostgreSQL waits `commit_delay` microseconds before flushing WAL, hoping more transactions will commit together and share one disk flush. This is a form of group commit.

**When useful**: High-throughput OLTP with many small commits. Batching them saves I/O.
**Risk**: Adds latency to each commit. Only use if you've measured that WAL fsync is your bottleneck.

Most systems: leave at 0. Modern NVMe makes this irrelevant.

## Full Configuration for a Write-Heavy System

```
# WAL
wal_level = replica
fsync = on
synchronous_commit = on
full_page_writes = on
wal_compression = lz4              # PG15+ ('on' means pglz); worth it on write-heavy systems
wal_buffers = 64MB

# Checkpoints
checkpoint_timeout = 30min
max_wal_size = 8GB
min_wal_size = 2GB
checkpoint_completion_target = 0.9

# bgwriter
bgwriter_delay = 100ms
bgwriter_lru_maxpages = 200
bgwriter_flush_after = 512kB

# Archiving (if enabled)
archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'
archive_timeout = 300
```

## What Happens If You Add SSDs But Don't Retune

**Old config (for HDD):**
```
random_page_cost = 4.0
checkpoint_timeout = 5min
max_wal_size = 1GB
```

**With NVMe SSDs:**
- Checkpoints run every 5 minutes regardless (often unnecessary — disk is fast enough)
- Planner still thinks random I/O is 4× more expensive (avoids indexes it should use)
- WAL fills 1GB quickly on busy system → too-frequent checkpoints

**Retune for NVMe:**
```
random_page_cost = 1.1
checkpoint_timeout = 30min
max_wal_size = 8GB
```

Queries start using indexes more. Checkpoints are less frequent. Commit rate improves.
