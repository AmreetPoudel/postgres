# 2.4 — PgBouncer: Connection Pooling

**Phase**: 2 — Configuration & Tuning
**Est. reading time**: 25 min

---

## The Problem

Every PostgreSQL connection = one OS process = ~10MB RAM + OS scheduling overhead.

Your app has 500 microservice instances. Each keeps 5 connections open. That's 2,500 PostgreSQL processes. At 10MB each = 25GB RAM just for connection overhead. Your queries haven't even started yet.

PostgreSQL was designed for tens to low hundreds of real connections. Beyond that, you need a connection pool in front.

---

## What PgBouncer Does

```
2500 app connections
       ↓
   [PgBouncer]
  maintains small pool
  e.g., 100 real connections
       ↓
  PostgreSQL (100 backends)
```

PgBouncer acts as a proxy. App connections talk to PgBouncer. PgBouncer multiplexes them across a small pool of real PostgreSQL connections.

---

## Pooling Modes

**Session pooling** (safest, default):
- One PostgreSQL connection is assigned to a client for the entire session
- Connection returned to pool when client disconnects
- Not much better than direct connections unless clients frequently connect/disconnect

**Transaction pooling** (what you actually want for most apps):
- PostgreSQL connection assigned for the duration of ONE transaction
- Returned to pool after COMMIT/ROLLBACK
- 2500 app connections can share 100 PostgreSQL connections if they're not all in a transaction simultaneously
- **Limitation**: session state such as `SET` variables, session advisory locks, `LISTEN` and `WITH HOLD` cursors doesn't survive across transactions. Protocol-level prepared statements work since PgBouncer 1.21 (see below); SQL-level `PREPARE` still doesn't

**Statement pooling** (avoid):
- Connection returned after each individual statement
- Multi-statement transactions are not allowed at all

**Choose transaction pooling** unless your app needs features that require session pooling.

## Installation and Config

```bash
# Install
apt install pgbouncer    # Debian/Ubuntu
yum install pgbouncer    # RHEL/Rocky

# Config file
/etc/pgbouncer/pgbouncer.ini
```

**pgbouncer.ini:**
```ini
[databases]
# Format: alias = host=... port=... dbname=...
mydb = host=127.0.0.1 port=5432 dbname=mydb
# Wildcard: any database name passed through to PostgreSQL
* = host=127.0.0.1 port=5432

[pgbouncer]
listen_addr = *
listen_port = 6432              # PgBouncer listens here (apps connect here)
auth_type = scram-sha-256       # or md5
auth_file = /etc/pgbouncer/userlist.txt

pool_mode = transaction         # transaction pooling

# Pool size per database/user combination
default_pool_size = 25          # 25 real connections per db/user combo
max_client_conn = 2000          # max app connections to PgBouncer

# Safety: how long to wait for a free connection
query_wait_timeout = 120        # after 120s of waiting: client gets error

# Session cleanup when a server connection goes back to the pool. Used only in
# session pooling; transaction pooling skips it (unless server_reset_query_always = 1)
server_reset_query = DISCARD ALL

# Protocol-level prepared statements in transaction pooling
# (PgBouncer 1.21+; 1.24 made 200 the default)
max_prepared_statements = 200

# Logging
log_connections = 0
log_disconnections = 0
log_pooler_errors = 1
stats_period = 60

# Admin access
admin_users = postgres
stats_users = monitoring
```

**userlist.txt** (stores passwords for PgBouncer to authenticate clients):
```
"myapp" "SCRAM-SHA-256$..."
"monitoring" "SCRAM-SHA-256$..."
```

Generate the SCRAM hash:
```bash
# Connect to PostgreSQL and get the stored SCRAM hash
psql -c "SELECT rolname, rolpassword FROM pg_authid WHERE rolname = 'myapp';"
# Copy the 'SCRAM-SHA-256$...' value into userlist.txt
```

Or use auth_query (more convenient — PgBouncer asks PostgreSQL for the password hash). Only superusers can read `pg_shadow`, so give PgBouncer a narrow SECURITY DEFINER function instead of a superuser login:
```ini
auth_user = pgbouncer_auth
auth_query = SELECT usename, passwd FROM pgbouncer.get_auth($1)
```

```sql
-- Run as a superuser, in every database PgBouncer connects to
CREATE ROLE pgbouncer_auth LOGIN PASSWORD 'strongpassword';
CREATE SCHEMA pgbouncer;
GRANT USAGE ON SCHEMA pgbouncer TO pgbouncer_auth;

CREATE FUNCTION pgbouncer.get_auth(p_usename text)
RETURNS TABLE (usename name, passwd text)
LANGUAGE sql SECURITY DEFINER SET search_path = pg_catalog AS $$
    SELECT usename, passwd FROM pg_catalog.pg_shadow WHERE usename = p_usename;
$$;

REVOKE ALL ON FUNCTION pgbouncer.get_auth(text) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION pgbouncer.get_auth(text) TO pgbouncer_auth;
```

`pgbouncer_auth` itself still needs an entry in `auth_file`, so PgBouncer can log in as it.

## Starting PgBouncer

```bash
systemctl enable pgbouncer
systemctl start pgbouncer

# Check status
systemctl status pgbouncer

# PgBouncer admin console (connect to the pgbouncer "database")
psql -h 127.0.0.1 -p 6432 -U postgres pgbouncer
SHOW POOLS;
SHOW CLIENTS;
SHOW SERVERS;
SHOW STATS;
```

**Key SHOW POOLS output:**
```
database | user | cl_active | cl_waiting | sv_active | sv_idle | sv_used | maxwait
mydb     | myapp|       80  |         3  |       25  |       0 |       0 |       2
```

- `cl_active`: app connections actively using a DB connection
- `cl_waiting`: app connections waiting for a free pool slot (danger if > 0 for long)
- `sv_active`: real PostgreSQL connections in use
- `sv_idle`: real PostgreSQL connections idle in pool
- `maxwait`: longest wait time in seconds (should be near 0)

## Application Configuration

Your app should connect to PgBouncer, not directly to PostgreSQL:

```
# Before PgBouncer
host=db-server port=5432

# After PgBouncer
host=db-server port=6432    # PgBouncer port
```

**In PostgreSQL's pg_hba.conf** — restrict direct connections to PgBouncer's server IP only:
```
# Only PgBouncer server can connect directly
host  all  all  127.0.0.1/32  scram-sha-256
# (keep your replication, monitoring and DBA rules above this line)
# Block everything else
host  all  all  0.0.0.0/0     reject
```

## Transaction Pooling Limitations

When using transaction pooling, these don't work across transactions:
- `SET` parameter values (worse than lost: they stay on the server connection and leak to whichever client gets it next; use `SET LOCAL` inside a transaction)
- SQL-level `PREPARE` / `EXECUTE`
- `LISTEN` (session-level; `NOTIFY` itself is fine)
- Session-level advisory locks (`pg_advisory_lock`; the `_xact_` variants are fine)
- `WITH HOLD` cursors
- `\set` in psql (client-side, fine)

**Prepared statements:** since PgBouncer 1.21, protocol-level prepared statements (what the JDBC driver, Npgsql, asyncpg and friends use) work in transaction pooling when `max_prepared_statements` is non-zero. PgBouncer tracks them and re-prepares them on whichever server connection a client lands on. On older PgBouncer versions, switch prepared statements off in the driver instead (for example `prepareThreshold=0` for JDBC).

Unrelated but often needed: the JDBC driver sends `extra_float_digits` at connection time, which PgBouncer rejects unless told to ignore it:
```ini
# pgbouncer.ini
ignore_startup_parameters = extra_float_digits
```

## Pool Sizing

```
default_pool_size = ?
```

**Rule of thumb:**
```
default_pool_size ≈ num_cpu_cores × 2
```

On a 16-core server: `default_pool_size = 32`

Why not more? At some point, more PostgreSQL connections means more context switching, more lock contention, more overhead. Diminishing returns after 2-4× CPU count.

**Too small pool**: clients wait (`cl_waiting` grows, `maxwait` rises)
**Too large pool**: PostgreSQL slows due to contention, no benefit over smaller pool

## Monitoring PgBouncer

```sql
-- Connect to admin console
psql -h 127.0.0.1 -p 6432 -U postgres pgbouncer

SHOW POOLS;       -- pool status per db/user
SHOW CLIENTS;     -- connected clients
SHOW SERVERS;     -- backend PostgreSQL connections
SHOW STATS;       -- queries/second, data rates
SHOW DATABASES;   -- configured databases
```

**Key metrics to alert on:**
- `cl_waiting > 0` for more than a few seconds → pool too small or PostgreSQL too slow
- `maxwait > 5s` → serious problem — clients timing out
- `sv_idle` always 0 → all connections permanently in use → increase pool size

## PgBouncer vs PgPool-II

| Feature | PgBouncer | PgPool-II |
|---|---|---|
| Connection pooling | Excellent | Good |
| Load balancing reads across replicas | Basic: round-robin across the hosts listed for one database entry, no read/write split | Yes |
| Query routing | No | Yes |
| Complexity | Simple | Complex |
| Performance overhead | Very low | Higher |
| Recommended for | Pooling (most cases) | Complex HA setups |

For pure connection pooling: PgBouncer. For query routing + pooling: PgPool-II (but PgBouncer + HAProxy is often simpler and better).
