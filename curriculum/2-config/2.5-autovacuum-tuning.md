# 2.5 — Autovacuum Tuning: Don't Let It Fall Behind

**Phase**: 2 — Configuration & Tuning
**Est. reading time**: 20 min

---

## Why This Phase Exists Separately

Phase 1.7 explained what autovacuum does. This phase is about making it actually keep up with your workload.

Default autovacuum settings are conservative — designed for a small server with light traffic. On production systems with large tables and high write rates, defaults mean:
- Millions of dead tuples pile up before vacuum triggers
- Statistics go stale
- Bloat accumulates
- Eventually: emergency situations

---

## How Autovacuum Decides to Run

For VACUUM:
```
trigger when: n_dead_tup > autovacuum_vacuum_threshold + (autovacuum_vacuum_scale_factor × n_live_tup)

default:
autovacuum_vacuum_threshold = 50       # absolute floor
autovacuum_vacuum_scale_factor = 0.2   # 20% of live rows
```

**The problem on large tables:**

Table with 50 million rows:
```
threshold = 50 + (0.2 × 50,000,000) = 10,000,050 dead tuples
```

You need 10 million dead tuples before autovacuum even starts. Meanwhile, you're doing 100,000 UPDATEs/minute. That's 10 minutes of bloat accumulation.

**Fix: Per-table settings for large hot tables:**
```sql
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.01,   -- trigger at 1% = 500,000 dead tuples
    autovacuum_vacuum_threshold = 10000      -- or 10,000 minimum
);

-- More aggressive for very hot tables:
ALTER TABLE events SET (
    autovacuum_vacuum_scale_factor = 0.005,  -- 0.5%
    autovacuum_vacuum_threshold = 5000,
    autovacuum_analyze_scale_factor = 0.005,
    autovacuum_analyze_threshold = 5000
);
```

Same logic for ANALYZE:
```sql
ALTER TABLE orders SET (
    autovacuum_analyze_scale_factor = 0.01,
    autovacuum_analyze_threshold = 5000
);
```

## The Worker Limit Problem

```
autovacuum_max_workers = 3    # default
```

If you have 50 tables all needing vacuum simultaneously, only 3 can be vacuumed at once. The rest queue. If vacuum falls behind, everything mentioned in Phase 1.7 happens.

**On systems with many tables:**
```
autovacuum_max_workers = 6     # or even 10 on large servers
```

Each worker uses `autovacuum_work_mem` (or `maintenance_work_mem` if set to -1) RAM. On a server with 32GB RAM and 1GB maintenance_work_mem, 6 workers = 6GB just for autovacuum RAM. Budget for it.

---

## The Cost Throttle

Autovacuum is deliberately throttled to not impact production queries:

```
autovacuum_vacuum_cost_delay = 2ms     # sleep this long between work chunks
autovacuum_vacuum_cost_limit = 200     # how much work per chunk

# Work costs:
vacuum_cost_page_hit = 1              # reading a cached page
vacuum_cost_page_miss = 10            # reading from disk
vacuum_cost_page_dirty = 20           # writing a modified page
```

At the defaults:
- If all pages are cached: 200/1 = 200 pages per chunk, 2ms sleep
  → effective rate: 100,000 pages/second
- If pages require disk reads: 200/10 = 20 pages per chunk, 2ms sleep
  → effective rate: 10,000 pages/second
- If writing dirty pages: 200/20 = 10 pages per chunk, 2ms sleep
  → effective rate: 5,000 pages/second

**On NVMe where disk reads are fast**: the throttle is overly conservative. Your vacuum can keep up with a higher limit:

```
autovacuum_vacuum_cost_limit = 800     # 4× more aggressive
autovacuum_vacuum_cost_delay = 2ms     # or reduce to 1ms
```

Per table override for the most critical tables:
```sql
ALTER TABLE orders SET (
    autovacuum_vacuum_cost_delay = 0,       -- no sleep (aggressive)
    autovacuum_vacuum_cost_limit = 1000
);
```

## The Check Interval

```
autovacuum_naptime = 1min    # how often the launcher wakes up to check all tables
```

On a busy system where tables can go stale quickly:
```
autovacuum_naptime = 30s     # check twice as often
```

## Global Settings for a High-Write Server

This is a starting point for a 32GB server with heavy writes:

```
# postgresql.conf
autovacuum = on
autovacuum_max_workers = 6
autovacuum_naptime = 30s

autovacuum_vacuum_threshold = 50
autovacuum_vacuum_scale_factor = 0.02    # 2% (down from 20%)
autovacuum_analyze_threshold = 50
autovacuum_analyze_scale_factor = 0.01   # 1%

autovacuum_vacuum_cost_delay = 2ms
autovacuum_vacuum_cost_limit = 800

autovacuum_work_mem = -1                 # use maintenance_work_mem
maintenance_work_mem = 1GB
```

## Monitoring: Is Autovacuum Keeping Up?

```sql
-- Tables with most dead tuples (autovacuum falling behind?)
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    round(n_dead_tup::numeric / nullif(n_live_tup + n_dead_tup, 0) * 100, 1) AS dead_pct,
    last_autovacuum,
    now() - last_autovacuum AS since_vacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;

-- Is autovacuum running? What is it working on?
SELECT pid, now() - query_start AS duration, query
FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker';

-- Transaction ID age across databases (wraparound risk)
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
-- Alert at: > 500,000,000
-- Emergency at: > 1,500,000,000

-- Per-table freeze age
SELECT relname, age(relfrozenxid) AS xid_age
FROM pg_class
WHERE relkind = 'r'
ORDER BY age(relfrozenxid) DESC
LIMIT 20;
```

## The Autovacuum Log

To see autovacuum decisions in the log:

```
# postgresql.conf
log_autovacuum_min_duration = 0      # log ALL autovacuum runs
# or
log_autovacuum_min_duration = 250    # log only runs taking > 250ms
```

Sample log line:
```
automatic vacuum of table "mydb.public.orders": index scans: 1
  pages: 0 removed, 450 remain, 0 skipped due to pins, 0 skipped frozen
  tuples: 15230 removed, 49680 remain, 0 are dead but not yet removable
  removable cutoff: 7851234, which was 42 transaction(s) ago
  new relfrozenxid: 7851193, which is 41 transaction(s) ahead of previous
  index scan needed: 7 pages from table (1.56% of total) had 15232 dead item identifiers removed
  avg read rate: 45.123 MB/s, avg write rate: 1.234 MB/s
  buffer usage: 5123 hits, 234 misses, 189 dirtied
  WAL usage: 1234 records, 123 full page images, 456789 bytes
  system usage: CPU: user: 1.23 s, system: 0.12 s, elapsed: 4.56 s
```

Key things to read:
- `tuples removed`: how much dead tuples it cleaned
- `avg read rate` / `avg write rate`: I/O load from this vacuum
- `elapsed`: how long it took

## Vacuum Freeze — Proactive Wraparound Prevention

```
autovacuum_freeze_max_age = 200000000    # 200M transactions
```

When a table's `relfrozenxid` age exceeds this, autovacuum switches to "aggressive freeze mode" — ignores visibility map, scans every page to freeze old transactions. This is more I/O intensive.

**To proactively freeze before it becomes urgent:**
```sql
-- Freeze a specific table
VACUUM (FREEZE, ANALYZE, VERBOSE) orders;

-- Freeze entire database
vacuumdb -d mydb --freeze --analyze --all
```

**Set aggressive freeze age lower on high-write systems** so autovacuum deals with small batches proactively instead of large emergency batches:
```
autovacuum_freeze_max_age = 100000000    # 100M (freeze twice as often but less at once)
```

## When to Run Manual VACUUM

Autovacuum handles routine maintenance. Run manual VACUUM for:

1. **After a large bulk DELETE**: autovacuum threshold might not trigger quickly enough
```sql
DELETE FROM logs WHERE created_at < now() - interval '1 year';
VACUUM ANALYZE logs;
```

2. **Before a large COPY/INSERT**: Update statistics first so planner makes good decisions
```sql
VACUUM ANALYZE target_table;
COPY target_table FROM '/data/import.csv';
VACUUM ANALYZE target_table;
```

3. **Emergency wraparound prevention**:
```sql
VACUUM FREEZE mydb;
```

4. **After pg_restore**: Restore skips statistics — always ANALYZE after restore
```bash
vacuumdb -d mydb --analyze-only
```

## Why Your Autovacuum Might Not Be Running

**1. Long-running transaction blocking vacuum**
Autovacuum can't clean dead tuples that might be visible to old transactions.

```sql
-- Find transactions older than 1 hour
SELECT pid, now() - xact_start AS age, state, query
FROM pg_stat_activity
WHERE xact_start < now() - interval '1 hour'
ORDER BY age DESC;
```

**2. Table being locked by DDL**
Autovacuum backs off if it can't get the lock quickly.

**3. Too few workers (autovacuum_max_workers)**
All workers are busy with other tables.

**4. Cost throttle too aggressive**
Workers finish too slowly relative to write rate.
