# 2.2 — pg_hba.conf: Who Can Connect and How

**Phase**: 2 — Configuration & Tuning
**Est. reading time**: 20 min

---

## What pg_hba.conf Does

Every connection to PostgreSQL goes through pg_hba.conf. Even if the password is correct, if pg_hba.conf says no — the connection is rejected.

HBA = Host-Based Authentication.

```bash
# Find it
psql -c "SHOW hba_file;"
# Typically: /etc/postgresql/16/main/pg_hba.conf
```

**Reload after changes (no restart needed):**
```bash
pg_ctl reload -D $PGDATA
# or
psql -c "SELECT pg_reload_conf();"
```

---

## File Format

Each line is a rule. PostgreSQL reads rules top-to-bottom and uses the FIRST matching rule:

```
TYPE    DATABASE    USER    ADDRESS         METHOD         OPTIONS
local   all         all                     trust
host    all         all     127.0.0.1/32    md5
host    mydb        myapp   10.0.0.0/24     scram-sha-256
```

**TYPE**: where the connection comes from

| Type | Meaning |
|---|---|
| `local` | Unix domain socket (same server, no network) |
| `host` | TCP/IP (with or without SSL) |
| `hostssl` | TCP/IP, SSL required |
| `hostnossl` | TCP/IP, SSL must NOT be used |
| `hostgssenc` | TCP/IP with GSSAPI encryption |
| `hostnogssenc` | TCP/IP, GSSAPI encryption must NOT be used |

**DATABASE**: which database this rule applies to

| Value | Meaning |
|---|---|
| `all` | All databases |
| `mydb` | Specific database |
| `sameuser` | User must connect to a DB with the same name as their role |
| `@filename` | Read database list from file |
| `replication` | Replication connections (not a real database) |

**USER**: which roles this rule applies to

| Value | Meaning |
|---|---|
| `all` | All users |
| `myuser` | Specific user |
| `+myrole` | Any user who is a member of myrole |
| `@filename` | Read user list from file |

**ADDRESS**: source IP address (only for host* types)

| Value | Meaning |
|---|---|
| `127.0.0.1/32` | Specific IPv4 address |
| `10.0.0.0/24` | Subnet (CIDR notation) |
| `::1/128` | IPv6 localhost |
| `0.0.0.0/0` | All IPv4 addresses (dangerous) |
| `samenet` | Same subnet as server |

**METHOD**: how to authenticate

| Method | Security | When to use |
|---|---|---|
| `trust` | None — no password | ONLY for local Unix socket superuser access |
| `reject` | Always deny | Block specific users/IPs |
| `md5` | MD5 hashed password | Legacy, avoid for new setups |
| `scram-sha-256` | Strong hashed password | Default choice for all new setups |
| `password` | Plaintext password | Never use |
| `peer` | Match OS username to PG username | Unix socket local connections |
| `ident` | Like peer but over TCP | Legacy, avoid |
| `ldap` | LDAP authentication | Enterprise setups |
| `cert` | TLS client certificate | Very high security |
| `gss` | Kerberos/GSSAPI | Enterprise/AD environments |

## A Secure Production pg_hba.conf

```
# TYPE  DATABASE        USER            ADDRESS                 METHOD

# Unix socket: OS user postgres → role postgres, no password (peer)
local   all             postgres                                peer

# Unix socket: application users → scram
local   all             all                                     scram-sha-256

# Local IPv4 loopback
host    all             all             127.0.0.1/32            scram-sha-256

# Local IPv6 loopback
host    all             all             ::1/128                 scram-sha-256

# Application servers (specific subnet)
host    mydb            myapp           10.0.1.0/24             scram-sha-256

# Read replicas (for streaming replication)
host    replication     replicator      10.0.0.0/24             scram-sha-256

# Monitoring user (specific IP of monitoring server)
host    all             monitoring      10.0.0.50/32            scram-sha-256

# DBA access from office VPN only
host    all             dba_team        10.8.0.0/16             scram-sha-256

# Reject everything else
host    all             all             0.0.0.0/0               reject
```

## scram-sha-256 vs md5

**Always use `scram-sha-256` for new setups.**

`md5` stores and transmits password hashes that can be attacked offline. `scram-sha-256` uses a challenge-response protocol — even if someone intercepts the authentication, they can't replay it.

**Migrating from md5 to scram-sha-256:**
```sql
-- Check current password encryption
SHOW password_encryption;

-- Set to scram in postgresql.conf
-- password_encryption = scram-sha-256

-- After reload, NEW passwords are stored as SCRAM. Existing md5 hashes
-- stay md5 until each password is set again:
\password myuser
-- or
ALTER USER myuser PASSWORD 'newpassword';
-- Now stored as scram-sha-256

-- Which stored password format does each user have? (prints only the prefix)
SELECT usename, left(passwd, 14) AS hash_prefix FROM pg_shadow WHERE passwd IS NOT NULL;
-- 'md5...' = old md5 hash
-- 'SCRAM-SHA-256$...' = new scram hash
```

**Order matters.** A pg_hba.conf rule with method `md5` accepts both kinds of stored password (it switches to SCRAM automatically when the stored hash is SCRAM). A rule with `scram-sha-256` rejects users whose stored password is still md5. So: set `password_encryption = scram-sha-256`, keep `md5` in pg_hba.conf while everyone resets their password, check that no md5 hashes remain, and only then switch the rules to `scram-sha-256`.

## The `peer` Method

For local Unix socket connections, `peer` authentication asks the OS: "What Unix user is connecting?" and matches it to a PostgreSQL role.

```
local   all   postgres   peer
```

This means: if you're the OS user `postgres`, you can connect as PostgreSQL role `postgres` without a password. This is how `sudo -u postgres psql` works.

```bash
# This works because the OS user 'postgres' matches PG role 'postgres'
sudo -u postgres psql
```

**pg_ident.conf**: If OS username ≠ PG role name, use pg_ident.conf to map them:
```
# pg_ident.conf
# MAPNAME      SYSTEM-USERNAME     PG-USERNAME
app_map        ubuntu              myapp_role
```

Then in pg_hba.conf:
```
local   mydb   all   peer map=app_map
```

## The `trust` Method

`trust` means: anyone connecting through this rule gets in with no password.

```
local   all   all   trust    ← ANYONE on this server can connect as ANY user
```

This is the default in some local/dev setups. It's fine for local development. **Never use trust over TCP in production.** Even over localhost — if any process on the server is compromised, it can connect to PostgreSQL as any user.

## Diagnosing Connection Errors

**`no pg_hba.conf entry for host "10.0.0.5", user "myapp", database "mydb", no encryption`**
No rule matches this connection. Add a rule (above any reject-all line) and reload. The last part tells you whether the client used SSL or GSSAPI encryption.

**`pg_hba.conf rejects connection for host ...`**
A rule did match, and its method is `reject`.

**"password authentication failed"**
Rule matched, but password wrong. Check user exists and password is correct.

**"connection refused"**
PostgreSQL is not listening on that address/port. Check `listen_addresses` in postgresql.conf.

**SSL mismatches**
If only `hostssl` rules match the client's address, a non-SSL connection gets the same "no pg_hba.conf entry ... no encryption" error: turn SSL on in the client (`sslmode=require` or stricter). If the client insists on SSL but the server has `ssl = off`, the client reports `server does not support SSL, but SSL was required`.

```sql
-- See rejected connections in logs. Set in postgresql.conf:
--   log_connections = on
-- Reload and check logs for "connection received" then "authentication failed"

-- Check your rules are what you think they are
SELECT * FROM pg_hba_file_rules;  -- PG10+
```

## Separating Roles for Security

Never use superuser for application connections.

```sql
-- Create a read-only role for reporting
CREATE ROLE reporting NOLOGIN;
GRANT CONNECT ON DATABASE mydb TO reporting;
GRANT USAGE ON SCHEMA public TO reporting;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO reporting;
-- Default privileges apply to tables created later *by the role that runs this*;
-- add FOR ROLE app_owner if a different role creates the tables
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO reporting;

-- Create a user that uses this role
CREATE USER reporter PASSWORD 'strongpassword' IN ROLE reporting;

-- Application user with specific permissions
CREATE USER myapp PASSWORD 'strongpassword';
GRANT CONNECT ON DATABASE mydb TO myapp;
GRANT USAGE ON SCHEMA public TO myapp;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO myapp;
```

## Replication User in pg_hba.conf

Streaming replication needs a dedicated user:

```sql
-- Create replication user
CREATE USER replicator WITH REPLICATION PASSWORD 'strongpassword';
```

```
# pg_hba.conf — allow replication from standby server
host    replication     replicator      10.0.0.20/32    scram-sha-256
```

The keyword `replication` in the DATABASE column is special — it's not an actual database name, it means "this is a replication connection."

## Common pg_hba.conf Mistakes

**1. Wrong order of rules**
pg_hba.conf uses the FIRST matching rule. If you have:
```
host all all 0.0.0.0/0 trust
host all all 10.0.0.5/32 scram-sha-256
```
The 10.0.0.5 rule never matches — the `trust` rule fires first for all IPs.

**2. Forgetting to reload**
Edit pg_hba.conf, forget to reload → old rules still in effect.

**3. Using `trust` for TCP connections**
Anyone who can reach port 5432 gets in. Don't.

**4. Overly broad rules**
`host all all 0.0.0.0/0 scram-sha-256` — any IP with a valid password can connect. Lock down to specific subnets/IPs.

**5. No reject-all rule at the bottom**
If nothing matches, PostgreSQL's internal default is to reject. But an explicit reject rule at the bottom makes the intent clear and prevents accidents from rule reordering.
