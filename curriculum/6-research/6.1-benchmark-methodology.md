# 6.1 — Benchmark Methodology: How to Measure Fairly

**Phase**: 6 — Research & Publication
**Est. reading time**: 20 min

---

## Why Methodology Matters

A benchmark that isn't done correctly is worse than no benchmark — it produces confident-sounding wrong conclusions.

Before you collect a single data point:
1. Define a clear hypothesis
2. Control all variables except the one you're measuring
3. Measure the right things
4. Run enough iterations for statistical significance
5. Know what your benchmark can and cannot prove

---

## pgbench — The Built-In Benchmark Tool

pgbench ships with PostgreSQL. It simulates an OLTP workload based on TPC-B.

```bash
# Initialize benchmark database
# Scale factor multiplies the base table sizes
# scale=100 → accounts table has 10,000,000 rows (~1.4GB)
pgbench -i -s 100 -U postgres -d pgbench_db

# Run a benchmark: 20 clients, 8 worker threads, 300 seconds, progress every 10 seconds
pgbench \
  -U postgres \
  -d pgbench_db \
  -c 20 \
  -j 8 \
  -T 300 \
  -P 10
```

**Output:**
```
transaction type: <builtin: TPC-B (sort of)>
scaling factor: 100
number of clients: 20
number of threads: 8
duration: 300 s
number of transactions actually processed: 228450
latency average = 26.262 ms
latency stddev = 18.543 ms
tps = 761.480 (without initial connection time)
```

**Key metrics:**
- **TPS**: Transactions per second. Higher = better.
- **Latency average**: Mean time per transaction. Lower = better.
- **Latency stddev**: Consistency. High stddev = unstable (bad).

## Designing a Parameter Experiment

**Example hypothesis**: "Increasing shared_buffers from 2GB to 8GB improves read-heavy TPS by >20% when the working set fits in the larger buffer."

**Variables:**
- **Independent variable**: The parameter you change (shared_buffers)
- **Dependent variable**: What you measure (TPS, latency, cache hit rate)
- **Controlled variables**: Everything else — same hardware, OS, workload, client count, PostgreSQL version

**The rule**: Change one thing at a time. If you change two things and performance improves, you don't know which one caused it.

## Running a Clean Experiment

```bash
#!/bin/bash
# experiment.sh

DB="pgbench_db"
CLIENTS=20
THREADS=8
DURATION=300      # 5 min run
WARMUP=60         # 1 min warmup (not recorded)
RUNS=3            # 3 runs per config for statistical confidence
OUTDIR="/research/experiments/$(date +%Y%m%d)"
mkdir -p "$OUTDIR"

run_config() {
    local label=$1
    local outfile="$OUTDIR/${label}.txt"

    echo "=== Config: $label ===" | tee "$outfile"
    psql -d $DB -c "SHOW shared_buffers;" | tee -a "$outfile"
    psql -d $DB -c "SELECT pg_stat_reset();" > /dev/null

    # Warmup
    pgbench -U postgres -d $DB -c $CLIENTS -j $THREADS -T $WARMUP > /dev/null 2>&1

    # Measured runs
    for i in $(seq 1 $RUNS); do
        echo "--- Run $i ---" | tee -a "$outfile"
        pgbench -U postgres -d $DB -c $CLIENTS -j $THREADS -T $DURATION \
            2>&1 | tee -a "$outfile"
    done

    # Capture pg_stat
    psql -d $DB -c "
        SELECT blks_hit, blks_read,
               round(blks_hit::numeric/nullif(blks_hit+blks_read,0)*100,2) AS hit_rate
        FROM pg_stat_database WHERE datname='$DB';" | tee -a "$outfile"
}

# Test different values
for size in 2GB 4GB 8GB 16GB; do
    psql -U postgres -c "ALTER SYSTEM SET shared_buffers = '$size';"
    pg_ctl restart -D "$PGDATA" -m fast -w
    sleep 30    # let cache settle
    run_config "shared_buffers_${size}"
done
```

## The Warmup Problem

When you restart PostgreSQL or change config, shared_buffers is empty (cold cache). The first queries must read everything from disk — results are artificially slow.

**Always warmup**: Run 1-2 minutes of load before starting measurement. This lets the buffer pool fill with hot data, giving you steady-state performance numbers. For a precise warm start, the `pg_prewarm` extension loads chosen tables into shared_buffers (`SELECT pg_prewarm('pgbench_accounts');`).

```bash
# Warmup: read-heavy pass to fill caches
pgbench -U postgres -d pgbench_db -c 10 -j 4 -T 60 -S > /dev/null
# Now measure
pgbench -U postgres -d pgbench_db -c 20 -j 8 -T 300
```

---

## Avoiding Common Mistakes

**1. Too short a run**: Short runs are dominated by startup noise. 5 minutes minimum; 15-30 minutes for stable results.

**2. Single run**: One measurement could be lucky/unlucky. Always run 3-5 times.

**3. Benchmarking on the same machine**: pgbench itself uses CPU. Run pgbench from a separate client server to avoid competing with PostgreSQL.

**4. Not resetting pg_stat counters**: Stats accumulate. Reset before each run:
```sql
SELECT pg_stat_reset();
SELECT pg_stat_reset_shared('bgwriter');
```
`pg_stat_reset()` also wipes the counters autovacuum uses to decide when to run. On a dedicated benchmark box that's acceptable (run `ANALYZE` afterwards); anywhere else, take snapshots and subtract instead.

**5. Changing multiple things**: Only change one parameter per experiment.

**6. Ignoring OS state**: Restarting PostgreSQL empties shared_buffers but *not* the Linux page cache. For shared_buffers experiments that's a major confound: a page evicted from shared_buffers is often still in the OS cache, so a smaller shared_buffers costs less than its hit rate suggests (`blks_read` counts those OS-cache hits as reads). Decide deliberately, and say which you did in the paper: drop the OS cache before each run for cold-start numbers (`sync; echo 3 > /proc/sys/vm/drop_caches`), or warm both caches for steady state. Dirty pages left over from the previous run matter too, so run `CHECKPOINT` before each measurement.

## pgbench Custom Workloads

The TPC-B test may not match your production queries. Write custom scripts:

```sql
-- File: custom_workload.sql
\set customer_id random(1, 1000000)
\set product_id random(1, 10000)

BEGIN;
SELECT id, name, email FROM customers WHERE id = :customer_id;
SELECT id, stock, price FROM products WHERE id = :product_id;
UPDATE products SET stock = stock - 1 WHERE id = :product_id AND stock > 0;
INSERT INTO orders (customer_id, product_id, created_at)
    VALUES (:customer_id, :product_id, now());
COMMIT;
```

```bash
pgbench -U postgres -d mydb \
  -f custom_workload.sql \
  -c 20 -j 8 -T 300
```

Custom scripts let you test your actual workload patterns, not a generic OLTP proxy.

## Statistical Basics for Results

Don't just report the mean. Report:

```python
import statistics

tps_readings = [761, 754, 778, 742, 769]

mean   = statistics.mean(tps_readings)      # 760.8
median = statistics.median(tps_readings)    # 761
stddev = statistics.stdev(tps_readings)     # 13.8
cv     = stddev / mean * 100               # 1.8% → very consistent

print(f"Mean TPS: {mean:.1f} ± {stddev:.1f}")
print(f"Coefficient of Variation: {cv:.1f}%")
# CV < 5% = consistent results (good)
# CV > 15% = too much noise, run longer or reduce concurrency
```

**p95 latency matters more than average for user experience.** pgbench doesn't print percentiles: `-r` reports per-statement *average* latency. Log every transaction with `-l` (one line per transaction; the third column is its latency in microseconds) and compute p95/p99 from the log files, one per thread. At high TPS, sample with `--sampling-rate`.

## Recording Your Experiments

Every experiment gets a directory:

```
research/experiments/
└── 20261015_shared_buffers/
    ├── hypothesis.md      ← what you expected to see
    ├── setup.md           ← hardware, OS, PG version, config
    ├── results_raw.txt    ← pgbench output
    ├── pg_stats.txt       ← pg_stat_database, pg_stat_bgwriter
    ├── os_metrics.txt     ← iostat / vmstat during run
    └── analysis.md        ← what you found, interpretation
```

If you can't reproduce a result 3 months later, it isn't a result — it's noise.
