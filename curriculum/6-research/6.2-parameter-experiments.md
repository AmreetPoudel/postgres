## Parameters Worth Experimenting With

Not all parameters have equal impact. These are the highest-yield ones, ranked by expected impact on typical workloads:

| Parameter | Expected Impact | Best Workload to Test |
|---|---|---|
| `shared_buffers` | High (10–30%) | Read-heavy, working set > default buffer |
| `random_page_cost` | High (10–50% on SSD) | Any indexed query workload |
| `work_mem` | High for sort/hash | Analytics, ORDER BY, GROUP BY |
| `max_wal_size` / `checkpoint_timeout` | Medium (5–15%) | High-write OLTP |
| `autovacuum_vacuum_cost_limit` | Medium | Tables with heavy UPDATE/DELETE |
| `effective_io_concurrency` | Medium on NVMe | Bitmap heap scans (the only place PG16 uses it for prefetching) |
| `huge_pages` | Low–Medium (2–8%) | Any workload with large shared_buffers |
| `wal_compression` | Variable | Write-heavy with bandwidth constraints |

The scripts below write to `/research/...` as shorthand for this repo's `research/experiments/` folder. Point them at a dated directory per experiment (see 6.3), e.g. `research/experiments/20261101_shared_buffers/`.

## Experiment 1: shared_buffers Sensitivity

**Hypothesis**: TPS increases as shared_buffers grows until the working set fits in the buffer pool, then plateaus. Cache hit rate should approach 99%+ once the buffer is large enough.

```bash
# Create a working set larger than any buffer value you'll test
pgbench -i -s 500 -U postgres -d pgbench_db
# ~7GB working set (good for testing 1GB–16GB shared_buffers)

for size in 1GB 2GB 4GB 8GB 12GB 16GB; do
    psql -U postgres -c "ALTER SYSTEM SET shared_buffers = '$size';"
    pg_ctl restart -D "$PGDATA" -m fast -w
    sleep 30

    # Warmup
    pgbench -U postgres -d pgbench_db -c 10 -j 4 -T 60 -S > /dev/null

    # Reset stats
    psql -d pgbench_db -c "SELECT pg_stat_reset();"

    # Read-only benchmark (isolates buffer cache effect)
    echo "=== shared_buffers=$size ===" >> /research/exp1_shared_buffers.txt
    pgbench -U postgres -d pgbench_db -c 20 -j 8 -T 300 -S \
        >> /research/exp1_shared_buffers.txt 2>&1   # (2>&1 must come after the file redirect)

    # Capture cache hit rate
    psql -d pgbench_db -c "
        SELECT setting AS shared_buffers,
               round(blks_hit::numeric/nullif(blks_hit+blks_read,0)*100,2) AS hit_rate
        FROM pg_settings, pg_stat_database
        WHERE name='shared_buffers' AND datname='pgbench_db';" \
        >> /research/exp1_shared_buffers.txt
done
```

**Expected result**: TPS increases sharply from 1GB→4GB, then levels off. Cache hit rate jumps above 95% once buffer fits the working set. Expect the TPS gain to be smaller than the hit-rate jump suggests: with plenty of RAM, most "reads" at small shared_buffers come from the OS page cache, not the disk (6.1, mistake 6). Record which cache state you measured.

## Experiment 2: random_page_cost and Plan Choice

**Hypothesis**: On NVMe, lowering `random_page_cost` from 4.0 to 1.1 changes plans only for medium-selectivity queries, moving them toward index access, and the new plans are faster. Point lookups use the index at any setting, so they make a poor test.

```sql
-- Create a 10M row table with an index (in pgbench_db, where the scripts below run)
CREATE TABLE orders_exp (
    id bigserial PRIMARY KEY,
    customer_id int,
    status text,
    amount numeric(10,2),
    created_at timestamp DEFAULT now()
);

INSERT INTO orders_exp (customer_id, status, amount)
SELECT
    (random() * 1000000)::int,
    CASE WHEN random() < 0.05 THEN 'pending' ELSE 'completed' END,
    (random() * 1000)::numeric(10,2)
FROM generate_series(1, 10000000);

CREATE INDEX ON orders_exp(customer_id);
VACUUM ANALYZE orders_exp;
```

```bash
# Range query whose selectivity you control with -D width=...
cat > /research/range.sql << 'SQL'
\set cid random(1, 1000000)
SELECT sum(amount) FROM orders_exp WHERE customer_id BETWEEN :cid AND :cid + :width;
SQL

for rpc in 4.0 2.0 1.5 1.1; do
    psql -d pgbench_db -c "ALTER SYSTEM SET random_page_cost = $rpc;"
    psql -d pgbench_db -c "SELECT pg_reload_conf();"

    for width in 1 1000 10000 100000; do     # ~10 rows up to ~10% of the table
        echo "=== random_page_cost=$rpc width=$width ===" >> /research/exp2_rpc.txt

        # Which plan does the planner choose at this selectivity?
        psql -d pgbench_db -c "EXPLAIN SELECT sum(amount) FROM orders_exp WHERE customer_id BETWEEN 1000 AND 1000 + $width;" \
            >> /research/exp2_rpc.txt

        # And how fast is it?
        pgbench -d pgbench_db -c 10 -j 4 -T 120 -D width=$width -f /research/range.sql \
            >> /research/exp2_rpc.txt 2>&1
    done
done
```

**Expected result**: at `width=1` the plan is an index scan at every setting. At medium widths, the plan shifts (seq scan or bitmap heap scan → bitmap or plain index scan) as `random_page_cost` drops. Whether that's *faster* is the real finding, and it depends on caching: if the table fits in RAM, random reads are cheap at any setting. Make the table larger than RAM, or drop caches between runs, to measure the storage effect.

## Experiment 3: Checkpoint Frequency and Write Performance

**Hypothesis**: Larger `max_wal_size` reduces checkpoint frequency, smoothing I/O and improving write throughput on high-write workloads.

```bash
for wal_size in 512MB 1GB 2GB 4GB 8GB; do
    psql -c "ALTER SYSTEM SET max_wal_size = '$wal_size';"
    psql -c "ALTER SYSTEM SET checkpoint_timeout = '15min';"
    pg_ctl reload -D "$PGDATA"

    # Start every run from the same state: no dirty pages left from the last one
    psql -c "CHECKPOINT;"
    psql -c "SELECT pg_stat_reset_shared('bgwriter');"
    psql -c "SELECT pg_stat_reset_shared('wal');"
    sleep 5

    echo "=== max_wal_size=$wal_size ===" >> /research/exp3_checkpoints.txt

    # Write-heavy workload (default TPC-B has writes). Run long enough to cover
    # several checkpoint_timeout cycles: 45 minutes here
    pgbench -U postgres -d pgbench_db -c 20 -j 8 -T 2700 \
        >> /research/exp3_checkpoints.txt 2>&1

    # Checkpoint stats, plus how many full-page images the WAL contained
    psql -c "
        SELECT checkpoints_timed, checkpoints_req,
               checkpoint_write_time, buffers_checkpoint, buffers_backend,
               (SELECT wal_fpi FROM pg_stat_wal) AS full_page_images
        FROM pg_stat_bgwriter;" >> /research/exp3_checkpoints.txt
done
```

**Expected result**: As max_wal_size increases, `checkpoints_req` drops toward 0 and time-based checkpoints take over. Fewer checkpoints also mean fewer full-page images (`full_page_images`), so less WAL per transaction. `buffers_backend` should fall and TPS should improve.

**Key insight to document**: `checkpoints_req >> checkpoints_timed` is a diagnostic signal that max_wal_size is too small.

## Experiment 4: work_mem and Sort Performance

**Hypothesis**: Increasing work_mem eliminates disk-based sorts (spills to temp files), dramatically improving sort/hash query latency.

```sql
-- Create 5M row dataset to sort (in pgbench_db)
CREATE TABLE sort_exp AS
SELECT
    (random() * 10000000)::int AS sort_key,
    md5(random()::text) AS payload
FROM generate_series(1, 5000000);
```

```bash
# OFFSET without LIMIT forces a full sort but returns one row. (With LIMIT 1000,
# PostgreSQL does a "top-N heapsort" that keeps only 1000 rows and never spills.)
cat > /research/sort_query.sql << 'SQL'
SELECT sort_key, payload FROM sort_exp ORDER BY sort_key OFFSET 4999999;
SQL

for wm in 4MB 16MB 64MB 256MB 1GB; do
    psql -c "ALTER SYSTEM SET work_mem = '$wm';"
    pg_ctl reload -D "$PGDATA"

    echo "=== work_mem=$wm ===" >> /research/exp4_workmem.txt

    # Get the plan: shows "Sort Method" (disk vs memory)
    psql -d pgbench_db -c "
        EXPLAIN (ANALYZE, BUFFERS)
        SELECT sort_key, payload FROM sort_exp ORDER BY sort_key OFFSET 4999999;" \
        >> /research/exp4_workmem.txt

    # Temp file stats
    psql -d pgbench_db -c "SELECT pg_stat_reset();"
    pgbench -d pgbench_db -c 5 -j 2 -T 60 -f /research/sort_query.sql > /dev/null
    psql -d pgbench_db -c "
        SELECT temp_files, pg_size_pretty(temp_bytes) AS temp_size
        FROM pg_stat_database WHERE datname='pgbench_db';" \
        >> /research/exp4_workmem.txt
done
```

**Expected result**: At 4MB, `Sort Method: external merge Disk`, temp_files > 0. At the threshold work_mem value, sort flips to `Sort Method: quicksort Memory` and temp_files drops to 0. Identify and document that threshold.

## Experiment 5: Autovacuum Cost Throttling

**Hypothesis**: Setting `autovacuum_vacuum_cost_limit = 800` (vs default 200) on NVMe allows autovacuum to clean dead tuples 4× faster without measurable impact on OLTP latency.

```sql
-- Create a table that generates lots of dead tuples (in pgbench_db)
CREATE TABLE autovac_exp (
    id serial PRIMARY KEY,
    counter int DEFAULT 0,
    data text DEFAULT md5(random()::text)
);
INSERT INTO autovac_exp (counter) SELECT 0 FROM generate_series(1, 500000);
```

**Measurement approach**:
1. Enable per-table autovacuum logging: `log_autovacuum_min_duration = 0`
2. Run continuous UPDATEs to generate dead tuples
3. Measure: how often autovacuum runs, how long it takes, n_dead_tup over time
4. Repeat with different cost limits

```bash
# Generate steady stream of dead tuples
cat > /research/update_loop.sql << 'SQL'
\set id random(1, 500000)
UPDATE autovac_exp SET counter = counter + 1 WHERE id = :id;
SQL

# Baseline (cost_limit=200)
psql -c "ALTER TABLE autovac_exp SET (autovacuum_vacuum_cost_limit = 200);"

pgbench -d pgbench_db -c 10 -j 4 -T 300 -f /research/update_loop.sql \
    > /research/exp5_autovac_200.txt 2>&1 &

# Monitor dead tuple count during the run
for i in $(seq 1 30); do
    sleep 10
    psql -d pgbench_db -c "
        SELECT n_dead_tup, n_live_tup, last_autovacuum
        FROM pg_stat_user_tables WHERE relname='autovac_exp';" \
        >> /research/exp5_autovac_200_dtp.txt
done
wait

# Repeat with cost_limit=800
psql -c "ALTER TABLE autovac_exp SET (autovacuum_vacuum_cost_limit = 800);"
# ... same benchmark
```
