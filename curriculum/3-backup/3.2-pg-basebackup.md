# 3.2 — pg_basebackup: Physical Backup

**Phase**: 3 — Backup, Recovery & PITR
**Est. reading time**: 20 min

---

## What pg_basebackup Does

pg_basebackup takes a **physical copy** of the entire PostgreSQL data directory while the database is running. It doesn't lock the database or interrupt queries.

It uses the replication protocol internally (that's why it needs replication permissions). It:
1. Tells PostgreSQL "start backup"
2. Copies all data files
3. Copies the WAL generated during the copy (so the backup is consistent)
4. Tells PostgreSQL "stop backup"

The result: a complete, consistent copy of your database that you can restore to another server or use as a starting point for PITR.

---

## Prerequisites

```sql
-- User needs REPLICATION privilege
CREATE USER backup_user WITH REPLICATION PASSWORD 'strongpass';
```

```
# pg_hba.conf — allow backup_user to connect for replication
host    replication     backup_user     127.0.0.1/32    scram-sha-256
```

```
# postgresql.conf
wal_level = replica           # must be replica or logical
max_wal_senders = 3           # at least 1 for backup (others for standbys)
```

## Basic pg_basebackup Usage

```bash
# Simple backup to a directory
pg_basebackup \
  -U backup_user \
  -h localhost \
  -D /backup/basebackup/$(date +%Y%m%d) \
  -P \          # show progress
  -v            # verbose

# Compressed tar format (smaller, not a usable directory directly)
pg_basebackup \
  -U backup_user \
  -h localhost \
  -D /backup/ \
  -F tar \      # tar format
  -z \          # gzip compress
  -P -v

# Result files:
# /backup/base.tar.gz      ← main data directory
# /backup/pg_wal.tar.gz    ← WAL files generated during backup
```

**Important flags:**

| Flag | Meaning |
|---|---|
| `-D dir` | Destination directory |
| `-F p` | Plain format (default, copies files as-is) |
| `-F t` | Tar format (single archive) |
| `-z` | Compress (with tar format) |
| `-Z level` | Compression level (0-9) |
| `-P` | Show progress |
| `-X stream` | Stream WAL during backup (most common) |
| `-X fetch` | Fetch WAL at end of backup |
| `-R` | Write recovery config (for standby setup) |
| `--checkpoint=fast` | Immediately trigger checkpoint before backup |
| `--wal-method=stream` | Same as -X stream |

---

## The `-R` Flag — For Standby Setup

```bash
# Create a standby server base backup with ready-to-use recovery config
pg_basebackup \
  -U backup_user \
  -h primary-server \
  -D /var/lib/postgresql/16/main \
  -R \          # write standby.signal + connection string to postgresql.auto.conf
  -P -v
```

With `-R`, pg_basebackup writes:
- `standby.signal` file (tells PostgreSQL to start in recovery/standby mode)
- `postgresql.auto.conf` with `primary_conninfo` (where to stream WAL from)

This is the fastest way to set up a standby server. See Phase 4.1 for the full process.

## pg_basebackup with WAL Streaming

```bash
# Stream WAL during backup (most reliable method)
pg_basebackup \
  -U backup_user \
  -h localhost \
  -D /backup/$(date +%Y%m%d) \
  -X stream \   # stream WAL during backup (uses a second connection)
  -P -v
```

With `-X stream` (default):
- PostgreSQL keeps a replication slot temporarily during the backup
- WAL generated during the backup is streamed in real-time
- The backup is always consistent — no need to manually copy WAL afterward

With `-X fetch` (older method):
- WAL accumulated during the backup is fetched at the end
- Requires `wal_keep_size` to be large enough that WAL isn't deleted before the backup finishes

Use `-X stream` unless you have a specific reason not to.

## Backup Size and Time

```bash
# How large will the backup be?
psql -c "SELECT pg_size_pretty(pg_database_size('mydb'));"

# How long does backup take? (rough estimate: 100-300 MB/s depending on disk speed)
# 1 TB database on NVMe: ~1-3 hours
# 1 TB database on HDD: ~3-8 hours

# pg_basebackup with throttle (don't saturate disk on production server)
pg_basebackup \
  -h localhost \
  -U backup_user \
  -D /backup/base \
  -r 100m \     # limit to 100 MB/s
  -X stream -P -v
```

## Restoring from pg_basebackup

**Basic restore (same server, same version):**

```bash
# 1. Stop PostgreSQL
pg_ctl stop -D /var/lib/postgresql/16/main

# 2. Move old data directory aside (keep it for safety)
mv /var/lib/postgresql/16/main /var/lib/postgresql/16/main.old

# 3. Restore the base backup
rsync -av /backup/20261001/ /var/lib/postgresql/16/main/
# or if using tar format:
mkdir /var/lib/postgresql/16/main
tar -xzf /backup/base.tar.gz -C /var/lib/postgresql/16/main

# 4. Fix permissions (critical — PostgreSQL won't start if permissions are wrong)
chown -R postgres:postgres /var/lib/postgresql/16/main
chmod 700 /var/lib/postgresql/16/main

# 5. Start PostgreSQL
pg_ctl start -D /var/lib/postgresql/16/main

# 6. Verify
psql -c "SELECT count(*) FROM pg_stat_user_tables;"
```

## What pg_basebackup Does NOT Back Up

- WAL files older than what was generated during the backup (you need archiving for PITR)
- Tablespaces on other filesystems (they're included but check symlinks)
- Configuration files not in PGDATA (some distros put config in `/etc/postgresql/`)

## Automating pg_basebackup

```bash
#!/bin/bash
# /usr/local/bin/pg_physical_backup.sh

BACKUP_BASE="/backup/pg_base"
DATE=$(date +%Y%m%d)
BACKUP_DIR="$BACKUP_BASE/$DATE"
KEEP_DAYS=7

# Run backup
pg_basebackup \
  -h localhost \
  -U backup_user \
  -D "$BACKUP_DIR" \
  -X stream \
  --checkpoint=fast \
  -P -v 2>&1

if [ $? -eq 0 ]; then
  echo "$(date): Backup to $BACKUP_DIR succeeded"
  # Compress (optional, saves space)
  tar -czf "$BACKUP_DIR.tar.gz" "$BACKUP_DIR" && rm -rf "$BACKUP_DIR"
else
  echo "$(date): Backup FAILED"
  exit 1
fi

# Cleanup old backups
find $BACKUP_BASE -name "*.tar.gz" -mtime +$KEEP_DAYS -delete
```

## For Production: Use pgBackRest Instead

pg_basebackup is the built-in tool and works well for basic setups. But for production DR, **pgBackRest** (Phase 3.4) gives you:
- Incremental backups (only changed blocks since last backup)
- Parallel backup and restore
- Built-in archiving management
- Retention policies
- Backup verification
- PITR orchestration

pg_basebackup is great for understanding how physical backup works and for quickly setting up a standby. For production backup strategy, move to pgBackRest.
