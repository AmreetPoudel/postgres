# 3.3 — WAL Archiving & Point-In-Time Recovery (PITR)

**Phase**: 3 — Backup, Recovery & PITR
**Est. reading time**: 25 min

---

## The Problem PITR Solves

A base backup (pg_basebackup) gives you the state of the database at the backup time. That's useful but limited.

**Scenario**: Your base backup runs at 2 AM. A developer runs `DELETE FROM orders;` at 10 AM and commits. You notice at 10:30 AM. Your base backup gets you back to 2 AM — you lose 8 hours of data.

With PITR + WAL archiving: You can restore to exactly 9:59:59 AM, losing only 30 seconds of data.

---

## How PITR Works

```
Base Backup             WAL Archives                    Crash / Target time
at 2:00 AM         2:00 AM → 10:30 AM                      10:00 AM
     │                     │                                      │
     └──────────────────────┴──── PITR replays WAL → stops here ──┘
```

PITR = base backup + all WAL segments from that backup to your target time.

You need:
1. A base backup
2. Continuous WAL archiving from the backup forward
3. A recovery target (time, transaction ID, or LSN)

## Setting Up WAL Archiving

```
# postgresql.conf
archive_mode = on                 # enable archiving (requires restart)
archive_command = 'test ! -f /archive/wal/%f && cp %p /archive/wal/%f'
archive_timeout = 300             # archive a segment even if not full (every 5 min)
wal_level = replica               # required
```

The `archive_command` is a shell command. PostgreSQL calls it for each completed WAL segment:
- `%p` = full path to the WAL segment file
- `%f` = just the filename

**Important**: The command must return 0 on success, non-zero on failure. If it fails, PostgreSQL retries indefinitely and keeps the WAL segment. This is the safety mechanism.

**The `test ! -f` part**: Prevents overwriting an existing archive file. If the archive already has this segment, do nothing (return 0). WAL filenames are unique, so this is safe.

**Better archive commands:**
```bash
# rsync to a remote backup server
archive_command = 'rsync -a %p backup-server:/archive/wal/%f'

# pgBackRest (Phase 3.4) — this is what production should use
archive_command = 'pgbackrest --stanza=main archive-push %p'
```

## Monitoring Archiving Health

```sql
-- Check archiving status
SELECT
    archived_count,
    last_archived_wal,
    now() - last_archived_time AS time_since_last_archive,
    failed_count,
    last_failed_wal,
    last_failed_time
FROM pg_stat_archiver;
```

**Alert if:**
- `failed_count` is increasing → archive command is failing
- `time_since_last_archive` > 10 minutes on a busy system → archiving is stuck

## Taking the Base Backup

Before starting PITR, you need a consistent base backup taken AFTER archiving was enabled:

```bash
# Take a base backup (this includes a backup label with start LSN)
pg_basebackup \
  -h localhost \
  -U backup_user \
  -D /backup/base/$(date +%Y%m%d) \
  -X stream \
  --checkpoint=fast \
  -P -v

# Record when this backup was taken — you'll need this for PITR
echo "Backup taken at: $(date)" > /backup/base/$(date +%Y%m%d)/backup_info.txt
```

## Performing a PITR Restore

**Scenario**: DELETE FROM orders ran at 10:00:00 AM. Restore to 9:59:00 AM.

### Step 1: Stop PostgreSQL
```bash
pg_ctl stop -m fast -D /var/lib/postgresql/16/main
```

### Step 2: Clear the data directory and restore base backup
```bash
# Save old data dir in case you need it
mv /var/lib/postgresql/16/main /var/lib/postgresql/16/main.broken

# Restore from base backup
rsync -av /backup/base/20261007/ /var/lib/postgresql/16/main/
# or
mkdir /var/lib/postgresql/16/main
tar -xzf /backup/base/20261007.tar.gz -C /var/lib/postgresql/16/main

chown -R postgres:postgres /var/lib/postgresql/16/main
chmod 700 /var/lib/postgresql/16/main
```

### Step 3: Configure recovery settings (PG12+ style)

```bash
# Edit postgresql.conf (or postgresql.auto.conf)
cat >> /var/lib/postgresql/16/main/postgresql.conf << 'EOF'

# Recovery settings
restore_command = 'cp /archive/wal/%f %p'
recovery_target_time = '2026-10-07 09:59:00 +0545'
recovery_target_action = 'promote'   # promote to writable after reaching target
EOF

# Create the recovery mode trigger file
touch /var/lib/postgresql/16/main/recovery.signal
```

### Step 4: Start PostgreSQL (it enters recovery mode)
```bash
pg_ctl start -D /var/lib/postgresql/16/main

# Watch the logs — you'll see WAL replay progress
tail -f /var/lib/postgresql/16/main/log/postgresql-*.log
```

Log output during recovery:
```
LOG:  starting point-in-time recovery to 2026-10-07 09:59:00
LOG:  restored log file "000000010000000000000023" from archive
LOG:  redo starts at 0/23000028
LOG:  consistent recovery state reached at 0/23000100
LOG:  recovery stopping before commit of transaction 15234567, time 2026-10-07 10:00:01
LOG:  pausing at the end of recovery
HINT:  Execute pg_wal_replay_resume() to promote.
```

If `recovery_target_action = 'promote'`, PostgreSQL promotes automatically. Otherwise you control it:

```sql
-- Check recovery status
SELECT pg_is_in_recovery();

-- Resume (promote to writable) when ready
SELECT pg_wal_replay_resume();
```

### Step 5: Verify and inspect
```bash
psql -c "SELECT count(*) FROM orders;"  # Should have the data from before the DELETE
psql -c "SELECT pg_is_in_recovery();"   # Should return false (promoted)
```

## Recovery Target Options

```
# Stop at a specific time
recovery_target_time = '2026-10-07 09:59:00'

# Stop at a specific transaction ID
recovery_target_xid = '15234560'

# Stop at a specific LSN (byte position in WAL)
recovery_target_lsn = '0/23456789'

# Restore to the end of WAL (full recovery after crash)
# Don't set recovery_target* — it will replay everything

# Named restore point (must have been created before with pg_create_restore_point())
recovery_target_name = 'before_migration'
```

**Creating named restore points** (use before risky operations):
```sql
-- Before a major migration:
SELECT pg_create_restore_point('before_v2_migration');
-- This creates a bookmark in WAL you can restore to by name
```

---

## recovery_target_action

```
recovery_target_action = 'pause'    # pause at target, wait for pg_wal_replay_resume()
recovery_target_action = 'promote'  # promote to writable immediately (default)
recovery_target_action = 'shutdown' # stop after reaching target (copy data then start fresh)
```

Use `pause` when you want to inspect data before committing to the restore:
```bash
# Start in pause mode
# recovery_target_action = 'pause'

# Start PostgreSQL, inspect data
psql -c "SELECT count(*) FROM orders;"  # check if restore looks right

# If good, promote
psql -c "SELECT pg_wal_replay_resume();"

# If bad (went too far), stop and retry with earlier target
pg_ctl stop -m fast
# Adjust recovery_target_time to earlier time
pg_ctl start
```

## restore_command

```
restore_command = 'cp /archive/wal/%f %p'
# %f = filename to retrieve
# %p = where to put it (local pg_wal directory during recovery)
```

PostgreSQL calls this for each WAL segment it needs during recovery. If the command fails (segment not in archive), recovery stops.

**For remote archives:**
```bash
# From another server
restore_command = 'scp backup-server:/archive/wal/%f %p'

# From S3 (using wal-g)
restore_command = 'wal-g wal-fetch %f %p'

# From pgBackRest
restore_command = 'pgbackrest --stanza=main archive-get %f %p'
```

## PITR Requirements Checklist

Before you're in a situation where you need PITR:
- [ ] `archive_mode = on` in postgresql.conf
- [ ] `archive_command` correctly sends WAL to archive location
- [ ] Archive location is on a different physical location than the database
- [ ] Base backup taken regularly (pg_basebackup or pgBackRest)
- [ ] Archive location has WAL from the base backup to now
- [ ] Recovery procedure is documented and tested

**Test your PITR procedure in a staging environment. Don't discover it doesn't work during an emergency.**

## Common PITR Failures

**1. Missing WAL segments in archive**
The restore_command returns non-zero → recovery stops with `FATAL: could not find file "000000010000000X"`.
Cause: Archive command was failing silently, gaps exist.
Prevention: Monitor `pg_stat_archiver.failed_count`.

**2. Recovery overshoots target time**
WAL doesn't have millisecond precision. Use `recovery_target_inclusive = false` to stop before the target transaction instead of at or after it.

**3. Permissions wrong on restored files**
PostgreSQL refuses to start. Fix: `chown -R postgres:postgres $PGDATA && chmod 700 $PGDATA`

**4. `recovery.signal` file missing**
PostgreSQL starts normally without recovery. Make sure to `touch $PGDATA/recovery.signal`.
