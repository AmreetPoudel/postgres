# 3.5 — Recovery Testing: Backup Is Only As Good As Your Last Test

**Phase**: 3 — Backup, Recovery & PITR
**Est. reading time**: 15 min

---

## The Uncomfortable Truth

Most teams have backups. Very few have tested them under pressure.

Until you've done an actual restore from backup in a realistic scenario, you don't know if your backups work. You know if the backup *command ran successfully*. That's not the same thing.

**What typically breaks during untested recoveries:**
- WAL archive has gaps (archive_command was silently failing)
- The restore user doesn't have permissions on the backup directory
- Recovery time is 8 hours and you didn't know — no runbook prepared
- Config files (pg_hba.conf, postgresql.conf) stored outside PGDATA weren't backed up
- The restore machine has a different PostgreSQL version (can't restore physical backup)
- Connection strings in apps still point to old server

---

## Recovery Drill Plan

Do this monthly (or quarterly at minimum). Document every step.

### Pre-Drill Checklist
- [ ] Identify a spare server/VM for restore testing (similar spec to production)
- [ ] Document where backup files are stored
- [ ] Document what user/permissions are needed to access backups
- [ ] Note current database size (to estimate restore time)
- [ ] Know your RTO target (how fast must restore complete?)

### The Drill

```bash
# 1. On test server — install the same PostgreSQL major version as production
#    (and give it read access to the backup repository)
apt install postgresql-16

# 2. Stop the test PostgreSQL
pg_ctl stop -D /var/lib/postgresql/16/main

# 3. Restore, and time it! Record the number.
#    --archive-mode=off matters on a test box: the restored copy carries the
#    production config and would otherwise push its own WAL into the
#    production repository once it promotes.
time pgbackrest --stanza=main --delta --archive-mode=off restore --log-level-console=detail

# 4. Start PostgreSQL
pg_ctl start -D /var/lib/postgresql/16/main

# 5. Verify data integrity
psql -c "SELECT count(*) FROM pg_stat_user_tables;"
psql -c "SELECT datname, pg_size_pretty(pg_database_size(datname)) FROM pg_database;"

# 6. Spot-check critical tables
psql -d mydb -c "SELECT count(*) FROM orders;"
psql -d mydb -c "SELECT max(created_at) FROM orders;"  # what's the latest data?

# 7. Test PITR (restore to a specific time): stop, then restore again
#    to 1 hour before "now"
pg_ctl stop -D /var/lib/postgresql/16/main -m fast
pgbackrest --stanza=main --delta --archive-mode=off restore \
  --type=time \
  --target="$(date -d '-1 hour' '+%Y-%m-%d %H:%M:%S')" \
  --target-action=promote
pg_ctl start -D /var/lib/postgresql/16/main
```

### Post-Drill Documentation
Record:
- Date of drill
- Backup set used (full + diff from when)
- Time to restore
- Data verified up to (timestamp of newest row in critical tables)
- Issues found
- Actions to fix issues

## Testing Archiving Separately

```bash
# Check archiving is healthy
psql -c "SELECT * FROM pg_stat_archiver;"

# Manually force a WAL segment to archive
# (it does nothing if no WAL was written since the last switch)
psql -c "SELECT pg_switch_wal();"

# Wait 30 seconds, check again
sleep 30
psql -c "SELECT last_archived_wal, now() - last_archived_time AS age FROM pg_stat_archiver;"
```

## Backup Monitoring in Production

```bash
# Script to check backup health daily
#!/bin/bash

# Check last successful backup time (pgBackRest)
LAST_BACKUP=$(pgbackrest --stanza=main info --output=json | \
  python3 -c "import json,sys; data=json.load(sys.stdin); \
  print(data[0]['backup'][-1]['timestamp']['stop'])")

# pgBackRest reports the stop time as epoch seconds
echo "Last backup: $(date -d @"$LAST_BACKUP")"

# Alert if backup is more than 25 hours old
NOW=$(date +%s)
AGE=$(( (NOW - LAST_BACKUP) / 3600 ))

if [ $AGE -gt 25 ]; then
  echo "ALERT: Last backup is ${AGE} hours old!"
  # Send alert to your monitoring system
fi

# Check archiving. failed_count only ever grows, so compare timestamps instead:
# is the most recent attempt a failure?
ARCHIVE_BROKEN=$(psql -At -c "SELECT coalesce(last_failed_time > last_archived_time, last_failed_time IS NOT NULL) FROM pg_stat_archiver;")
if [ "$ARCHIVE_BROKEN" = "t" ]; then
  echo "ALERT: the most recent WAL archive attempt failed"
fi
```

## What Your Runbook Should Include

A runbook is the step-by-step procedure you follow during an actual incident. Write it before you need it.

```markdown
# PostgreSQL Recovery Runbook

## Step 1: Assess the situation
- Full data loss (disk failure)?  → Full restore from latest backup
- Accidental DELETE/DROP?         → PITR restore to before the event
- Standby promotion needed?       → See HA runbook (Phase 5.6)

## Step 2: Notify stakeholders
- Who to notify: [list names/channels]
- Status page to update: [link]

## Step 3: Restore procedure
[specific commands for your setup]

## Step 4: Verification
- Row count checks
- Latest data timestamp
- Application smoke tests

## Step 5: DNS/connection update
- How to point apps to restored database
- PgBouncer reload command

## Step 6: Post-mortem
- Document what happened, when, cause, timeline
```

## pg_dump as a Complement to Physical Backup

Even if you use pgBackRest for physical backup, keep periodic pg_dump:

```bash
# Weekly logical backup alongside physical backup
pg_dump -U postgres -d mydb -F c -Z 9 -f /backup/logical/mydb_$(date +%Y%m%d).dump
```

Why both?
- Physical backup: Fast restore, PITR capability. Requires same PG version.
- Logical backup: Can restore to different PG version. Good for migrations. Selective table restore.

For a major-version upgrade you'd normally use pg_upgrade, or run the *newer* version's pg_dump against the old server. The weekly dump is your fallback for everything the physical backup can't do.
