# 4.5 — Replication Lag: Causes, Measurement, and Mitigation

**Phase**: 4 — Replication
**Est. reading time**: 15 min

---

## Types of Replication Lag

There are four LSN positions that matter for replication:

```
Primary generates WAL
    ↓
sent_lsn    ← primary sent to standby (network lag shows here)
    ↓
write_lsn   ← standby wrote WAL to disk
    ↓
flush_lsn   ← standby flushed WAL (durable)
    ↓
replay_lsn  ← standby applied WAL to data files (query-visible)
```

Each gap between these points represents a different type of lag.

---

## Measuring Lag

### On primary:

```sql
SELECT
    application_name,
    state,
    -- Byte-based lag
    pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn) AS send_lag_bytes,
    pg_wal_lsn_diff(pg_current_wal_lsn(), write_lsn) AS write_lag_bytes,
    pg_wal_lsn_diff(pg_current_wal_lsn(), flush_lsn) AS flush_lag_bytes,
    pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag_bytes,
    -- Time-based lag (PG10+)
    write_lag,
    flush_lag,
    replay_lag,
    sync_state
FROM pg_stat_replication;
```

### On standby:

```sql
-- Age of last applied transaction
SELECT now() - pg_last_xact_replay_timestamp() AS lag_time;

-- Current receive and replay positions
SELECT receive_start_lsn, received_lsn, latest_end_lsn
FROM pg_stat_wal_receiver;
```

## Causes of Replication Lag

### 1. Network bandwidth / latency

Symptoms: `sent_lsn` close to primary's current WAL, but `write_lsn` far behind (standby receiving slowly).

Fix:
```
wal_compression = on    # compress WAL before sending (reduces bandwidth 50-70%)
```

### 2. Standby disk I/O — can't write WAL fast enough

Symptoms: `write_lsn` close to `sent_lsn`, but `flush_lsn` lags (disk is slow for standby).

Fix: Faster disk on standby. Put standby's WAL on NVMe.

### 3. Standby disk I/O — can't apply WAL fast enough

Symptoms: `flush_lsn` good, but `replay_lsn` lags significantly.

Causes:
- Heavy DDL (many index updates to apply)
- Large sequential writes (COPY, bulk INSERT) that require many page writes on standby
- Too many parallel queries on standby consuming I/O

Fix:
- Tune standby's `shared_buffers` (larger = more pages cached, fewer disk reads during replay)
- Limit read queries on standby (they compete with WAL replay I/O)
- `max_parallel_workers` tuning on standby

### 4. Long-running queries on standby blocking WAL apply

Hot standby queries can block WAL recovery when WAL needs to modify a row that a query is reading.

```
max_standby_streaming_delay = 30s    # after 30s, cancel conflicting standby queries
max_standby_archive_delay = 30s      # same for archive recovery
```

With `hot_standby_feedback = on` (on standby), the standby tells primary what its oldest active transaction is. Primary's autovacuum won't clean rows the standby might still need. This reduces conflicts but can cause bloat on the primary.

### 5. Large transactions

One huge transaction generates a lot of WAL at once. The standby must apply all of it before it's visible. This is normal and expected.

## Alerting Thresholds

| Metric | Warning | Critical |
|---|---|---|
| Replay lag bytes | > 100MB | > 1GB |
| Replay lag time | > 10s | > 60s |
| Slot WAL retained | > 1GB | > 5GB |
| Standby disconnected | Any | > 5 min |

```sql
-- Prometheus-style query for lag in seconds
SELECT
    application_name,
    extract(epoch from replay_lag) AS lag_seconds
FROM pg_stat_replication;
```

## Intentional Lag — Delayed Standby

Sometimes you WANT a standby to lag behind, as a safety net for accidental deletes:

```
# postgresql.conf on standby
recovery_min_apply_delay = '1h'    # standby always 1 hour behind
```

If someone drops a table at 10 AM:
- Normal standbys apply the DROP immediately → no protection
- Delayed standby (1 hour behind): the DROP hasn't been applied yet → you have a 1-hour window to recover

**Workflow:**
1. Accidental DELETE/DROP detected at 10:30 AM
2. Connect to delayed standby (still 1 hour behind = has data from 9:30 AM)
3. Stop replication: `pg_wal_replay_pause()` to freeze the standby
4. Export data from the delayed standby
5. Import into production (or promote the delayed standby)
