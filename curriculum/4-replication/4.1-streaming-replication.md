# 4.1 — Streaming Replication: Setup and Monitoring

**Phase**: 4 — Replication
**Est. reading time**: 25 min

---

## What Streaming Replication Is

Streaming replication is PostgreSQL's built-in way to keep a standby server in sync with a primary.

The standby continuously receives WAL records from the primary and applies them. The result:
- Standby has a near-real-time copy of the primary's data
- If primary fails, standby can be promoted to become the new primary
- Standby can serve read-only queries (reduces load on primary)

```
PRIMARY                                     STANDBY
  │                                            │
  │── WAL stream (via replication slot) ──────►│
  │                                            │
  │ wal sender process ←────────────────────── │ wal receiver process
  │                                            │
  │ Data files (master copy)                   │ Data files (replica)
```

## Setting Up: Primary Configuration

### Step 1: postgresql.conf on primary

```
wal_level = replica              # required
max_wal_senders = 5             # allow 5 replication connections (1 per standby + backups)
wal_keep_size = 1GB             # keep this much WAL for standbys catching up
hot_standby = on                # allow read queries on standbys (set on both)
max_replication_slots = 5       # allow replication slots (Phase 4.3)
```

Restart required after changing `wal_level` and `max_wal_senders`.

### Step 2: Create replication user

```sql
CREATE USER replicator WITH REPLICATION PASSWORD 'strongpassword';
```

### Step 3: pg_hba.conf on primary

```
# Allow standby to connect for replication
host    replication     replicator      10.0.0.20/32    scram-sha-256
```

Reload pg_hba.conf:
```bash
pg_ctl reload -D /var/lib/postgresql/16/main
```

## Setting Up: Standby Server

### Step 1: Create base backup from primary

```bash
# On standby server (as postgres user)
# Clear the data directory first
rm -rf /var/lib/postgresql/16/main/*

# Take base backup from primary with -R flag (writes recovery config)
pg_basebackup \
  -h 10.0.0.10 \            # primary IP
  -U replicator \
  -D /var/lib/postgresql/16/main \
  -R \                       # write standby.signal + primary_conninfo
  -X stream \
  --checkpoint=fast \
  -P -v
```

The `-R` flag does two things:
1. Creates `standby.signal` file (tells PostgreSQL to start as standby)
2. Writes to `postgresql.auto.conf`:
   ```
   primary_conninfo = 'host=10.0.0.10 port=5432 user=replicator password=...'
   ```

### Step 2: Start the standby

```bash
pg_ctl start -D /var/lib/postgresql/16/main
```

PostgreSQL will:
1. See `standby.signal` → enter standby mode
2. Connect to primary using `primary_conninfo`
3. Start streaming WAL
4. Apply WAL to local data files continuously

## Verifying Replication

### On primary:

```sql
-- See all standbys connected and their lag
SELECT
    pid,
    application_name,
    client_addr,
    state,                     -- streaming, startup, catchup
    sent_lsn,                  -- what we sent
    write_lsn,                 -- standby wrote to disk
    flush_lsn,                 -- standby flushed (durable)
    replay_lsn,                -- standby applied (visible to queries)
    pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes,
    write_lag,                 -- time lag for write (PG10+)
    flush_lag,                 -- time lag for flush
    replay_lag,                -- time lag for replay
    sync_state                 -- async, sync, potential, quorum
FROM pg_stat_replication;
```

**What these LSN columns mean:**
- `sent_lsn`: Primary has sent up to this point
- `write_lsn`: Standby has received and written to disk (WAL on standby disk)
- `flush_lsn`: Standby has flushed (durable on standby)
- `replay_lsn`: Standby has applied to data files (queries on standby see up to here)

The most important for data safety is `flush_lsn`. For query freshness on standby, it's `replay_lsn`.

### On standby:

```sql
-- Check standby status
SELECT * FROM pg_stat_wal_receiver;

-- Is this server in standby mode?
SELECT pg_is_in_recovery();  -- true = standby, false = primary

-- How far behind is the standby?
SELECT now() - pg_last_xact_replay_timestamp() AS replication_delay;
```

## Replication Lag — Causes and Monitoring

```sql
-- Primary: lag in bytes
SELECT
    application_name,
    pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
FROM pg_stat_replication;

-- Primary: lag in seconds (time-based)
SELECT
    application_name,
    replay_lag
FROM pg_stat_replication;

-- Standby: age of last applied transaction
SELECT now() - pg_last_xact_replay_timestamp() AS lag_seconds;
```

**Common causes of high lag:**

1. **Heavy write workload on primary**: Standby can't apply WAL as fast as primary generates it
   - Fix: Bigger standby server, faster disk, tune recovery parameters

2. **Hot standby queries blocking recovery**: Long SELECT queries on standby can block WAL apply
   - Fix: `max_standby_streaming_delay = 30s` (cancel standby queries if they block recovery)
   - Or: Use a replica with `recovery_min_apply_delay` for safe read workloads

3. **Network bandwidth**: Large WAL volumes saturating the link
   - Fix: WAL compression (`wal_compression = on`)

4. **Vacuuming causing write I/O on standby**: Visibility map writes during recovery
   - This is normal, monitor but don't panic

## Read Queries on Standby (Hot Standby)

With `hot_standby = on`, the standby accepts read-only queries:

```bash
# Connect to standby (read-only)
psql -h standby-server -U myapp -d mydb

# Read queries work
SELECT * FROM orders WHERE id = 42;

# Write queries fail (expected)
INSERT INTO orders (...) ...;
# ERROR: cannot execute INSERT in a read-only transaction
```

**Routing reads to standby:**
- Use HAProxy or PgBouncer to split read traffic to standby
- Connection string: `postgresql://user@primary?target_session_attrs=read-write` vs `any`

**Important**: Data on standby is slightly behind primary. Don't read from standby if you need the freshest possible data for critical operations (e.g., "check inventory before charging card").

## Setting application_name for Standby

In `primary_conninfo` on the standby:

```
# postgresql.auto.conf on standby
primary_conninfo = 'host=10.0.0.10 port=5432 user=replicator application_name=standby1'
```

This makes `pg_stat_replication` show a meaningful name instead of a random string.

## Failover (Manual)

If primary fails and you need to promote the standby:

```bash
# On standby server
pg_ctl promote -D /var/lib/postgresql/16/main

# Or with pg_promote() function (PG12+)
psql -c "SELECT pg_promote();"

# Check it's now primary
psql -c "SELECT pg_is_in_recovery();"  # should return false
```

After promotion:
- The standby becomes a new primary
- Update your app connection strings to point to the new primary
- Old primary (if recoverable) becomes a standby: use pg_rewind to resync

We cover the full automated failover process in Phase 5 (Patroni).

## postgresql.conf on Standby

```
# Hot standby settings
hot_standby = on
hot_standby_feedback = on         # tell primary what the standby's oldest active transaction is
                                   # prevents primary's autovacuum from cleaning rows
                                   # the standby might still need for queries
                                   # CAUTION: can cause bloat on primary if standby has long queries

max_standby_streaming_delay = 30s  # cancel standby queries if WAL recovery is delayed > 30s
max_standby_archive_delay = 30s    # same but when recovering from archive

recovery_min_apply_delay = 0       # delay before applying WAL (for delayed standby)
                                    # '1h' = standby always 1 hour behind (safety net)
```

## Cascading Replication

You can chain standbys:

```
Primary → Standby1 → Standby2
```

Standby2 streams from Standby1, not from Primary. Useful when:
- Standby1 is in datacenter A, Standby2 is in datacenter B — no direct link to primary
- Reduces WAL sender connections on primary

```
# postgresql.auto.conf on Standby2
primary_conninfo = 'host=standby1-ip port=5432 user=replicator application_name=standby2'
```

Standby1 needs:
```
max_wal_senders = 3    # needs to be able to send to Standby2
```
