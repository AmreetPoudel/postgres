# 4.2 — Synchronous vs Async Replication

**Phase**: 4 — Replication
**Est. reading time**: 20 min

---

## The Fundamental Question: What Does "Committed" Mean?

In async replication (default): COMMIT returns to the client as soon as WAL is on the primary's disk. The standby might be slightly behind.

In sync replication: COMMIT only returns to the client after the standby confirms it has received (and optionally applied) the WAL.

---

## Async Replication (Default)

```
Client                 Primary                 Standby
  │                      │                        │
  │── COMMIT ───────────►│                        │
  │                      │ WAL flushed to disk     │
  │◄── OK ───────────────│                        │
  │                      │── WAL stream ─────────►│
  │                      │                        │ (async, may lag)
```

**Behavior on primary failure:**
- If primary crashes right after telling client "committed" but before WAL reaches standby
- The committed transaction is lost
- Maximum data loss = lag between primary and standby

**Use when:**
- Some data loss is acceptable (eventually consistent systems)
- Latency matters more than zero data loss
- Standby is geographically distant (high network latency)

---

## Synchronous Replication

```
Client                 Primary                 Standby
  │                      │                        │
  │── COMMIT ───────────►│                        │
  │                      │── WAL stream ─────────►│
  │                      │                        │ writes WAL to disk
  │                      │◄── ack ────────────────│
  │◄── OK ───────────────│                        │
```

COMMIT doesn't return to client until standby confirms. If primary crashes: the committed transaction is safe on the standby.

**Use when:**
- Zero data loss is required (financial systems, medical records)
- Both servers are in the same datacenter or low-latency link

---

## Configuring Synchronous Replication

```
# postgresql.conf on primary
synchronous_standby_names = 'standby1'
```

The standby's `application_name` (in `primary_conninfo`) must match.

**The synchronous_commit levels:**

```
# postgresql.conf (or per session / per transaction)
synchronous_commit = on             # default: wait for standby WAL flush
synchronous_commit = remote_write   # wait for standby to write WAL (not flush)
synchronous_commit = remote_apply   # wait for standby to apply WAL (query-visible)
synchronous_commit = local          # only wait for local WAL flush (like async)
synchronous_commit = off            # don't even wait for local flush (~200ms risk)
```

**Strongest guarantee**: `remote_apply` — you know the transaction is query-visible on standby.

**What gets waited on per level:**

| Level | Primary flush | Standby write | Standby flush | Standby apply |
|---|---|---|---|---|
| `off` | No | No | No | No |
| `local` | Yes | No | No | No |
| `remote_write` | Yes | Yes | No | No |
| `on` (default) | Yes | Yes | Yes | No |
| `remote_apply` | Yes | Yes | Yes | Yes |

---

## Multiple Synchronous Standbys

```
# Any 1 of the listed standbys must confirm
synchronous_standby_names = 'ANY 1 (standby1, standby2, standby3)'

# ALL of them must confirm
synchronous_standby_names = 'ALL (standby1, standby2)'

# First listed with highest priority (traditional)
synchronous_standby_names = 'FIRST 1 (standby1, standby2)'

# Quorum: any 2 of 3 must confirm
synchronous_standby_names = 'ANY 2 (standby1, standby2, standby3)'
```

**Quorum commit** (`ANY N`) is the most production-robust setup:
- Tolerates 1 standby being down while maintaining synchronous guarantee
- Good for 3-node setups (1 primary + 2 standbys with ANY 1)

---

## The Latency Cost of Sync Replication

Sync replication adds a round-trip to every commit:
- Same datacenter, 1Gbps network: ~0.1-0.5ms added per commit
- Same datacenter, 10Gbps network: ~0.05ms added
- Cross-datacenter: depends on network RTT (50ms RTT between DCs = 50ms added to every commit)

**The "one bad commit" trap**: If synchronous_standby_names lists a standby that is down or unreachable, COMMIT will BLOCK FOREVER (or until `wal_sender_timeout`).

```
wal_sender_timeout = 60s    # how long to wait before declaring standby dead
```

With default `synchronous_commit = on` and a dead standby:
- Every commit blocks for 60 seconds
- Your entire application is effectively stopped
- Fix: Use `ANY 1 (standby1, standby2)` with 2 standbys — losing one doesn't block

## Per-Transaction Sync Level

You can override synchronous_commit for individual transactions:

```sql
-- Critical transaction: ensure standby durability
SET synchronous_commit = remote_apply;
BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
COMMIT;
RESET synchronous_commit;

-- Bulk load: async is fine, speed matters
SET synchronous_commit = off;
INSERT INTO logs SELECT ... FROM generate_series(1, 1000000);
COMMIT;
RESET synchronous_commit;
```

## Practical Recommendation for Two-Datacenter Setup

Your goal is a 2-site HA cluster. Here's the production setup:

```
Site A (primary datacenter):
  PostgreSQL primary
  synchronous_standby_names = 'ANY 1 (siteB-standby, siteA-standby)'

Site A (local standby, optional):
  PostgreSQL standby
  Fast LAN → async or sync with low latency

Site B (DR datacenter):
  PostgreSQL standby
  High network latency → consider async for write performance
  OR: Use sync with remote_write (faster than full sync)
```

For zero RPO (zero data loss on any failure): sync replication to at least one standby.
For near-zero RPO with best write performance: async with monitoring of lag.

## Monitoring Sync Replication

```sql
-- Check sync state of all standbys
SELECT application_name, sync_state, replay_lag
FROM pg_stat_replication;
-- sync_state: 'sync', 'potential', 'async', 'quorum'

-- 'sync' = this standby is the active sync replica
-- 'potential' = listed in synchronous_standby_names but not currently the active sync one
-- 'async' = not in synchronous_standby_names, purely async
-- 'quorum' = counted toward quorum commit
```

**Alert conditions:**
- No standbys in `sync` or `quorum` state while synchronous_standby_names is set → all commits are blocked
- Lag time > threshold → standby is falling behind
