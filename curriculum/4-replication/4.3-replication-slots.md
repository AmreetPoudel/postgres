# 4.3 — Replication Slots: Guaranteed WAL Retention

**Phase**: 4 — Replication
**Est. reading time**: 15 min

---

## The Problem Without Slots

Without a replication slot, PostgreSQL deletes old WAL segments based on `wal_keep_size` and checkpoint policies. If a standby falls behind (network issue, restart), the WAL it needs might be deleted before it can catch up.

Result: standby loses its replication stream, must be rebuilt from a new base backup.

---

## What a Replication Slot Does

A replication slot is a bookmark. It tells PostgreSQL:

> "This slot's consumer needs WAL starting from this LSN. Don't delete WAL until this slot has consumed it."

PostgreSQL will keep all WAL that any active slot needs, regardless of `wal_keep_size`.

---

## Physical Replication Slots

Used for streaming replication standbys.

```sql
-- Create a physical slot on primary
SELECT pg_create_physical_replication_slot('standby1_slot');

-- See all slots
SELECT slot_name, slot_type, active, restart_lsn,
       pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS lag_bytes
FROM pg_replication_slots;
```

Configure the standby to use the slot:
```
# postgresql.auto.conf on standby
primary_slot_name = 'standby1_slot'
```

Now the standby can fall behind significantly and still catch up when it reconnects — WAL is preserved.

---

## The Critical Danger of Slots

**A slot is only safe if the standby is actively consuming it.**

If a standby is offline for a long time and has a slot:
- PostgreSQL keeps accumulating WAL for that slot
- `pg_wal/` directory grows without bound
- Eventually, disk fills up
- Database stops accepting writes → emergency

```sql
-- Monitor slot WAL retention (should be near 0 for healthy standbys)
SELECT
    slot_name,
    active,
    pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS retained_bytes,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_pretty
FROM pg_replication_slots
ORDER BY retained_bytes DESC;
```

**Set a max WAL retention limit** (PG13+):
```
max_slot_wal_keep_size = 10GB    # delete WAL even if a slot needs it, once this is exceeded
                                  # standby will need to be rebuilt, but disk won't fill
```

This is a safety valve. Set it. Without it, a dead standby with a slot = ticking disk bomb.

**Drop a slot that's no longer needed:**
```sql
SELECT pg_drop_replication_slot('standby1_slot');
```

---

## Logical Replication Slots

Used for logical replication and CDC (Change Data Capture) tools like Debezium.

```sql
-- Create a logical slot
SELECT pg_create_logical_replication_slot('my_logical_slot', 'pgoutput');

-- Peek at changes without consuming them
SELECT * FROM pg_logical_slot_peek_changes('my_logical_slot', NULL, 10);

-- Consume changes
SELECT * FROM pg_logical_slot_get_changes('my_logical_slot', NULL, 10);

-- Drop when done
SELECT pg_drop_replication_slot('my_logical_slot');
```

Logical slots retain WAL just like physical slots — same disk-fill danger applies.

## Patroni and Slots

If using Patroni (Phase 5), Patroni manages replication slots for you:
- Creates physical slots for each standby
- Drops slots when a node is removed
- Monitors slot lag and alerts

You should still know how to inspect and manually manage slots.

## Slot Monitoring Query for Dashboard

```sql
-- Complete slot health view
SELECT
    slot_name,
    slot_type,
    active,
    CASE WHEN active THEN 'connected' ELSE 'DISCONNECTED' END AS status,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_retained,
    now() - pg_last_xact_replay_timestamp() AS approx_lag
FROM pg_replication_slots;
```

**Alert thresholds:**
- `active = false` → standby disconnected → investigate immediately
- `wal_retained > 5GB` → investigate why standby is behind
- `wal_retained > max_slot_wal_keep_size * 0.8` → critical, slot about to be invalidated
