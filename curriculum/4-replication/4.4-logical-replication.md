# 4.4 — Logical Replication: Selective, Cross-Version Replication

**Phase**: 4 — Replication
**Est. reading time**: 20 min

---

## Physical vs Logical Replication

**Physical replication** (Phase 4.1): Replicates raw WAL bytes. Standby is an exact copy. Must be same PostgreSQL major version. Standby is read-only.

**Logical replication**: Decodes WAL into logical changes (INSERT, UPDATE, DELETE on specific tables) and sends them. More flexible:
- Replicate only specific tables
- Replicate to a different PostgreSQL major version
- Replicate to a different database or schema
- Subscriber can write to tables not being replicated
- Useful for zero-downtime major version upgrades

---

## How Logical Replication Works

```
Publisher (source)                    Subscriber (target)
    │                                       │
    │ WAL Level: logical                    │
    │ Publication: defines what to publish  │
    │                                       │
    │── decoded changes (INSERT/UPDATE/DELETE) ──►│
    │                                       │
    │                                Subscription: applies changes
```

## Setting Up Logical Replication

### Publisher (source database)

```
# postgresql.conf
wal_level = logical         # required for logical replication
max_replication_slots = 10  # need one per subscription
max_wal_senders = 10
```

```sql
-- Create a publication (defines what to publish)

-- All tables in current database
CREATE PUBLICATION my_pub FOR ALL TABLES;

-- Specific tables only
CREATE PUBLICATION my_pub FOR TABLE orders, customers, products;

-- With row filter (PG15+): only publish active customers
CREATE PUBLICATION my_pub FOR TABLE customers WHERE (is_active = true);

-- See publications
SELECT * FROM pg_publication;
SELECT * FROM pg_publication_tables;
```

### Subscriber (target database)

```sql
-- Create subscription (connects to publisher and starts replication)
CREATE SUBSCRIPTION my_sub
    CONNECTION 'host=publisher-host port=5432 user=replicator dbname=mydb password=pass'
    PUBLICATION my_pub;

-- This automatically:
-- 1. Creates a replication slot on the publisher
-- 2. Copies initial data (like pg_dump/restore for those tables)
-- 3. Starts streaming ongoing changes

-- Check subscription status
SELECT * FROM pg_subscription;
SELECT * FROM pg_stat_subscription;
```

## Replication User for Logical Replication

```sql
-- On publisher: replication user needs REPLICATION + read access to published tables
CREATE USER logical_rep WITH REPLICATION PASSWORD 'pass';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO logical_rep;
GRANT USAGE ON SCHEMA public TO logical_rep;

-- Or superuser (simpler but less secure)
-- For PG16+: pg_create_subscription privilege for non-superusers
```

## Limitations of Logical Replication

1. **Schema not replicated**: DDL (CREATE TABLE, ALTER TABLE) is not replicated. You must apply schema changes manually on subscriber.

2. **Sequences not replicated**: Auto-increment IDs in sequences are not replicated. If subscriber generates IDs, they might conflict.

3. **Large objects not replicated**.

4. **Conflicts**: If both publisher and subscriber write to the same table, you'll get conflicts. Subscriber tables in logical replication should be read-only or use non-overlapping key ranges.

5. **Table must have replica identity**: For UPDATE and DELETE to replicate, the table needs a way to identify rows:
```sql
-- Check replica identity
SELECT relname, relreplident FROM pg_class WHERE relname = 'orders';
-- 'd' = default (primary key)
-- 'f' = full (entire row as identity, slow)
-- 'n' = nothing (can't replicate UPDATE/DELETE)
-- 'i' = specific index

-- Tables without primary key need explicit replica identity
ALTER TABLE no_pk_table REPLICA IDENTITY FULL;
-- or
ALTER TABLE no_pk_table REPLICA IDENTITY USING INDEX some_unique_index;
```

## Zero-Downtime Major Version Upgrade Using Logical Replication

This is one of the most valuable uses of logical replication:

```
Old server (PG14):  Publication → logical replication → New server (PG16)
                    │                                         │
                    │ Initial data copy + ongoing changes     │
                    │─────────────────────────────────────────►│
                    │                                         │
                    │ Monitor lag → nearly zero lag           │
                    │                                         │
                    └── Switch app traffic to PG16 ──────────┘
                    (old PG14 can be decommissioned)
```

Steps:
1. Set up PG16 server
2. Create identical schema on PG16 (pg_dump --schema-only, then pg_restore --schema-only)
3. Create publication on PG14, subscription on PG16
4. Wait for initial sync and lag to reach near-zero
5. Point application at PG16 (connection string change, PgBouncer update)
6. Decommission PG14

This gives you:
- No downtime during data sync
- Only a brief downtime when switching (seconds to minutes)

## Monitoring Logical Replication

```sql
-- On publisher: subscription status
SELECT
    slot_name,
    active,
    pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn) AS lag_bytes
FROM pg_replication_slots
WHERE slot_type = 'logical';

-- On subscriber: subscription worker status
SELECT
    subname,
    pid,
    relid::regclass AS table,
    received_lsn,
    last_msg_send_time,
    last_msg_receipt_time,
    latest_end_time
FROM pg_stat_subscription;

-- Check for conflicts/errors
SELECT * FROM pg_stat_subscription_stats;  -- PG15+
```

## Managing Subscriptions

```sql
-- Disable subscription (stop receiving changes)
ALTER SUBSCRIPTION my_sub DISABLE;

-- Re-enable
ALTER SUBSCRIPTION my_sub ENABLE;

-- Refresh subscription (pick up new tables added to publication)
ALTER SUBSCRIPTION my_sub REFRESH PUBLICATION;

-- Drop subscription
DROP SUBSCRIPTION my_sub;  -- also drops the slot on publisher

-- Drop subscription but keep slot (dangerous - manage manually)
DROP SUBSCRIPTION my_sub WITH (slot_name = NONE);
```
